# Vuyro PRD

## 한 줄 정의

**작업(티켓)이 기획부터 QA까지 거치는 단계를 그래프로 정의하고, 사람과 AI 에이전트가 그 그래프 위에서 함께 일하는 단독 데스크톱 앱.**

## 문제

- Claude Code나 Codex 같은 코딩 에이전트는 강력하지만, 기획 → 스펙 → 계획 → 구현 → 검수로 이어지는 **전체 흐름**은 사람이 손으로 이어 붙이고 있다.
- 오케스트레이션 툴(Paperclip, Orca 등)은 "에이전트를 어떻게 돌리나"에 집중한다. "작업이 어떤 단계를 거쳐 완료되나"를 정의하고 재사용하는 툴은 드물다.
- 가장 가까운 Archon도 개발자용 CLI/YAML 엔진이다. 티켓 개념, 기획자용 UX, 저장소 밖 산출물(Perforce, 문서) 추적, 상위 단계가 바뀌었을 때의 처리가 없다.
- 개발 도중 기획이 바뀌면 어떤 작업을 다시 해야 하는지 사람이 일일이 판단해야 한다.
- 에이전트가 무엇을 하고 있는지, 얼마나 걸렸는지, 토큰과 비용을 얼마나 썼는지 한눈에 보기 어렵다.

## 목표

1. **워크플로를 그래프로 정의하고 재사용한다.** 기본 템플릿을 제공하고, 다른 사람이 만든 워크플로를 불러올 수 있다.
2. **사람과 AI가 같은 흐름 안에서 일한다.** 사람 승인 게이트, 에이전트 자동 실행, 병렬 실행, 스크립트 노드를 섞어 쓴다.
3. **변경에 강하다.** QA 반려 루프, 변경 요청(CR)과 Stale 전파로 "무엇을 다시 해야 하는지"를 툴이 알려준다.
4. **모든 실행이 보인다.** 노드별 소요 시간, 토큰, 도구 호출, 세션, 현재 상태를 수집해서 보여준다. 목적은 **어느 작업이 토큰을 얼마나 쓰고 어디서 병목이 생기는지 분석하는 것**이다. 그래서 기준 단위는 토큰과 시간이다. 금액은 공급자가 실제 값을 줄 때만 보조로 표시한다(Codex는 토큰만, 추정 금액은 표시하지 않음).
5. **AI가 툴 자체를 다룬다.** 티켓 단위와 앱 전체 단위의 에이전트 패널에서 대화로 확인하고 조작한다.
6. **확장할 수 있다.** VSCode나 Obsidian처럼 외부 개발자가 플러그인(노드 타입, 산출물 타입, 에이전트 어댑터)을 만들 수 있다.

## 대상 사용자

| 사용자 | 주로 하는 일 | 주로 쓰는 화면 |
|---|---|---|
| 기획자 | 브레인스토밍, 스펙 작성, 승인·반려, 변경 요청 | 칸반 보드, 결정 인박스, 에이전트 패널 |
| 개발자 | 계획 승인, 에이전트 작업 확인, 그래프와 템플릿 편집 | 그래프 캔버스, 에이전트 패널 |
| 운영·리드 | 실행 중 에이전트 감시, 병목 확인, 비용 관리 | 관제실, 타임라인 |

첫 사용 환경은 게임 개발팀(Unreal, Perforce)이다.

## 핵심 개념

- **티켓:** 작업 하나. 워크플로 템플릿을 한 번 실행한 것이다. 시작할 때 템플릿 버전을 고정한다.
- **노드:** 티켓 안의 각 단계. 완료 방식은 네 가지다.
  - 사람이 승인해서 완료
  - 에이전트가 끝나서 완료
  - 앞 노드들이 모두 끝나서 완료(병렬 합류)
  - 스크립트 결과로 완료(예: p4 sync)
- **노드 상태:** Wait → Running → Review → Done. 그 밖에 Failed, Rejected, Stale, Paused(일시정지. 다른 티켓의 claim을 기다리는 경우 등), Queued(공유 노드의 대기열에서 기다림)가 있다.
- **산출물:** 코드, 기획서, 데이터는 툴 폴더 밖(로컬 파일, git, Perforce, Confluence/Jira)에 있다. 툴은 **위치와 버전만** 기록한다.
- **변경 요청(CR):** 상위 노드를 다시 열고, 그 산출물을 읽는 하위 노드를 Stale로 표시한다. AI가 영향 범위를 제안하고 사람이 확정한다.
- **공유 노드:** 티켓 밖 프로젝트 범위에 있는 노드. 여러 티켓이 대기열에 들어오면 한 번에 처리하고(예: Unreal 빌드), 결과를 티켓마다 나눠 돌려준다.
- **BlackBoard:** 여러 워크플로와 티켓이 함께 쓰는 공용 게시판(값, 링크·폴더 참조, 점유 표시). 항목마다 버전이 있고 누가 읽었는지 기록해서, 값이 바뀌면 Stale을 전파한다.

## 기능 범위

### MVP

> **데모 버전 = 아래 MVP 목록 전체**(2026-10-23 결정). 데모에서 에이전트가 작업하는 대상은 새로 만든 샘플 git 저장소(메모장 같은 작은 앱)다. 구현 중 생긴 기획 질문은 기본값으로 진행하고 [[결정 대기]]에 모아 데모 후 확인한다.

- 기본 템플릿 1개(AI-Native SDLC: BrainStorming → Spec → Plan → 병렬 Dev → QA → Done)와 반려 루프
- 티켓 생성과 진행, 사람 승인 게이트
- Claude CLI / Codex CLI 실행과 이벤트 수집(`stream-json` 등 구조화된 출력 모드)
- 산출물 레지스트리(경로 + 버전)와 에이전트용 CLI(`vuyro artifact add`, `vuyro node done`)
- 노드별 시간, 토큰, 도구 호출 표시(병목 분석용. 금액은 보조)
- 트레이 상주: 창을 닫아도 앱이 트레이에 남고, 에이전트 실행·공유 노드 대기열·감시는 멈추지 않는다
- 화면: 그래프 캔버스, 칸반 보드
- 템플릿과 노드 타입의 JSON 가져오기 / 내보내기
- 내부 체크아웃(여러 노드의 같은 파일 동시 수정 방지, 자동 체크아웃 훅은 옵션)
- 작업 공간 모드: 같은 폴더(`shared`) 또는 git worktree 병렬 처리(`worktree`, 사용자가 선택)
- 공유 노드: 여러 티켓의 작업을 모아 한 번에 빌드하는 노드(대기열, 실행 조건, 실행 중 소스 보호, 실패 원인 티켓 추정, 원인 티켓이 고쳐질 때까지 멈춤)

### 다음 단계
- 변경 요청과 Stale 전파
- 관제실, 타임라인, 대시보드
- 에이전트 패널(티켓 / 프로젝트 범위)
- AI 권한 정책(명령 단위 allow / ask / deny 규칙, 프리셋, 규칙 저장)
- BlackBoard(앱 / 프로젝트 범위 공용 게시판)
- 템플릿 추가(버그 수정, 작은 작업, 퍼포스 연동)와 그래프 편집기
- 플러그인 API와 템플릿·플러그인 공유
- MCP 서버(에이전트가 툴을 조작하는 두 번째 경로)

## 비목표 (지금은 하지 않음)

- 호스팅 서비스나 웹 SaaS. 단독 데스크톱 앱이 먼저다.
- MVP에서의 팀 협업과 여러 앱 연동. MVP는 **내 로컬에서만 도는 앱**이다. 공유는 JSON 파일과 클립보드로 한다. 다만 나중에 동기화를 붙일 수 있게 id, 버전, 이벤트 기록은 처음부터 갖춘다.
- 에이전트 자체 개발. 기존 CLI 에이전트를 실행하고 관찰하는 데 집중한다.
- 범용 프로젝트 관리 툴(Jira 대체). 티켓은 워크플로를 실행하는 단위로만 쓴다.
- YAML이나 셸 지식이 있어야 쓰는 구조. 기획자가 쓸 수 있어야 한다.

## 설계 원칙

- **화면의 모든 동작은 같은 명령 API를 거친다.** UI 버튼, `vuyro` CLI, 에이전트 패널, MCP가 같은 경로로 실행되고 같은 작업 기록에 남는다.
- **엔진은 UI와 분리한다.** 데스크톱 앱과 CLI가 같은 엔진을 쓴다.
- **상태는 이벤트로 기록하고, 통계는 이벤트에서 계산한다.** 크래시 후 재개, 감사 기록, 새 지표 추가가 쉬워진다.
- **비용이 들거나 되돌릴 수 없는 작업은 기본적으로 사람이 확인한다.** 사람 게이트 승인까지 AI에게 맡길 수 있지만, 맡기는 설정은 사람이 하고 AI가 한 승인은 구분해서 기록한다.
- **항상 커스텀할 수 있게 만든다.** 노드 타입과 입출력 스키마는 사람도 에이전트도 만들고 고칠 수 있다. 기본 노드도 같은 방식으로 만들고 특별 취급하지 않는다. 노드 사이에 넘기는 봉투의 바깥 모양만 고정한다. ([[n8n 노드 데이터 전달 분석]] §6.7)
- **만든 것은 모두 JSON으로 가져오고 내보낸다.** 노드 타입, 템플릿, 스키마, 권한 프리셋, BlackBoard 정의를 같은 봉투 형식으로 주고받는다. 비밀값은 들어가지 않는다.
- **AI가 Vuyro를 다루는 범위는 전부 옵션이다.** 명령 하나하나에 allow / ask / deny 규칙을 건다. 단, AI가 자기 권한을 올리는 것은 막는다. ([[공유·권한·BlackBoard 설계]])

## 차별점

1. 기획 단계부터 사람과 AI가 함께 쓰는 티켓 중심 흐름
2. 저장소 밖 산출물 추적(Perforce, Confluence, 문서)
3. 변경 요청과 Stale 전파
4. 실행 관측(시간, 토큰, 비용, 도구 호출)이 기본으로 들어감
5. 툴 안의 에이전트가 툴을 직접 조작
6. 플러그인 생태계를 갖춘 단독 앱, 게임 개발(Perforce) 친화
