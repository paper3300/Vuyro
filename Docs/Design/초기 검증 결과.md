## #1 엔진 파이프 접근 통제

### 결론 (2026-10-24 개정)

**파이프 접근 자체를 막는 대신, 명령은 엔진 토큰으로 인증한 연결에서만 처리한다**(결정 C, Claude·Codex 합의, [[기술 스택 결정]] §3·§14).

- 처음 목표는 "파이프를 현재 사용자만 열 수 있게"였다. Node가 만든 파이프에 사후로 DACL을 거는 것까지는 됐지만, 확실히 닫을 수 없었다(아래 "버린 방식").
- 지금 방식: 토큰 파일(현재 사용자 전용 ACL) + 상호 인증 핸드셰이크 + 미인증 연결 제한.

### Node 기본값은 열려 있다 (실측, 유지되는 사실)

`net.Server.listen('\\.\pipe\...')`로 만든 파이프의 보안 설명자:

```
O:<user>G:DUD:(A;;FA;;;SY)(A;;FA;;;BA)(A;;FA;;;<user>)(A;;FR;;;WD)(A;;FR;;;AN)
```

- Everyone(`WD`)과 Anonymous(`AN`)에 읽기(FR)가 있다. Node API에는 보안 설명자를 줄 방법이 없다.
- libuv는 인스턴스를 `PIPE_REJECT_REMOTE_CLIENTS` 없이 만든다(`NamedPipeType` = 0). 이 플래그는 만든 뒤에는 바꿀 수 없다.
- 따라서 **다른 사용자도 이 파이프를 읽기 전용으로 열 수 있다.** 쓰기 권한이 없으므로 hello를 보낼 수 없고, 서버는 hello 전에는 아무것도 쓰지 않는다.

### 지금 방식

**엔진 토큰 파일** (`packages/engine/src/ipc/engine-token.ts`)

1. `%LOCALAPPDATA%\Vuyro\engine\` 아래에 임시 파일을 빈 채로 만든다.
2. 현재 사용자 전용 DACL(`D:P(A;;FA;;;<user>)`, 상속 차단)을 명시하고, 같은 핸들로 다시 읽어 확인한다.
3. 무작위 32바이트 비밀을 쓴다.
4. `engine.token`으로 옮긴다(이름 바꾸기는 파일 자신의 DACL을 유지한다). 옮긴 뒤 한 번 더 확인한다.
5. 어느 단계든 실패하면 남은 파일을 지우고 예외를 던진다. 엔진은 시작하지 않는다.
6. 엔진이 시작할 때마다 새 토큰을 만든다.

**시작 경로** (`startEnginePipe`)

- 순서는 다음과 같다.
  1. 옵션 검증
  2. `prepareEngineToken`: 임시 파일에 ACL을 적용하고 확인한 뒤 비밀을 쓴다. 최종 경로는 건드리지 않는다.
  3. 리스닝: `FILE_FLAG_FIRST_PIPE_INSTANCE`가 단일 인스턴스 확인이다.
  4. `commit`: 자리로 옮기고 다시 확인한다.
- 실패하면 이렇게 된다.
  - 리스닝 실패(예: 두 번째 시작의 `EADDRINUSE`): 임시 파일만 지운다. 실행 중인 엔진의 토큰과 인증은 그대로다.
  - `commit` 실패: 리스닝을 멈춘다.
- 중복 시작 회귀 테스트는 같은 파이프·같은 토큰 경로로 확인한다. 토큰 준비 실패, 다른 이유의 리스닝 실패, `commit` 실패도 실패를 주입해 시험하고, 변이 시험 6개로 각 가드를 확인했다.
- `listenAuthenticatedPipe`는 `VerifiedEngineToken`만 받는다. 이 토큰은 `createEngineToken` 안에서만 만들 수 있다(모듈 밖에 노출하지 않은 심볼 팩토리, 발급 목록 `WeakSet`).
- 리스닝 직전에 토큰 파일을 다시 확인한다. DACL이 현재 사용자 전용이 아니거나, 파일 내용이 그 토큰이 아니거나, 파일이 없으면 시작이 실패한다.
- 패키지 진입점에는 `startEnginePipe`만 공개한다.

**상호 인증 핸드셰이크** (`packages/engine/src/ipc/pipe-auth.ts`, NDJSON)

```
C → S  {"type":"auth.hello","protocol":"vuyro-auth-1","nonce":<32바이트 hex>}
S → C  {"type":"auth.challenge","nonce":<hex>,"proof":HMAC(token, "server", cN, sN)}
C → S  {"type":"auth.response","proof":HMAC(token, "client", cN, sN)}
S → C  {"type":"auth.ok"}            이후 JSON-RPC
```

- 토큰을 평문으로 보내지 않는다. 서버가 먼저 증명하므로, 이름을 선점한 가짜 서버에 클라이언트 증명이 가지 않는다.
- 증명은 역할 문자열(`server`/`client`)을 넣어서 만든다. 그래서 상대의 증명을 되돌려 보내는 반사 공격이 안 된다. 비교는 `timingSafeEqual`(상수 시간)로 한다.
- 인증 전 메시지가 하나라도 형식에 맞지 않으면 이유를 알리지 않고 끊는다. 해당하는 것: JSON이 아님, 프로토콜이 다름, nonce·증명의 길이나 형식이 다름, 순서가 틀림.
- `auth.ok` 전에는 명령 처리기를 부르지 않는다. 핸드셰이크 바로 뒤에 붙어 온 바이트는 처리기에 그대로 넘긴다.
- 처리기가 리스너를 늦게 붙여도 첫 요청이 사라지지 않는다. 처리기가 예외를 던지면 그 소켓을 파기한다.

**미인증 연결 제한** (옵션, 기본값)

| 항목 | 기본 | 허용 범위 |
|---|---|---|
| 동시에 인증 중인 연결 | 16개. 넘으면 바로 끊는다 | 1 – 65536 |
| 인증 메시지 바이트(hello·response 줄과 끝나지 않은 줄. 응답 뒤의 첫 요청은 세지 않음) | 2 KiB | 1 – 1 MiB |
| 인증 제한 시간 | 5초 | 1 – 2³¹−1 ms |

한도 값은 범위 안의 정수여야 한다. NaN, 무한대, 0, 음수, 소수, 문자열, null이면 토큰을 만들기 전에 시작이 실패한다. 클라이언트의 `timeoutMs`도 같은 규칙을 따른다.

**그대로 두는 것**

- 이름 선점·중복 실행: libuv가 첫 인스턴스를 `FILE_FLAG_FIRST_PIPE_INSTANCE`로 만든다. 그래서 같은 이름이 있으면 `listen`이 `EADDRINUSE`로 실패한다. 이것을 사용자별 단일 인스턴스 잠금으로도 쓴다.
- koffi: 현재 사용자 SID를 읽고 토큰 파일 DACL을 걸고 다시 읽는 데 필요하므로 엔진 의존성에 남긴다. 파이프 관련 Win32 바인딩은 모두 지웠다.

### 남는 위험

- **같은 사용자의 다른 프로세스는 토큰을 읽을 수 있다.** 에이전트 CLI도 같은 사용자로 돈다. 그래서 연결 인증으로는 사람 UI와 에이전트를 구분하지 못한다.
  - AI 권한은 M1 명령 버스에서 명령마다 판정한다.
  - 사람 UI 자격을 어떻게 나눌지는 [[구현 계획]] M1/M3의 결정 항목이다.
- 같은 PC의 관리자는 토큰 파일을 읽을 수 있다. 위협 모델 밖이다.
- 다른 사용자도 파이프를 읽기 전용으로 열 수 있으므로, 인스턴스를 점유하거나 동시 인증 수 한도를 채울 수 있다(같은 PC의 서비스 거부). 자기 계정 외의 로컬 사용자가 있는 PC는 MVP 대상이 아니라고 보고 둔다.
- 원격(SMB)에서 들어오는 연결도 토큰 파일을 읽을 수 없으면 인증하지 못한다. 네트워크 로그온 거부 ACE는 이제 걸지 않는다.

### 버린 방식: 사후 DACL + 핸들 탐색 + 클라이언트 PID 검사

- **했던 것:**
  - 프로세스 핸들 목록에서 libuv의 서버 인스턴스를 찾아 DACL을 바꿨다.
  - 연결마다 `GetNamedPipeClientProcessId` → 토큰 SID로 클라이언트를 확인했다.
  - 거부한 인스턴스는 `DisconnectNamedPipe`로 끊었다.
- **실측으로 확인한 사실:**
  - DACL은 인스턴스가 아니라 파이프 이름 단위로 걸린다.
  - DACL에서 빠진 주체는 OS가 막는다(`EPERM`).
  - SMB 루프백(`\\localhost\pipe\…`)은 로컬 토큰으로 처리된다.
- **버린 이유:** 검수에서 fail-open이 네 번 나왔다.
  1. accept 순서를 가정했다.
  2. PID 조회 실패를 통과시켰다.
  3. 인스턴스를 놓치면 검증 없이 처리기에 닿았다.
  4. 관계없는 핸들의 이름 조회 실패로 시작 자체가 실패했고, 동기 핸들 조회가 멈출 위험도 있었다.
  - 공통 원인은 Node가 감춘 OS 상태를 밖에서 추론해야 한다는 구조였다. 코드와 테스트는 지웠고, 이력은 git에 있다.

## #5 worker 안의 `node:sqlite` WAL과 동시 읽기

### 결론

**문제 없다.** worker 안에서 WAL이 켜진다. 다른 worker의 읽기 연결은 쓰기 트랜잭션이 열려 있어도 기다리지 않고 마지막 커밋 시점의 스냅샷을 읽는다. 실험 플래그나 경고는 나오지 않는다.

### 구조

- `SqliteWorker`: `node:sqlite` 연결 하나를 worker 스레드 하나에 둔다. 요청은 순서대로 처리한다(`exec`, `run`, `all`, `get`, `transaction`).
- `transaction`은 `BEGIN IMMEDIATE … COMMIT`으로 묶고, 하나라도 실패하면 롤백한다.
- 쓰기 연결: `journal_mode=WAL`, `synchronous=FULL`(기본), `busy_timeout=5000`, `foreign_keys=ON`.
- 읽기 연결: `readOnly`로 연다.

### 확인한 것 (테스트)

| 확인 | 결과 |
|---|---|
| 쓰기 worker가 WAL로 열림, `-wal` 파일 생김 | 확인 |
| 트랜잭션 원자성: 중복 키로 실패하면 같은 트랜잭션의 앞 문장도 롤백 | 확인 (`SQLITE_CONSTRAINT_UNIQUE`) |
| 쓰기 트랜잭션이 열린 동안 읽기 worker가 이전 스냅샷을 바로 읽음 | 확인, 커밋 뒤에는 새 값 |
| 연속 쓰기(100건 × 50 트랜잭션) 중 읽기 worker 2개가 계속 읽음 | 오류 없음. 개수가 줄지 않고 항상 100의 배수(커밋 중간이 안 보임), revision에 빈틈 없음 |
| 읽기 전용 연결에 쓰기 | `SQLITE_READONLY` |
| worker가 1초 넘는 쿼리를 도는 동안 메인 스레드 | 최대 공백 2.43 ms (스파이크) |

### 수치 (스파이크)

이벤트 한 건 ≈ 300바이트 JSON, 집계 200개, 고유 인덱스 `(aggregate_id, revision)`.

**긴 읽기 트랜잭션과 WAL 크기**

- 읽기 쪽이 스냅샷을 잡고 있는 동안 2만 건을 쓰면 WAL이 16.7 MB까지 커진다. 체크포인트가 그 스냅샷 너머로 진행하지 못하기 때문이다.
- 읽기 트랜잭션을 끝내고 `wal_checkpoint(TRUNCATE)`를 부르면 0 MB가 된다.

### 해석과 결정

- **쓰기 worker 1개 + 읽기 전용 worker 1개로 시작한다.** 같은 worker에서 읽으면 쓰기 뒤에 줄을 서서 p99가 14~17 ms, 최대 39 ms로 늘어난다. 읽기 전용 worker는 p99가 0.5~3.6 ms다. 화면 조회와 이벤트 구독 읽기는 읽기 worker로 보낸다. 부족하면 읽기 worker를 늘린다.
- **`synchronous`는 FULL을 기본으로 하고 옵션으로 둔다.**
  - 이벤트가 정본이다. NORMAL은 프로세스 크래시에는 안전하지만, 전원이 나가면 마지막 커밋이 사라질 수 있다.
  - FULL의 단건 커밋은 초당 약 460건(커밋당 약 2 ms)이다. 에이전트 출력처럼 이벤트가 몰리면 M1 이벤트 저장소에서 쓰기 worker가 대기 중인 명령을 한 트랜잭션으로 묶어 커밋한다(group commit). 배치 10만 돼도 초당 4,000건이다.
- **읽기 트랜잭션은 짧게 유지한다.** 엔진이 한가할 때 `wal_checkpoint(TRUNCATE)`를 돌린다.
- Windows에서는 `monitorEventLoopDelay`로 이벤트 루프 지연을 잴 수 없다. 타이머 해상도(약 15.6 ms)만 보인다. 지연 지표가 필요하면 `setImmediate` 간격으로 잰다.

### 한계

- 이 PC의 SSD 기준이다. 디스크와 백신 실시간 검사에 따라 fsync 비용이 달라진다.
- `node:sqlite`의 안정성 등급은 여전히 1.2(release candidate)다. Node 버전을 올릴 때 이 테스트와 스파이크를 다시 돌린다.
- 읽기 worker 여러 개의 처리량은 재지 않았다. 2개가 함께 정상 동작하는 것만 확인했다.

**정리**

- 두 CLI 모두 파일 수정 직전에 막을 수 있다. 다만 **공통으로 동작하는 방식은 JSON 거부 하나뿐이다.** Vuyro 훅은 exit 2를 쓰지 않고 항상 JSON `deny`를 낸다. 같은 훅 스크립트를 두 CLI에 함께 쓸 수 있다.
- Codex는 신뢰 우회 플래그가 있어야 주입한 훅이 돈다. 이 플래그를 주면 그 실행에서 **다른 훅(사용자·프로젝트 훅)도 신뢰 확인 없이 돈다.** 그래서 대안을 M4에서 정한다.
  - (1) 플래그를 주고, 대상 저장소의 프로젝트 훅이 실제로 함께 실행되는지 확인한다.
  - (2) 사용자 Codex 설정의 신뢰 기록(`[hooks.state] trusted_hash`)에 Vuyro 훅을 등록한다. 사용자 설정 파일을 고치는 일이라 동의를 받아야 한다.
  - 별도 `CODEX_HOME`은 쓰지 않는다. 로그인 정보를 복사해야 하고, 토큰이 갱신되면 원래 로그인이 깨질 수 있다.
- **Codex는 거부된 호출을 stdout에 남기지 않는다.** 거부 기록의 정본은 Vuyro 훅 자신이다. 훅이 거부할 때 `vuyro` 명령으로 이벤트를 남긴다.
- **셸로 쓰는 수정은 파일 도구 매처로 막을 수 없다**(Claude Bash/PowerShell, Codex Bash). 명령 문자열을 해석해서 막는 것은 믿을 수 없으므로, 사후 검출([[기술 스택 결정]] §10 감시 + SHA-256)이 최종 안전망이다. 노드 설정에서 셸 도구를 빼는 것은 선택지로 둔다.

### M1 이벤트 계약에 반영할 것

1. **[M1 계약] 실행의 정본 식별자는 Vuyro가 부여하는 실행 id(run id)다.** Vuyro는 에이전트 프로세스를 띄울 때마다 run id를 만들어 저장하고, 그 실행의 모든 이벤트에 붙인다.
   - 공급자 세션 id(Claude `session_id`, Codex `thread_id`)는 **이어하기에 쓰는 속성**으로만 보관한다. 실행을 구분하는 키로 쓰지 않는다.
   - 이유: 이어하기한 실행도 같은 세션 id를 쓴다. Claude는 `num_turns`도 원 실행과 이어하기가 둘 다 1이라, "세션 id + 턴 번호" 조합도 겹친다(픽스처 `simple`/`resume`로 테스트).
   - 세션 하나에 run이 여러 개 달린다. run에는 "이어받은 이전 run id"를 기록한다.
2. **토큰 정규화**: `{ input(캐시 제외), cacheRead, cacheWrite, output, reasoning? }`.
   - Claude: `input_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`, `output_tokens`를 그대로 쓴다.
   - Codex: `input = input_tokens − cached_input_tokens`, `cacheRead = cached_input_tokens`, `cacheWrite = cache_write_input_tokens`, `reasoning = reasoning_output_tokens`.
   - 확정 사용량은 **실행·턴이 끝날 때 한 번** 기록한다. Claude는 `result.usage`, Codex는 `turn.completed.usage`다. Claude의 메시지별 usage는 중간 값이라 합산하지 않는다.
3. **금액은 선택 필드이고 출처를 함께 적는다.** 예: `cost: { usd, basis: "list" }`. Claude 값은 정가 기준 추정이고, Codex는 비운다.
4. **정착 판정은 공급자별 규칙으로 하고, 프로세스 종료 코드와 함께 본다.**
   - Claude: `result.is_error`와 `terminal_reason`.
   - Codex: `turn.completed`와 `turn.failed` 중 무엇이 왔는가.
   - 마지막 줄이 오지 않고 프로세스가 끝나면 "비정상 종료"로 기록한다. M0b 테스트는 합성 픽스처 `synthetic-truncated-*`로 "종료 줄이 없다"는 상태만 확인한다.
   - **M3 계약 테스트에서 확인할 것:** 프로세스 종료 이벤트와 함께 판정하는 규칙. 종료 코드 0/1/그 밖, 신호로 끊김(사용자 취소, 엔진이 중단), stdout이 닫히기 전에 프로세스가 끝남, 종료 줄은 왔는데 종료 코드가 0이 아님(Claude 실패 예시는 exit 1) 같은 조합을 가짜 프로세스로 재현한다.
   - 도구 하나가 실패해도 실행은 성공으로 끝날 수 있다. 도구 실패는 도구 호출 이벤트의 결과로 기록하고, 실행의 정착과 섞지 않는다.
5. **도구 호출 이벤트는 시작과 끝 두 단계로 둔다.** id는 공급자 값을 보존한다(Claude `toolu_…`, Codex `item_N`).
   - Codex 훅의 `tool_use_id`(`exec-<uuid>`)는 같은 호출의 stream `item.id`와 다르다. 그래서 연결 키로 쓸 수 없다(허용된 같은 호출 한 쌍의 픽스처로 테스트). 둘이 같은 세션이라는 것만 `session_id` = `thread_id`로 알 수 있다.
   - Claude는 훅 `tool_use_id`와 stream `tool_use.id`가 같다(`toolu_…`).
   - 결과의 실패 여부는 선택 필드다. Claude `is_error`는 실패일 때만 오므로, 없으면 성공으로 읽는다.
6. **경고와 오류를 구분한다.** Codex의 `item.type = "error"`는 경고로 기록하고 실패로 보지 않는다.
7. **원본 보존**: `rate_limit_event`, `thinking_tokens`, 훅 이벤트처럼 계약에 없는 줄은 원본 그대로 보존하는 이벤트로 남긴다(§5 "모르는 이벤트는 원본 보존").

### 코드와 다시 돌리기

- 픽스처와 녹화 명령: `packages/agent-adapters/fixtures/`(README 포함)
- 치환 스크립트: `packages/agent-adapters/scripts/sanitize-fixture.ts`
- 사실 고정 테스트: `packages/agent-adapters/test/fixtures.test.ts`
