## #1 named pipe를 현재 사용자 전용으로 만들기

### 결론

**된다. 다만 Node `net`만으로는 안 되고, Win32 보안 API를 koffi로 직접 부른다.**

### Node 기본값은 정말로 열려 있다

`net.Server.listen('\\.\pipe\...')`로 만든 파이프의 보안 설명자:

```
O:<user>G:DUD:(A;;FA;;;SY)(A;;FA;;;BA)(A;;FA;;;<user>)(A;;FR;;;WD)(A;;FR;;;AN)
```

- `WD`(Everyone)와 `AN`(Anonymous)에 읽기(FR)가 들어 있다. Codex의 지적이 맞다.
- Node API에는 보안 설명자를 넘길 방법이 없다. `readableAll`/`writableAll`은 권한을 넓히기만 한다.

### 방법

1. 파이프 보안 설명자는 인스턴스마다 따로 있지 않고 파이프 이름 하나에 묶여 있다. 그래서 `WRITE_DAC` 권한이 있는 핸들 하나로 전체를 바꿀 수 있다.
2. Node는 서버 핸들을 감춘다. 대신 `listen` 직후 같은 프로세스가 **클라이언트로** `READ_CONTROL | WRITE_DAC` 핸들을 연다. 소유자는 기본 DACL에서 모든 권한을 가지므로 열린다.
3. 그 핸들로 `SetSecurityInfo`를 불러 DACL을 바꾸고, 같은 핸들로 다시 읽어서 확인한다.

결과:

```
O:<user>G:DUD:P(D;;FA;;;NU)(A;;FA;;;<user>)
```

- 허용 ACE는 현재 사용자 하나뿐이다. SYSTEM, Administrators, Everyone, Anonymous가 모두 빠졌다.
- `P`로 상속을 막았다.
- `NU`(네트워크 로그온) 거부 ACE는 SMB로 들어오는 원격 접속을 막기 위한 방어 겹이다(아래 한계 참고).

### 확인한 것

| 확인 | 결과 | 위치 |
|---|---|---|
| 현재 사용자 SID를 프로세스 토큰에서 읽기 | 성공 | 테스트 |
| 기본 DACL에 WD, AN이 있음 | 확인 | 테스트, 스파이크 |
| DACL 교체 후 허용 대상이 현재 사용자 하나뿐 | 확인 | 테스트 |
| 동시 연결 12개로 libuv가 인스턴스를 더 만든 뒤에도 DACL 유지 | 유지됨 | 테스트 |
| **OS가 실제로 막는지**: DACL을 SYSTEM 전용으로 바꾸고 현재 사용자로 연결 | `net.connect` → `EPERM`, `CreateFileW` → `ERROR_ACCESS_DENIED(5)` | 테스트, 스파이크 |
| `listen`과 DACL 교체 사이에 연결한 클라이언트 | 서버가 끊음, 이후 쓰기 실패 | 테스트 |
| 같은 이름으로 두 번째 `listen` | `EADDRINUSE` | 테스트 |
| 클라이언트가 서버 프로세스의 사용자 SID 확인 | 현재 사용자와 일치 | 테스트 |
| `listen` + DACL 교체 + 게이트에 드는 시간 | 중앙값 0.24 ms, 최대 1.96 ms (20회) | 스파이크 |

**"DACL에 없는 주체는 OS가 막는다"를 자기 자신을 빼는 방식으로 확인했다.** 다른 계정이 막히는 근거는 이것이다.

### 교체 전 짧은 구간 막기 (게이트)

`listen`과 DACL 교체 사이(1 ms 미만)에는 기본 DACL이 걸려 있다. 그 사이에 다른 사용자가 연결할 수 있다. 기본 DACL에서 Everyone은 읽기만 되므로 요청을 보낼 수는 없지만, 그것도 남기지 않으려고 게이트를 둔다.

1. `listen`
2. DACL 교체(클라이언트 핸들 A로 연결)
3. 새 DACL 아래에서 다시 연결해 임의의 nonce 32바이트를 보낸다(핸들 B)
4. 서버는 B보다 먼저 받아들인 연결을 모두 끊는다. B 다음부터 받은 연결만 처리기로 넘긴다.

libuv는 파이프 연결을 I/O 완료 포트 하나에서 들어온 순서대로 꺼내므로, 받아들인 순서가 연결한 순서와 같다.

### 이름 선점과 중복 실행

- libuv는 첫 인스턴스를 `FILE_FLAG_FIRST_PIPE_INSTANCE`로 만든다. 그래서 같은 이름의 파이프가 이미 있으면 `listen`이 `EADDRINUSE`로 실패한다.
- 이것을 사용자별 단일 인스턴스 잠금으로 함께 쓸 수 있다. 다른 사용자가 이름을 먼저 차지한 경우에도 엔진은 떠 있는 척하는 가짜 서버에 붙지 않고 실패한다.
- 반대로 **클라이언트**(CLI, Electron main)가 가짜 서버에 붙지 않도록 `getPipeServerUserSid()`로 서버 프로세스의 사용자를 확인할 수 있다. 연결할 때 이 검사를 넣는 것은 M3에서 한다.

### 한계 (이 PC에서 못 한 것)

- **다른 Windows 계정으로 실제 접속하는 시험은 못 했다.** 계정이 하나뿐이고, 관리자 권한이 없어 계정을 만들 수 없다. 관리자 권한이 있는 PC에서 아래를 한 번 수동으로 확인한다(M7 전).
  1. A 계정에서 `listenSecurePipe`로 서버를 띄운다(스파이크 스크립트를 조금 고치면 된다).
  2. B 계정(`runas /user:B`)에서 같은 파이프 이름으로 `net.connect` → `EPERM`이 나와야 한다.
- **원격 거부(`NU` ACE)의 효과는 확인하지 못했다.** `\\localhost\pipe\...`, `\\127.0.0.1\pipe\...`, `\\<호스트 이름>\pipe\...` 모두 연결됐고, `NU` 거부 ACE를 빼도 같았다. 같은 PC의 SMB 루프백은 네트워크 로그온으로 처리되지 않고 호출자의 로컬 토큰을 그대로 쓰는 것으로 보인다. 다른 PC에서만 확인할 수 있다.
- OpenSSH 세션은 네트워크 로그온이라 `NU` 거부에 걸릴 수 있다. 그래서 `rejectRemote: false` 옵션을 두었다([[결정 대기]]).
- 같은 PC의 관리자는 막지 못한다. DACL에서 뺐지만 소유권 가져오기나 디버그 권한으로 우회할 수 있다. 위협 모델 밖으로 둔다.
- 같은 사용자로 도는 다른 프로세스는 막지 않는다. 노드 에이전트를 구분하는 일은 실행 토큰([[기술 스택 결정]] §3)이 맡는다.
- Windows 전용이다. 다른 OS에서는 `listenSecurePipe`가 예외를 던진다.

### 결정

- 엔진의 파이프 서버는 `listenSecurePipe()`로만 연다. 기본 DACL은 "현재 사용자만 + 네트워크 로그온 거부"다.
- **koffi를 엔진 의존성에 넣는다(Win32 호출 전용).** [[기술 스택 결정]] §2의 "작은 네이티브 보조 모듈"을 당분간 koffi로 대신한다.
  - 사전 빌드 바이너리가 들어 있어 컴파일러가 필요 없다. 엔진은 고정 Node에서 돌므로 Node-API만 맞으면 된다.
  - `.node` 파일이 하나 생기므로 배포할 때 서명 대상에 넣는다.
  - Job Object 같은 다른 OS 기능도 같은 방식으로 부를 수 있다.
- 바인딩은 `ffi.ts` 한 곳에 모으고 지연 로드한다. 엔진을 import하는 것만으로 네이티브 모듈이 올라오지 않는다.

## #5 worker 안의 `node:sqlite` WAL과 동시 읽기

### 결론

**문제 없다.** worker 안에서 WAL이 켜진다. 다른 worker의 읽기 연결은 쓰기 트랜잭션이 열려 있어도 기다리지 않고 마지막 커밋 시점의 스냅샷을 읽는다. 실험 플래그나 경고는 나오지 않는다.

### 구조

- `SqliteWorker`: `node:sqlite` 연결 하나를 worker 스레드 하나에 둔다. 요청은 순서대로 처리한다(`exec`, `run`, `all`, `get`, `transaction`).
- `transaction`은 `BEGIN IMMEDIATE … COMMIT`으로 묶고, 하나라도 실패하면 롤백한다.
- 쓰기 연결: `journal_mode=WAL`, `synchronous=FULL`(기본), `busy_timeout=5000`, `foreign_keys=ON`.
- 읽기 연결: `readOnly`로 연다.

### 확인한 것 (테스트)

| 확인 | 결과 |
|---|---|
| 쓰기 worker가 WAL로 열림, `-wal` 파일 생김 | 확인 |
| 트랜잭션 원자성: 중복 키로 실패하면 같은 트랜잭션의 앞 문장도 롤백 | 확인 (`SQLITE_CONSTRAINT_UNIQUE`) |
| 쓰기 트랜잭션이 열린 동안 읽기 worker가 이전 스냅샷을 바로 읽음 | 확인, 커밋 뒤에는 새 값 |
| 연속 쓰기(100건 × 50 트랜잭션) 중 읽기 worker 2개가 계속 읽음 | 오류 없음. 개수가 줄지 않고 항상 100의 배수(커밋 중간이 안 보임), revision에 빈틈 없음 |
| 읽기 전용 연결에 쓰기 | `SQLITE_READONLY` |
| worker가 1초 넘는 쿼리를 도는 동안 메인 스레드 | 최대 공백 2.43 ms (스파이크) |

### 수치 (스파이크)

이벤트 한 건 ≈ 300바이트 JSON, 집계 200개, 고유 인덱스 `(aggregate_id, revision)`.

**쓰기 처리량 (건/초, 배치 하나 = 트랜잭션 하나)**

| synchronous | 배치 1 | 배치 10 | 배치 100 |
|---|---|---|---|
| FULL | 464 | 4,175 | 18,965 |
| NORMAL | 6,944 | 26,605 | 31,151 |

**읽기 지연 (ms, 이벤트 5만 건, 메인 스레드에서 왕복)**

| 상황 | 쿼리 | p50 | p95 | p99 | 최대 |
|---|---|---|---|---|---|
| 쓰기 없음 | count | 0.04 | 0.08 | 0.28 | 3.15 |
| 쓰기 없음 | 집계 최근 20건 | 0.08 | 0.17 | 0.34 | 0.72 |
| 쓰기 없음 | 최근 100건(seq) | 0.16 | 0.21 | 0.58 | 1.04 |
| 쓰기 중, **읽기 전용 worker** | count | 0.07 | 3.07 | 3.58 | 3.97 |
| 쓰기 중, **읽기 전용 worker** | 집계 최근 20건 | 0.14 | 0.42 | 0.50 | 0.98 |
| 쓰기 중, **읽기 전용 worker** | 최근 100건(seq) | 0.19 | 0.36 | 0.47 | 1.06 |
| 쓰기 중, 쓰기 worker에서 읽기 | count | 2.31 | 5.52 | 14.44 | 18.53 |
| 쓰기 중, 쓰기 worker에서 읽기 | 집계 최근 20건 | 2.47 | 3.52 | 16.12 | 39.46 |
| 쓰기 중, 쓰기 worker에서 읽기 | 최근 100건(seq) | 2.51 | 4.21 | 16.62 | 38.25 |

"쓰기 중"은 트랜잭션 하나에 이벤트 10건씩 쉬지 않고 쓰는 상황이다.

**긴 읽기 트랜잭션과 WAL 크기**

- 읽기 쪽이 스냅샷을 잡고 있는 동안 2만 건을 쓰면 WAL이 16.7 MB까지 커진다. 체크포인트가 그 스냅샷 너머로 진행하지 못하기 때문이다.
- 읽기 트랜잭션을 끝내고 `wal_checkpoint(TRUNCATE)`를 부르면 0 MB가 된다.

### 해석과 결정

- **쓰기 worker 1개 + 읽기 전용 worker 1개로 시작한다.** 같은 worker에서 읽으면 쓰기 뒤에 줄을 서서 p99가 14~17 ms, 최대 39 ms로 늘어난다. 읽기 전용 worker는 p99가 0.5~3.6 ms다. 화면 조회와 이벤트 구독 읽기는 읽기 worker로 보낸다. 부족하면 읽기 worker를 늘린다.
- **`synchronous`는 FULL을 기본으로 하고 옵션으로 둔다.**
  - 이벤트가 정본이다. NORMAL은 프로세스 크래시에는 안전하지만, 전원이 나가면 마지막 커밋이 사라질 수 있다.
  - FULL의 단건 커밋은 초당 약 460건(커밋당 약 2 ms)이다. 에이전트 출력처럼 이벤트가 몰리면 M1 이벤트 저장소에서 쓰기 worker가 대기 중인 명령을 한 트랜잭션으로 묶어 커밋한다(group commit). 배치 10만 돼도 초당 4,000건이다.
- **읽기 트랜잭션은 짧게 유지한다.** 엔진이 한가할 때 `wal_checkpoint(TRUNCATE)`를 돌린다.
- Windows에서는 `monitorEventLoopDelay`로 이벤트 루프 지연을 잴 수 없다. 타이머 해상도(약 15.6 ms)만 보인다. 지연 지표가 필요하면 `setImmediate` 간격으로 잰다.

### 한계

- 이 PC의 SSD 기준이다. 디스크와 백신 실시간 검사에 따라 fsync 비용이 달라진다.
- `node:sqlite`의 안정성 등급은 여전히 1.2(release candidate)다. Node 버전을 올릴 때 이 테스트와 스파이크를 다시 돌린다.
- 읽기 worker 여러 개의 처리량은 재지 않았다. 2개가 함께 정상 동작하는 것만 확인했다.

- `packages/engine/src/db/sqlite-worker-client.ts`: 호출 쪽 `SqliteWorker`

| 줄 종류 | `system`(subtype `init`, `hook_started`, `hook_response`, `thinking_tokens`), `assistant`, `user`, `rate_limit_event`, `result` | `thread.started`, `turn.started`, `item.started`, `item.completed`, `turn.completed`, `turn.failed`, `error` |

| 이어하기 | `--resume <id>` 결과가 **같은 `session_id`** 다(`--fork-session`을 줘야 새 id) | `exec resume <id>` 결과도 **같은 `thread_id`** 이고 `thread.started`가 다시 온다 |
| 메시지 | `assistant.message.content[]`의 `text`, `thinking`(서명만, 본문 빈 문자열), `tool_use` 블록. **같은 `message.id`가 블록마다 여러 줄로 나뉘어 온다** | `item.completed`의 `item.type = "agent_message"`, `text` |

| 토큰 | **정확한 값은 마지막 `result.usage`뿐이다**: `input_tokens`(캐시 제외), `cache_creation_input_tokens`, `cache_read_input_tokens`, `output_tokens`. `assistant` 줄의 `message.usage`는 스트리밍 중간 값이라 출력 토큰이 작게 찍히고(16 vs 최종 217) 같은 메시지 줄마다 반복된다 | 턴마다 `turn.completed.usage`: `input_tokens`(**캐시 포함**), `cached_input_tokens`, `cache_write_input_tokens`, `output_tokens`, `reasoning_output_tokens`. 이어하기 턴의 `input_tokens`에는 이전 대화가 다시 들어간다 |
| 비용 | `result.total_cost_usd`, 모델별 `result.modelUsage[모델].costUSD`. **`costBasis: "list"`, 즉 정가로 계산한 값**이다. 구독 요금제에서 실제로 청구된 금액이 아니다 | 없음 |
| 정착(끝) | 마지막 줄 `type: "result"`. 성공은 `is_error: false` + `terminal_reason: "completed"`. **실패해도 `subtype`은 `"success"`다**(없는 모델: `is_error: true`, `terminal_reason: "api_error"`, `api_error_status: 404`). 프로세스 exit 1 | `turn.completed`(성공) 또는 `turn.failed {error.message}`(실패, 앞에 최상위 `error` 줄). 프로세스 exit 1 |
| 주의 | stdin을 닫지 않으면 "no stdin data received in 3s" 경고 후 진행한다. `rate_limit_event`에 계정 사용률이 온다 | stdin이 닫혀 있어도 stderr에 "Reading additional input from stdin..."이 찍힌다. **`item.type = "error"`는 실패가 아니다**(경고: 훅 신뢰 우회, 모델 메타데이터 없음) |

### 훅 (#2, #4)

| 시험 | Claude `--settings` PreToolUse | Codex `hooks.PreToolUse` |
|---|---|---|
| 주입 방법 | `--settings '<JSON>'`. `--setting-sources ""`여도 적용된다 | `-c 'hooks.PreToolUse=[...]'`(세션 플래그) |
| 신뢰 확인 | 필요 없음 | **`--dangerously-bypass-hook-trust`가 없으면 훅이 실행되지 않는다.** 경고도 없이 파일이 생성됐다 |
| Windows 명령 | `command`를 셸로 실행 | **`commandWindows`가 쓰인다.** `command`에 없는 경로를 넣어도 막혔다 |
| JSON 거부 (`hookSpecificOutput.permissionDecision: "deny"` + 사유) | Write, Edit 모두 막힘 | apply_patch 막힘 |
| exit 2 + stderr 사유 | 막힘 | **막지 못함**. 파일이 생성됐다 |
| 거부가 출력에 보이는가 | 보인다: `tool_result.is_error = true`("PreToolUse:Write hook error: <사유>"), `result.permission_denials[]`, `--include-hook-events`면 `system/hook_response` | **stdout에는 아무 흔적이 없다.** `item.started`도 나오지 않는다. stderr 로그에만 "Command blocked by PreToolUse hook"이 남는다 |
| 훅이 받는 stdin | `session_id`, `transcript_path`, `cwd`, `permission_mode`, `hook_event_name`, `tool_name`, `tool_input {file_path, content \| old_string…}`, `tool_use_id` | `session_id`(= thread_id), `turn_id`, `transcript_path`, `cwd`, `model`, `permission_mode`, `hook_event_name`, `tool_name`, `tool_input.command`(패치 원문), `tool_use_id` |
| 셸로 쓰기 | Bash/PowerShell 도구는 `Write\|Edit` 매처에 걸리지 않는다(이번 녹화에서는 도구 목록에서 뺐다) | PowerShell `Set-Content`는 `tool_name: "Bash"`, `tool_input.command`에 PowerShell 명령 원문으로 온다. `apply_patch` 매처에 걸리지 않는다 |

**정리**

- 두 CLI 모두 파일 수정 직전에 막을 수 있다. 다만 **공통으로 동작하는 방식은 JSON 거부 하나뿐이다.** Vuyro 훅은 exit 2를 쓰지 않고 항상 JSON `deny`를 낸다. 같은 훅 스크립트를 두 CLI에 함께 쓸 수 있다.
- Codex는 신뢰 우회 플래그가 있어야 주입한 훅이 돈다. 이 플래그를 주면 그 실행에서 **다른 훅(사용자·프로젝트 훅)도 신뢰 확인 없이 돈다.** 그래서 대안을 M4에서 정한다.
  - (1) 플래그를 주고, 대상 저장소의 프로젝트 훅이 실제로 함께 실행되는지 확인한다.
  - (2) 사용자 Codex 설정의 신뢰 기록(`[hooks.state] trusted_hash`)에 Vuyro 훅을 등록한다. 사용자 설정 파일을 고치는 일이라 동의를 받아야 한다.
  - 별도 `CODEX_HOME`은 쓰지 않는다. 로그인 정보를 복사해야 하고, 토큰이 갱신되면 원래 로그인이 깨질 수 있다.
- **Codex는 거부된 호출을 stdout에 남기지 않는다.** 거부 기록의 정본은 Vuyro 훅 자신이다. 훅이 거부할 때 `vuyro` 명령으로 이벤트를 남긴다.
- **셸로 쓰는 수정은 파일 도구 매처로 막을 수 없다**(Claude Bash/PowerShell, Codex Bash). 명령 문자열을 해석해서 막는 것은 믿을 수 없으므로, 사후 검출([[기술 스택 결정]] §10 감시 + SHA-256)이 최종 안전망이다. 노드 설정에서 셸 도구를 빼는 것은 선택지로 둔다.

### M1 이벤트 계약에 반영할 것

1. **세션 id는 이어하기 후에도 같다.** 실행(run) 하나는 "세션 id + 턴 번호"로 식별한다. 세션 id만으로는 실행을 구분할 수 없다.
2. **토큰 정규화**: `{ input(캐시 제외), cacheRead, cacheWrite, output, reasoning? }`.
   - Claude: `input_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`, `output_tokens`를 그대로 쓴다.
   - Codex: `input = input_tokens − cached_input_tokens`, `cacheRead = cached_input_tokens`, `cacheWrite = cache_write_input_tokens`, `reasoning = reasoning_output_tokens`.
   - 확정 사용량은 **실행·턴이 끝날 때 한 번** 기록한다. Claude는 `result.usage`, Codex는 `turn.completed.usage`다. Claude의 메시지별 usage는 중간 값이라 합산하지 않는다.
3. **금액은 선택 필드이고 출처를 함께 적는다.** 예: `cost: { usd, basis: "list" }`. Claude 값은 정가 기준 추정이고, Codex는 비운다.
4. **정착 판정은 공급자별 규칙으로 하고, 프로세스 종료 코드와 함께 본다.**
   - Claude: `result.is_error`와 `terminal_reason`.
   - Codex: `turn.completed`와 `turn.failed` 중 무엇이 왔는가.
   - 마지막 줄이 오지 않고 프로세스가 끝나면 "비정상 종료"로 기록한다.
5. **도구 호출 이벤트는 시작과 끝 두 단계로 둔다.** id는 공급자 값을 보존한다(Claude `toolu_…`, Codex `item_N`). Codex 훅의 `tool_use_id`(`exec-<uuid>`)는 stream의 `item.id`와 다르므로 연결 키로 쓸 수 없다.
6. **경고와 오류를 구분한다.** Codex의 `item.type = "error"`는 경고로 기록하고 실패로 보지 않는다.
7. **원본 보존**: `rate_limit_event`, `thinking_tokens`, 훅 이벤트처럼 계약에 없는 줄은 원본 그대로 보존하는 이벤트로 남긴다(§5 "모르는 이벤트는 원본 보존").
