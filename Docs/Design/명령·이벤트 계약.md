# 명령·이벤트 계약

> M2~M6이 그대로 올라설 바닥이다. 바꿀 때는 아래 "버전 규칙"을 따른다.
> 코드: `packages/contracts/src/`(타입과 JSON Schema), `packages/engine/src/{store,commands,runtime}/`(구현).

## 1. 이벤트 envelope

| 필드 | 형식 | 규칙 |
|---|---|---|
| `eventId` | UUIDv7 | 전역 유일. 나중에 replica 사이 동기화의 키 |
| `sequence` | 정수 ≥ 1 | **이 DB의 로그 위치**. 빈틈 없음. replica끼리 비교하지 않는다 |
| `type` | `<명사>.<과거형>` | 예: `ticket.created`. 카탈로그에 없는 타입은 쓸 수 없다 |
| `schemaVersion` | 정수 ≥ 1 | `type`별 `data` 버전 |
| `aggregateType`, `aggregateId` | 문자열 | id는 UUIDv7 또는 고정 이름(`permissions:app`) |
| `revision` | 정수 ≥ 1 | 집계별 1, 2, 3…, 빈틈 없음. 낙관적 동시성 키 |
| `timestamp` | epoch ms(UTC) | 엔진 시계(주입) 기준 저장 시각. 통계 계산에 그대로 쓴다 |
| `replicaId` | UUIDv7 | 이 DB를 만든 엔진 설치. DB 생성 때 한 번 정한다 |
| `actor` | Principal | 누가 했는가(§3) |
| `authorization` | `{decision:'allow', rule}` | 명령에서 나온 이벤트만. 어느 규칙으로 허용됐는가 |
| `requestId`, `correlationId` | 문자열 | 원인 명령, 묶음 추적 |
| `data` | 타입별 스키마 | 저장 전에 검증한다 |

**저장 규칙**

- 이벤트 테이블은 트리거로 지킨다: 갱신·삭제 금지, `sequence`와 `revision`은 직전 값 + 1만 허용.
- 한 번의 append = 한 트랜잭션: 이벤트, 조회 테이블 갱신, 조회 체크포인트(`projection_sequence`), 멱등 기록이 함께 커밋된다.
- 동시에 들어온 append는 한 트랜잭션으로 묶는다(group commit). 묶음이 실패하면 하나씩 다시 시도해서 문제 있는 것만 실패시킨다.
- 조회 테이블은 이벤트의 순수 함수다. 버전·상태·체크포인트가 맞지 않으면 엔진이 열릴 때 지우고 재생한다. 재구축 중 죽으면 다음에 다시 한다.

## 2. 명령 envelope

| 필드 | 필수 | 규칙 |
|---|---|---|
| `requestId` | 예 | 클라이언트가 정한다(`[A-Za-z0-9._:-]{8,128}`). 멱등 키 |
| `type` | 예 | `<명사>.<동사>`. 예: `ticket.create` |
| `schemaVersion` | | 생략 = 1. 엔진이 모르는 버전은 거부 |
| `expectedRevision` | | 대상 집계의 revision. 0 = 아직 없어야 함. 생략 = 검사 안 함 |
| `context` | | `{ticketId?, nodeId?}`. 호출자가 "이 작업 중"이라고 밝히는 것. 실행 토큰과 다르면 거부 |
| `auth.runToken` | | 노드 실행 토큰(`VUYRO_RUN_TOKEN`). **주체를 좁히기만 한다** |
| `correlationId` | | 추적용 |
| `payload` | 예 | 명령별 스키마. 추가 필드 거부 |

- **주체(principal)는 요청에 쓸 수 없다.** 엔진이 연결과 토큰으로 정한다. envelope에 `principal` 같은 필드를 넣으면 검증에서 거부된다.
- 응답: 성공 `{ok, requestId, type, result, revision?, events: {firstSequence, lastSequence, count} | null, replayed}`, 실패 `{ok: false, requestId?, error}`.

**검사 순서:** envelope → 명령 타입 → 스키마 버전 → 호출자(토큰, 사람 증명) → 멱등 → payload → 권한 → 대상 집계 읽기 → `expectedRevision` → 결정 → append.
- 권한은 payload만으로 판정한다. 대상 집계를 읽기 전에 거부하므로, 범위 밖 명령은 아무것도 읽지 않는다.
- 범위가 대상 상태에 달린 명령(`run.observe`, `run.settle`: 실행의 티켓·노드. `node.done`, `artifact.add`: 레인을 지정했을 때 그 레인을 돌리는 실행)은 **두 번 판정한다(M2 변경).** 먼저 payload만으로 판정하고, 통과한 호출자에 대해서만 대상을 읽어 전체 범위로 다시 판정한다(`scopeNeedsTarget`, payload별 함수 가능).
  - 이유: M1은 이런 명령에서 대상을 먼저 읽었다. 그러면 다른 티켓의 에이전트가 레인을 지정해 보낸 명령도 그 티켓을 읽은 뒤에 거부된다. 두 단계로 바꾸면 범위 밖 호출자는 여전히 아무것도 읽지 않는다.
- 권한을 `expectedRevision`과 존재 여부보다 먼저 본다. 권한 없는 호출자에게 revision이나 존재 여부를 알려주지 않기 위해서다.

**멱등**

| 상황 | 결과 |
|---|---|
| 같은 `requestId` + 같은 호출자 + 같은 내용(`type`, 버전, `expectedRevision`, `context`, `payload`의 정규 JSON 해시) | 처음 응답을 그대로, `replayed: true`. 새 이벤트 없음. 엔진 재시작 뒤에도 같다 |
| 같은 `requestId`, 다른 내용이나 다른 호출자 | `idempotency_conflict` |
| 실패한 명령 | 기록하지 않는다. 고쳐서 같은 id로 다시 보낼 수 있다 |
| 비밀이 든 결과(`run.start`의 `runToken`) | 저장하는 응답에서 뺀다. 재전송하면 `runId`만 돌아간다(복구는 §4 "실행 복구") |
| 실행이 끝나 토큰이 폐기된 뒤 재전송 | **같은 실행이 보냈던 요청을 그대로 다시 보낸 것만** 처음 응답을 돌려준다(`replayed: true`). 판정은 토큰 해시로 찾은 실행의 주체 키 + 내용 해시다 |
| 토큰 폐기 뒤 다른 요청(새 id, 같은 id에 다른 내용, 다른 실행의 토큰) | `unauthenticated`. `idempotency_conflict`를 주지 않는다. 저장된 결과가 있는지조차 알려주지 않기 위해서다 |

## 3. 호출자 맥락과 주체

**연결이 보증하는 것(TransportIdentity) → 주체**

| 연결 | 실행 토큰 없음 | 실행 토큰 있음 |
|---|---|---|
| `internal`(엔진 내부 호출) | `system{component}` | 거부(`unauthenticated`) |
| `ui-session`(UI 자격까지 증명, M3) | `human{userId:'local', via:'ui'}` | `agent{node.agent}`로 **좁힌다** |
| `engine-token` + `humanProof`(사람 자격) | `human{via:'cli'}`. 증명이 틀리거나 검증기가 없으면 `unauthenticated` | `agent{node.agent}` |
| `engine-token`, client `cli`/`unknown` | `unverified{client}`(**읽기 전용**) | `agent{node.agent}` |
| `engine-token`, client `mcp` | `agent{mcp.external}`(읽기 전용) | `agent{node.agent}` |

- 토큰이 형식에 안 맞거나, 모르는 토큰이거나, 실행이 끝났으면 `unauthenticated`다. 더 넓은 주체로 물러나지 않는다.
- **엔진 토큰만 증명한 연결은 사람으로 보지 않는다.** 토큰 파일은 같은 사용자의 모든 프로세스(에이전트 포함)가 읽을 수 있다. 그래서 터미널의 사람과 토큰을 버린 에이전트를 구분할 수 없고, 둘 다 `unverified`(AI 취급)다([[결정 대기]] D-003).
- **`unverified`는 읽기 전용이다.** 실행 토큰을 넣으면 남의 노드가 `out_of_scope`인데, 토큰만 빼면 허용되는 구멍을 막기 위해서다. 협조적인 에이전트가 환경 변수를 잘못 넘기는 실수도 여기서 걸린다.
- **사람 자격 주입점:** `CommandBus`의 `humanCredential` 옵션과 연결의 `humanProof`. M3 데몬은 `HumanCredentials.cliVerifier()`를 연결한다(아래 "사람 자격"). 비밀은 파일에 쓰지 않고, 엔진은 해시만 들고 상수 시간으로 비교한다.
- **연결의 주체는 `session.hello`에서 한 번 정해진다(M3).** UI 자격 → `ui-session`, CLI 사람 자격 → `engine-token` + `humanProof`, 그 밖 → `unverified`(client `ui`라고만 말해도 같다) 또는 `mcp`. 두 번째 hello는 거부한다. hello 전 요청은 `unauthenticated`.
- **AI 주체** = `agent` + `unverified`. `isAiPrincipal()`.

**주체(Principal)**

| kind | 필드 | 용도 |
|---|---|---|
| `human` | `userId`, `via:'ui'` | 사람. MVP는 한 명(`local`) |
| `agent` | `role`(`node.agent` / `panel.app` / `panel.ticket` / `mcp.external`), `provider?`, `runId?`, `ticketId?`, `nodeId?` | AI. 노드 에이전트는 토큰의 실행·티켓·노드가 들어간다 |
| `system` | `component` | 엔진 자신(스케줄러, 어댑터, 복구) |
| `unverified` | `client` | 엔진 토큰만 증명한 로컬 클라이언트 |

**AI 승인 구분:** 모든 이벤트에 `actor`와 `authorization.rule`이 있다. M2의 `node.approve` 이벤트도 같으므로, `actor.kind === 'agent'`면 "AI 승인" 배지와 통계 분리를 이벤트만으로 할 수 있다([[공유·권한·BlackBoard 설계]] §2.8).

**사람 자격 (M3 결정: 후보 (b), 실행 중인 엔진이 사람 확인을 거쳐 발급)**

M1이 남긴 후보는 (a) UI가 항상 엔진을 띄우고 CLI가 띄운 엔진은 UI가 붙을 때 재시작, (b) 엔진이 사람 확인을 받아 실행 중에 자격을 발급, 둘이었다. 조건은 "실행 중 엔진을 재시작하지 않는다", "에이전트(같은 사용자 프로세스)가 쉽게 사람 자격을 얻지 못한다"였다. **(b)를 골랐다.** (a)는 재시작이 상주 작업을 끊고, 앱이 죽었다 다시 뜨는 흔한 경우에도 같은 문제가 생긴다.

| 자격 | 어떻게 받나 | 수명 | 쓰는 곳 |
|---|---|---|---|
| UI 자격 `vuc_…` | (1) 앱이 엔진을 띄울 때 stdin 첫 줄로 넘긴다(`--ui-credential-stdin`). 파일·인자·환경 변수에는 두지 않는다. (2) 이미 떠 있는 엔진이면 `auth.pair {kind: 'ui'}`로 사람 확인을 받아 발급 | 엔진이 멈출 때까지 | `session.hello.uiCredential` → 연결이 `ui-session` |
| CLI 사람 자격 `vhc_…` | `vuyro auth login` = `auth.pair {kind: 'cli'}` + 사람 확인 | 8시간(D-023) | 사람이 자기 터미널에 `VUYRO_HUMAN_CREDENTIAL`로 둔다 → hello의 `humanCredential` → `humanProof`. 버스가 **명령마다** 다시 확인한다(만료) |

- **사람 확인:** 엔진 프로세스가 직접 Windows 대화 상자를 띄운다(`MessageBoxTimeoutW`, 시스템 모달, 기본 버튼 "아니요", 2분 뒤 닫힘). 대화 상자와 요청한 쪽(앱 화면, CLI 출력)에 같은 4자리 코드가 보인다. "예"를 명시적으로 누른 경우만 발급한다. 거부·시간 초과·대화 상자 오류는 모두 거부다(fail closed). 한 번에 하나의 요청만 받는다(다른 요청은 `invariant_violated`).
  - 파이프로만 말하는 프로세스(실행 토큰을 버린 에이전트)는 자기 요청을 스스로 승인할 수 없다. 요청하면 사람 눈앞에 대화 상자가 뜬다. 사람이 요청하지 않았다면 "아니요"를 누른다.
- **두 종류는 서로 대신하지 않는다.** UI 자격을 `humanCredential`로, CLI 자격을 `uiCredential`로 내면 `unauthenticated`. 틀린 자격은 오류다. 읽기 전용으로 조용히 물러나지 않는다.
- 엔진은 SHA-256만 메모리에 둔다. 엔진이 재시작하면 모든 자격이 사라진다(앱은 다시 짝을 맺는다).
- **에이전트에게 가지 않게:** 엔진은 에이전트 환경에서 상속된 `VUYRO_*`를 모두 지운다(대소문자 무관). 사람이 엔진을 띄운 터미널에 `VUYRO_HUMAN_CREDENTIAL`이 있어도 에이전트는 받지 못한다. 엔진을 띄울 때도 띄우는 쪽의 `VUYRO_*`를 넘기지 않는다.
- 엔진 중지(`engine.shutdown`)는 사람(`ui-session` 또는 유효한 CLI 자격)만 할 수 있다.

**남는 위험**

- 같은 사용자로 도는 **악의적** 프로세스는 막지 못한다: UI 자동화로 대화 상자를 누르기, 앱 메모리 읽기, DB 파일 직접 고치기. 이 경계의 목표는 협조적인 에이전트가 실수로, 또는 쉽게 사람이 되는 것을 막는 것이다(§4).
- 엔진이 **떠 있지 않을 때** 사람 터미널에서 도는 외부 AI(사용자가 직접 띄운 Claude Code 등)가 `--ui-credential-stdin`으로 엔진을 띄우면 그 자격을 가진다. 엔진이 떠 있으면 단일 인스턴스라 불가능하다. 노드 에이전트는 엔진이 떠 있을 때만 존재하므로 해당하지 않는다.
- CLI 자격을 터미널에 둔 사람이 같은 터미널에서 외부 AI 도구를 쓰면 그 도구도 사람 자격을 쓴다. 사람이 자격을 넘긴 것으로 본다. `vuyro auth login`이 이 점을 출력한다.
- 대화 상자 요청이 몰리면 사람을 귀찮게 할 수 있다(동시 1건 제한만 있다). 반복 거부 시 대기 시간은 M6에서 본다.
- 확인은 언제나 엔진의 대화 상자다. M6a는 앱 화면으로 보내지 않았다: 앱 화면은 렌더러(에이전트 출력을 보여 주는 곳)라서 엔진이 직접 띄우는 대화 상자보다 경계가 약하다. 앱은 같은 코드를 배너에 보여 주기만 한다(§16).

## 4. 최소 권한 경계 (M1)

| 순서 | 규칙 | 결과 | 고칠 수 있나 |
|---|---|---|---|
| 1 | `permission.*` 명령은 `human`만 | AI 주체, 엔진 자신 모두 `forbidden` | **고정**(설정으로 못 연다) |
| 2 | `systemOnly` 명령(`run.start/observe/settle`)은 `system`만 | 그 밖 `forbidden` | 고정 |
| 3 | 토큰의 `context` 불일치 | `out_of_scope` | 고정 |
| 4 | 노드 에이전트: 카탈로그 `nodeAgent: 'own-node'` 명령만, payload의 티켓·노드가 토큰과 같을 때만 | 다른 명령 `forbidden`, 다른 노드·티켓 `out_of_scope` | 정책 도입 후 좁힐 수만 있다 |
| 5 | `unverified`(엔진 토큰만) | 쓰기 명령 `forbidden`(읽기 전용) | 고정(사람은 사람 자격, 에이전트는 실행 토큰을 쓴다) |
| 6 | `mcp.external` | 쓰기 명령 `forbidden`(읽기 전용) | 정책 도입 후 |
| 7 | 나머지(`human`, `panel.*`, `system`) | 허용 | 정책 도입 후(MVP 이후) |

- 거부(`forbidden`, `out_of_scope`)는 `command.denied` 이벤트로 남긴다(집계 `audit`, 한 건이 한 집계). 조회 테이블 `p_command_denials`.
- **감사 기록이 실패해도 거부는 그대로다(fail closed).** 대신 숨기지 않는다: 응답 `error.details`에 `{audit: 'failed', auditError}`를 넣고, 버스의 `reportError`(기본: stderr)로 알린다.
- 이 경계는 **협조적인 에이전트가 실수로 남의 노드를 건드리는 것**을 막는다. 같은 사용자로 도는 악의적 프로세스는 DB 파일을 직접 고칠 수도 있으므로 막지 못한다. 그 수준의 격리는 MVP 범위가 아니다.
- 변이 시험: 위 가드를 하나씩 "통과"로 바꿔 테스트가 실패하는 것을 확인했다(§8).

**실행 복구 (토큰 비저장의 짝)**

- `run.start`는 엔진 전용이고 프로세스 안에서 부른다. 응답을 잃는 경우는 "커밋 뒤, 에이전트를 띄우기 전에 엔진이 죽은 경우"뿐이다. 이때 토큰은 어디에도 없으므로 그 실행은 스스로 끝날 수 없다.
- 에이전트 프로세스도 엔진과 함께 죽는다. 그래서 **엔진이 시작할 때(M3 기동 경로) `settleOrphanedRuns`를 부른다.**
  1. `running`인 실행을 모두 `run.settle`(`abnormal_exit`, `terminalReason: 'engine_restarted'`)로 정착시킨다. 토큰이 폐기된다.
  2. 요청 id는 `recover-settle-<runId>`라서, 복구 도중 다시 죽어도 다시 돌리면 남은 것만 처리한다.
  3. 워크플로(M2/M3)가 그 노드에 새 `run.start`를 낸다. 공급자 세션이 기록돼 있으면 `resumedFromRunId`로 이어서 시작한다.
- 같은 요청 id로 `run.start`를 재시도해서 토큰을 되찾는 방법은 두지 않는다. 토큰을 저장하지 않는다는 원칙이 우선이다.

## 6. 버전 규칙

| 대상 | 규칙 |
|---|---|
| 이벤트 `data` | 선택 필드 추가만 하면 버전 유지. 그 밖의 변경은 버전 +1과 업캐스터(n → n+1)를 `EVENT_UPCASTERS`에 추가. **저장된 이벤트는 고치지 않고 읽을 때 올린다.** 엔진보다 새 버전, 업캐스터 누락, 모르는 타입은 읽기 실패(fail closed) |
| 이벤트 형식 변경: **배포 전** | 버전 +1, 이전 버전은 카탈로그의 `retired`에 적는다. 변환기는 만들지 않는다. 이전 버전은 저장된 그대로 읽히고(`isRetiredEvent`), 그런 이벤트가 있는 집계는 이어서 처리하지 않는다: 티켓은 "주의 필요"(`attention: legacy-events`, 조회 테이블 `p_tickets.attention`)가 되고, 엔진이 재개하지 않으며, 노드 명령은 거부된다(fail closed). 배포 전에는 이전 로그가 개발용 DB뿐이라서다. 예: M2의 `node.activated`·`node.completed`·`node.passedOver` v2(`basis`) |
| 이벤트 형식 변경: **배포 후** | 변환기(업캐스터) 필수. `retired`를 쓰지 않는다 |
| 명령 payload | 엔진이 아는 버전만 받는다. 바꿀 때 버전 +1 |
| 코어 DB 스키마 | `PRAGMA user_version`. 마이그레이션은 추가만. 엔진보다 새 DB는 열지 않는다 |
| 조회 테이블 | projector마다 `version`. 바뀌면 열 때 지우고 재생 |
| 와이어 프로토콜 | `PROTOCOL_VERSION`(현재 1) |
| JSON Schema | 2020-12 전용. `$ref`/`$id`는 `#…`과 `urn:vuyro:…`만. 원격·상대 경로 금지 |

## 9. 노드 타입 선언의 확장

- `NodeTypeSpec`은 엄격하다(모르는 필드 거부). 오타가 조용히 통과하지 않게 하려는 것이다.
- **확장 방식:** 엔진 기능이 늘면 선택 필드를 추가한다(타입의 `version`과 무관). 플러그인 데이터는 `extensions.<네임스페이스>`에 둔다. 엔진은 해석하지 않고 보존한다. 더 오래된 엔진은 새 필드가 든 정의를 거부한다(fail closed).
- **M4·M5용으로 지금 넣은 필드**([[공유·권한·BlackBoard 설계]] §3.5, §3.7, §4)

| 필드 | 형식 | 쓰임 |
|---|---|---|
| `reads`, `writes` | BlackBoard 키 또는 패턴(`app:…`, `project:a/b`, `project:a/*`) | 그래프 표시, 내보내기 `requires.blackboard`, 권한 판정 |
| `claims[]` | `{path, mode: exclusive\|shared, release?: nodeDone\|ticketDone\|manual, ttl?: '2h', onConflict?, pauseMode?}` | 노드 시작 때 한꺼번에 잡는 claim. 충돌 정책은 층별 설정을 claim에서 덮어쓸 수 있다 |
| `completion: 'shared'` | | 공유 노드 요청 노드(대기열에 넣고 자기 몫의 결과를 기다림) |
| `extensions` | `{ '<ns>': any }` | 플러그인 전용 |

- **공유 노드 정의 `SharedNodeSpec`**(내보내기 `kind: sharedNode`): `name`, `node{type, version, params}`, `requestSchema?`, `batchTrigger{count?, window?, afterPrevious?, manual?, schedule?, expediteOnPriority?}`(실제로 켜진 조건 하나 이상: `count`·`window`·`schedule`이 있거나 `afterPrevious`·`manual`이 true. `expediteOnPriority`는 조건이 아니다), `maxConcurrent`, `protect?: ClaimSpec[]`(실행 중 읽기 claim), `onBatchFailure: blame|ask|allFail|bisect|agent`, `raiseBlamedPriority?`.
- 작업 공간 모드(`workspaceMode`, `worktreeScope`, `autoCheckoutHook`, `onMergeConflict`, `overlapWarning`)는 노드 타입이 아니라 앱 → 프로젝트 → 템플릿 → 노드 인스턴스 층의 설정이다. **M2에서 템플릿과 노드 인스턴스의 `settings`에 자리를 만들었다.** M4에서 해석한다(§14.1). `claims[]`도 M4부터 노드 시작 때 잡는다(§14.3).
- **M2에서 넣은 필드:** `prompt`(에이전트 노드의 프롬프트 템플릿), `script`(스크립트 노드: `program`, `args`, `env`, `cwd`, `timeout`, `exitPorts`, `output: none|json`). 둘 다 표현식을 쓴다(§10.4). `env` 이름 `VUYRO_*`는 엔진 예약이라 쓸 수 없다.
- `completion: 'shared'` 노드 타입(요청 노드)은 M5부터 받는다. 저장 조건은 §15.2다(M4까지는 저장 단계에서 거부했다).

## 10. 워크플로 (M2)

### 10.1 정의 파일과 저장 순서

- 노드 타입과 템플릿은 내보내기 봉투(`vuyro: 'export'`, `formatVersion: 1`, `kind`, `id`, `version`, `content`, 선택 `checksum`) 파일 하나가 한 버전이다. 위치: `<root>/node-types/<type>/<version>.json`, `<root>/templates/<namespace>/<name>/<version>.json`.
- 해시는 `checksum`을 뺀 봉투의 정규 JSON SHA-256(`sha256:<hex>`)이다. `checksum`이 있으면 맞아야 한다.
- **버전은 바꿀 수 없다.** 같은 `id`+`version`에 다른 내용은 `invariant_violated`. 같은 내용이면 아무 일도 하지 않는다.
- **저장 순서([[기술 스택 결정]] §4의 4단계를 구체화):**
  1. `nodeType.save`/`template.save`가 권한·형식·의미 검사를 통과하면 `definition.staged`를 남긴다. **이벤트에 내용이 들어간다.**
  2. 쓰기 담당(`DefinitionWriter`)이 임시 파일(`<version>.json.tmp`)에 쓰고 원래 이름으로 바꾼 뒤, 다시 읽어 해시를 비교한다. **한 명령이 올린 정의(가져오기 하나)는 모든 파일을 먼저 쓴 뒤 한 번에 활성화한다**(M6b 재검수: `definition.activateMany`, 한 커밋). 파일 하나라도 못 쓰거나 활성화가 거부되면 그 명령의 모든 버전을 **한 커밋으로** 버리고(`definition.abandonMany`) 이번에 쓴 파일을 지운다. 시작할 때의 복구도 같은 묶음으로 하고, 묶음 중 하나라도 이미 버려졌으면 나머지도 버린다(버리는 도중 멈춘 경우).
  3. `definition.activate`(엔진 전용)가 파일을 한 번 더 읽어 해시를 확인하고 활성으로 만든다. 실패하면 `definition.abandon`.
  4. 엔진이 시작할 때 staged로 남은 버전을 마저 처리한다. 파일이 없거나 다르면 staged 이벤트의 내용으로 다시 쓴다.
  - **기술 스택 문서와 다른 점과 이유:** 문서의 순서는 "파일 → DB 등록 → 시작 때 미등록 파일 등록"이다. 그대로 하면 권한 없는 호출자가 파일만 써 두고 다음 시작 때 엔진이 그것을 등록하게 된다. 그래서 **권한 판정(staged)을 파일보다 먼저** 두고, 복구는 staged된 것만 처리한다. 아무도 저장하지 않은 파일은 `scan()`이 "미등록"으로 보고만 한다.
- **쓸 때마다 해시를 다시 본다(fail closed, 검수 반영).** 컴파일한 그래프는 캐시하지만, 템플릿·노드 타입 파일은 쓸 때마다 다시 읽어 해시를 비교한다. 워크플로 명령과 실행기 시작(`node.start`)이 모두 이 경로를 거치므로, 엔진이 도는 중에 파일을 고쳐도 그 티켓은 다음 단계에서 멈춘다(`invariant_violated`). 파일을 되돌리거나 새 버전으로 저장해야 한다.
  - 이유: 처음 구현은 한 번 불러온 정의를 캐시해서 재검증을 건너뛰었다. 그러면 실행 중에 고친 파일로 티켓이 계속 갈 수 있어 [[결정 대기]] D-012와 어긋난다. 명령마다 작은 JSON 파일 몇 개를 읽는 비용은 감수한다.
- 티켓은 `ticket.created.template`에 템플릿 `id`·`version`·`hash`와, 쓰는 노드 타입마다 `type@version → hash`를 고정한다.

### 10.2 템플릿

- `TemplateSpec { id: 'namespace/name', version, name, nodes[], edges[], settings? }`.
- 노드 인스턴스: `{ id, type, version, label?, params?, ports?, review?, settings?, position? }`.
  - `ports.<port>`: `schema`(타입 스키마에 allOf로 추가), `artifacts`(슬롯 추가, 같은 이름은 대체), `strict`, 입력 포트의 `mode: whole|each`.
  - `review: 'human'`: 에이전트·스크립트의 결과를 사람이 승인해야 다음으로 간다(리뷰 게이트).
  - `params`의 문자열은 표현식 템플릿이다. 빠진 값은 param 스키마의 `default`.
- 간선: `{ from: {node, port}, to: {node, port}, when? }`. `when`은 조건 AST(§10.4)로, 간선을 탈 아이템을 고른다.
- 저장 때 검사: 노드 id 중복, 노드 타입 존재(활성), 포트·param 존재와 스키마, 표현식 문법과 루트, `nodes.<id>` 참조 대상, 조건 AST, 진입 노드(들어오는 간선 없음) 1개 이상, 끝 노드(출력 포트 없음) 1개 이상. 닿을 수 없는 노드는 경고.
- **되돌아가는 간선(back edge):** 진입 노드부터 깊이 우선으로 걸을 때 이미 열린 노드로 돌아가는 간선(승인 reject → Spec, QA reject → Dev). 이 간선으로 온 입력은 대상의 "재작업(rework)"이다.

### 10.3 실행 모델

- **레인(lane):** 노드 하나의 병렬 사본. `whole` 입력 노드는 `main` 하나, `each` 입력 노드는 아이템마다 `1`, `2`, …(다시 쓰지 않음). 함께 만들어진 레인은 **그룹**이다. 팬아웃 뒤의 팬아웃은 앞 그룹 아래에 묶인다.
- **실행(run):** 노드의 n번째 실행(레인 전체에서 1, 2, …). `ItemRef.run`이 이것이다. 에이전트 실행(`runId`)과 다르다. 실행 하나가 에이전트 실행 여러 개를 가질 수 있다(엔진 재시작 뒤 이어서 시작).
- **노드 상태(`NODE_STATUSES`):** `wait`(입력 없음, 조회 테이블에 행 없음), `queued`(실행 슬롯 대기), `running`, `review`(사람 차례: 사람 노드, 리뷰 게이트), `done`, `failed`(error 포트로 끝남), `rejected`(반려되어 다시 시작되기 전), `paused`, `stale`(값만 정의). 실행에만 있는 상태: `superseded`(새 입력에 밀림), `discarded`(리뷰에서 반려된 결과).
- **활성화 이유(`cause`):** `start`(진입), `input`, `rework`(되돌아가는 간선, 또는 lineage가 그 레인의 이전 결과로 이어지는 each 입력), `review`(리뷰 게이트 반려: 같은 입력 + `feedback`), `retry`.
- **라우팅은 명령 안에서 끝난다.** 노드를 끝내는 명령이 다음 노드의 활성화, 합류, 티켓 완료까지 같은 커밋에 쓴다. 그래서 "끝났는데 다음이 안 켜진" 상태가 생기지 않는다.
  - `node.completed.routes`에 간선별로 지나간 아이템을 적는다. 티켓 상태는 템플릿 없이 이벤트만 접어서 만든다.
  - `whole` 입력: 팬아웃이 아닌 출처에서 전달이 오면 바로 켠다. 출처가 팬아웃이면 팬인 규칙(§10.6)을 따른다.
  - `each` 입력: 아이템의 lineage가 그 노드의 살아 있는 레인으로 이어지면 그 레인만 다시 돌린다(QA가 고른 아이템만 재실행). 아니면 새 레인을 연다. 그룹과 세대는 §10.6.
  - 합류(`completion: 'join'`, 끝 노드 포함)와 팬인은 **죽은 경로 제거**(dead path elimination, BPMN과 같은 생각)로 판정한다. 규칙 전체는 §10.6 "합류 의미론"이 정본이다.
  - 활성 실행이 있는 레인에 새 입력이 오면 이전 실행은 `superseded`가 되고 엔진이 그 에이전트를 취소한다. 밀려난 실행의 토큰으로는 `node.done`도 `artifact.add`도 할 수 없다(레인을 생략해도 실행 소유권을 확인한다).
  - **빈 출력(검수 반영, [[결정 대기]] D-016):** 에이전트·스크립트가 간선이 이어진 포트로 아무것도 보내지 못하면(아이템 0개, 또는 어떤 아이템도 간선 조건을 통과하지 못함. error 포트도 같다) 바로 보내지 않고 사람 확인(`node.reviewRequested`, `reason: 'empty'`)으로 간다. 반려하면 의견을 받아 다시 돈다. 승인하면(사람 노드를 아이템 없이 끝낸 경우도) **빈 전달**을 보낸다. 빈 전달을 받은 each 노드는 레인을 열지 않고 넘어가며(`node.passedOver`: 빈 그룹, error가 아닌 출력 간선으로 빈 전달을 넘김), whole 입력 노드는 아이템 0개로 돌고, 합류는 가진 것으로 켜진다. `node.completed.empty`에 빈 전달을 받은 간선을 적는다.
  - **낡은 반려(검수 반영, D-017):** each 입력으로 가는 아이템의 lineage가 대상 노드의 **옛 세대** 레인으로만 이어지면(그 사이 Plan이 다시 돌아 작업이 바뀜) 아무 데도 보내지 않고 `node.completed.stale`에 남긴다. 새 세대의 레인과 합류 결과는 그대로다.
  - **새 세대가 열리면 옛 세대의 활성 실행은 밀려난다(D-019).** 경로의 끝, 대기 사유, 티켓 종료도 §10.6에 있다. 테스트 하네스의 `drive()`가 매번 모든 티켓에서 "열린 티켓에는 대기 사유가 있다"를 검사하고, `test/workflow-property.test.ts`가 §10.6을 엔진과 따로 구현한 오라클(`test/helpers/join-oracle.ts`)로 검사한다.
- **lineage:** 입력 아이템은 원본 출력 아이템을 가리키는 `[ref]`를 가진다. 출력 아이템의 기본 lineage는 입력이 하나면 그것, 입력 수와 출력 수가 같으면(2 이상) 순서대로, 아니면 모든 입력이다. `pairedInput`(입력 순서 번호)이나 명시 `lineage`(티켓 안에 실제로 있는 출력만)로 정할 수 있다.
- **결과 제출:** 에이전트는 실행 중 `node.done`으로 결과를 내고(`node.outputSubmitted`), 실행이 정착하면 엔진이 `node.finish`로 적용한다. 정착 전에 다시 내면 마지막 것이 쓰인다. 결과를 낸 뒤 비정상 종료해도 결과를 인정한다. 결과 없이 끝나면 `failed`. 결과를 낸 뒤 등록한 산출물도 합친다.
- **검증:** 포트 data 스키마(사람·에이전트가 쓴 스키마는 비엄격 Ajv: 모르는 키워드 무시), 산출물 슬롯의 kind와 필수 여부. 틀리면 `validation_failed` + `issues`로 돌려줘서 에이전트가 고친다. 스키마가 닫혀 있으면 선언되지 않은 최상위 필드를 `undeclared`로 남긴다.
- **재시작:** 엔진이 시작하면 고아 실행을 정착시키고(§4) 남은 일을 다시 잡는다. 중단된 에이전트는 자동으로 최대 3번(`MAX_AUTOMATIC_ATTEMPTS`) 다시 시작하고, 세션이 기록됐으면 `resumedFromRunId`로 이어서 한다. 스크립트는 부작용이 있을 수 있어 다시 돌리지 않고 `failed`로 끝낸다.
- **일시정지:** 실행 중이 아닌 레인은 바로 `paused`. 실행 중인 에이전트는 `node.pauseRequested` → 엔진이 취소 → `paused`(재개하면 세션을 이어서). 실행 중인 스크립트는 멈출 수 없다. 일시정지가 적용되기 전에 재개하면 취소된 실행은 다시 줄을 선다(실패가 아님).

### 10.4 표현식과 조건

- 템플릿 문자열의 `{{ path }}`. 경로만 쓸 수 있다(연산자, 호출, 리터럴 없음). `\{{`는 글자 그대로의 `{{`다.
- 루트: `input`(첫 입력 아이템. each 레인은 자기 아이템), `inputs.<port>`, `nodes.<id>`(`item`: lineage로 찾은 짝. `data`/`artifacts`/`summary`: 짝, 없으면 최신 실행의 첫 아이템. `runs`(`runs.last`), `port`, `items`), `params`(렌더된 값. param 안에서는 못 씀), `ticket`, `node`, `feedback`, 간선 조건에서만 `item`.
- 배열은 `[n]`, `first`, `last`, `length`/`count`. 평범한 JSON 객체의 자기 속성만 읽는다. `__proto__`, `prototype`, `constructor`는 문법에서 거부한다. 없는 값은 빈 문자열(텍스트)이나 `undefined`(값)다.
- 템플릿 전체가 표현식 하나면 원래 값(배열, 객체)을 쓴다. 스크립트 인자에서 배열이면 인자 여러 개로 펼친다.
- 조건 AST: `{all|any: [...]}`, `{not}`, `{op: eq|ne|lt|lte|gt|gte|in|contains, left, right}`, `{op: exists|empty, left}`. 피연산자는 `{path}` 또는 `{value}`(평범한 JSON). 깊이 32, 노드 512, 리터럴 값 1만 개, 리터럴 문자열 65,536자 제한. 제한을 넘으면 그 자리에서 검사를 멈춘다(오류는 최대 50개). 형 변환 없음.

### 10.5 실행기

- **에이전트:** `node.start`가 실행과 토큰을 만들고, 엔진이 `AgentAdapter.start(AgentStartRequest)`를 부른다(`packages/agent-adapters`, M3가 구현). 요청: `runId`, `provider`, 티켓·노드·레인·실행 번호, 프롬프트(노드 템플릿 + 보고 방법과 포트 설명), `env`(`VUYRO_RUN_TOKEN`, `VUYRO_TICKET`, `VUYRO_NODE`, `VUYRO_LANE`, `VUYRO_RUN_ID`), `cwd`, `resume`. 반환: `observations`(정규화 관측), `settled`, `cancel()`. 엔진이 관측을 `run.observe`로, 끝을 `run.settle`로 남긴 뒤 `node.finish`를 낸다. **토큰은 환경 변수로만 넘긴다.**
- **작업 폴더:** 엔진 옵션 `workspace(target)`이 실행마다 폴더를 정한다. `target = { ticketId, projectId, nodeId, lane, run, attempt }`(M4의 `nodeRun` 단위 worktree용).
- **스크립트:** 셸 없이 실행한다. 환경 변수는 기본 집합(PATH, SystemRoot, TEMP/TMP, HOME/USERPROFILE, LANG)과 노드가 선언한 것뿐이다. 선언하는 이름에 `VUYRO_`는 대소문자와 상관없이 쓸 수 없다(Windows 환경 변수 이름은 대소문자를 가리지 않는다). 실행 토큰은 받지 않는다. 종료 코드 → 포트(`exitPorts`, 기본 `0 → done`, 나머지 `error`). `output: json`이면 마지막 줄 JSON(`{port?, data?, summary?, items?}`, items는 스키마로 검사). 제한 시간(기본 30분)이 지나면 죽이고 `failed`.
- **동시 실행:** 앱 전체에서 에이전트+스크립트 기본 4개. 나머지는 `queued`.
- **엔진의 요청 id**는 (단계, 티켓, 노드, 레인, 실행, 시도)에서 만든 해시라서, 크래시 뒤 같은 단계를 다시 보내면 멱등으로 처리된다.

### 10.6 합류 의미론 (M2 재검수 반영)

> 합류·팬인·재실행·티켓 종료 규칙의 정본이다. `workflow/machine.ts`가 이것을 구현하고, 속성 테스트의 오라클(`test/helpers/join-oracle.ts`)은 엔진의 상태 접기를 쓰지 않고 이벤트 로그에서 이 절을 따로 구현한다. 규칙을 바꾸면 셋을 함께 바꾼다.
> 오라클은 같은 판정을 같은 방식으로 복제하지 않는다(재검수 지적: 복제한 오라클은 구현과 같이 틀린다). 세대(3)는 이벤트의 `basis` 필드를 쓰지 않고, 오라클이 활성화마다 "무엇을 소비했는가"(직접 전달의 출처 실행, 합류·팬인에 기여한 실행과 건너뛴 그룹, 재실행의 원래 실행)를 스스로 다시 계산해 소비 그래프를 만들고, 실행에서 시작하는 **모든 경로를 하나씩 나열**해 판정한다. 그 결과를 엔진이 적은 `basis`와 비교한다.

**용어**

1. **차례.** 티켓 안의 활성화(`node.activated`), 완료(`node.completed`), 건너뛰기(`node.passedOver`)는 일어난 순서대로 차례 번호를 받는다. "X 이후"는 이 번호로 센다. 노드의 **마지막 활성화**는 그 노드의 가장 최근 `node.activated`다.
2. **팬아웃 노드**는 each 입력 포트가 있는 노드다. 팬아웃 노드가 한 번의 전달로 연 레인 묶음이 **그룹**이다. 팬아웃 레인에서 온 전달로 열린 그룹(연쇄 팬아웃)은 출처 레인의 그룹을 **부모**로 가진다. 빈 전달로 건너뛰어도 레인 없는 그룹이 생긴다.
3. **현재 그룹**은 노드가 가장 최근에 연 그룹이다. 그룹이 **살아 있다** = 자기 노드의 현재 그룹이고, 부모가 있으면 부모도 살아 있다. 레인이 살아 있다 = 그룹이 없거나(`main`) 그룹이 살아 있다. 살아 있는 그룹이 **현재 세대**, 나머지는 **옛 세대**다.
   - **세대 기록(재검수 반영).** 세대는 아이템 lineage로 추정하지 않고 실행과 전달에 직접 적는다. 기록은 `basis = {groups, free?}`다. `groups`는 그 일이 기대는 팬아웃 그룹들(그룹 id가 노드와 세대를 함께 가리킨다), `free`는 팬아웃을 거치지 않은 출처에도 기댄다는 뜻이다.
     - **전달의 기록**(`node.completed.basis`, `node.passedOver.basis`): 팬아웃 레인 실행이 보낸 것은 `{그 레인의 그룹}`, 건너뛰기가 넘긴 빈 전달은 `{건너뛴 그룹}`, 그 밖의 실행이 보낸 것은 그 실행의 기록이다. 빈 전달도 기록을 싣는다.
     - **실행의 기록**(`node.activated.basis`): 그 활성화가 소비한 전달들(직접 전달, 합류·팬인의 기여, 다른 포트의 최신 전달. 빈 전달 포함) 기록의 합이다. 아무것도 소비하지 않은 실행(입구)은 `free`. 재시도·리뷰 재실행은 원래 실행의 기록을 그대로 쓴다.
     - **새 세대를 연 실행**(`node.activated.openedBy`, `node.passedOver.openedBy`): 전달로 새 그룹을 연 실행이 보내는 것은 **그 실행이 연 그룹들에만** 속한다. 그 실행 자신의 판정도 같다. 자기 기록(`free`나 다른 그룹)은 더하지 않는다(재검수 반영: 입구 Plan이 g1을 열고 같은 완료로 사람 Review에도 보내면 Review의 기록은 `{g1}`이고, 다음 계획이 g1을 바꾸면 Review도 밀려난다). 예: 빈 계획을 본 검토가 반려해 새 작업 묶음을 열면, 같은 반려로 다른 노드에 보낸 일도 새 세대다(오라클이 찾은 반례). 그래서 한 완료가 보내는 것은 each 입력 대상부터 처리한다. 같은 완료가 연 세대가 나머지 전달에 실린다. `node.completed.basis`는 그 완료 시점의 기록(아직 연 그룹 없음)이다.
   - **옛 세대의 실행:** 옛 세대 레인의 실행, 그리고 팬아웃 레인이 아닌 실행 중 기록이 `free`가 아니고 `groups`가 모두 옛 세대인 것(옛 계획의 결과에만 기대는 후속 작업. 예: 옛 합류 결과를 받은 QA, **빈 계획을 건너뛴 합류로 빈 입력을 받은 QA**). 한 출처라도 현재 세대이거나 `free`면 현재 세대다. 아이템이 있는지, lineage가 무엇을 가리키는지와 무관하다(검수 반영). 이렇게 해서 "실제로 받은 빈 전달"(건너뛴 그룹의 기록을 싣는다)과 "옛 세대라서 기여가 아닌 것"(7)이 구별된다.
4. **활성 실행** = queued/running/review/rejected/paused. **정착한 실행** = done/failed. 레인의 **현재 실행**은 그 레인의 마지막 실행이다.

**세대**

5. 전달이 팬아웃 노드 T에 오면 아이템마다:
   - lineage가 T의 살아 있는 레인으로 이어지면 그 레인을 다시 돌린다(재작업).
   - T의 레인으로 이어지지만 모두 옛 세대 레인이면 낡음(D-017). 보내지 않는다.
   - 나머지는 새 레인이다. 넣을 그룹: 연쇄 팬아웃이면 출처 레인 그룹 아래의 살아 있는 그룹(없으면 연다). 아니면 같은 전달에 재작업 아이템이 있으면 T의 현재 그룹에 더하고(D-020), 없으면 **새 그룹을 연다(새 세대)**.
   - 빈 전달은 레인 없이 같은 방식으로 그룹을 정하고(연쇄면 부모 아래 그룹을 다시 쓰거나 열고, 아니면 새 빈 그룹), error가 아닌 출력 간선으로 빈 전달을 넘긴다.
6. **옛 세대 정리(D-019).** 그룹이 열려 다른 그룹이 살아 있지 않게 되면, 옛 세대가 된 활성 실행(그 그룹들과 연쇄 하위의 레인, 그리고 3의 "옛 세대의 실행"인 후속 노드 실행)은 같은 커밋에서 `node.superseded`(`reason: 'replaced'`)로 끝나고 엔진이 그 에이전트를 취소한다. 그래서 **활성 실행은 항상 현재 세대에만 있다**(불변식). 옛 세대의 실행은 승인·반려·재시도할 수 없다.

**기여와 정착**

7. 출처 S가 간선 묶음 E(S → T)로 T에 주는 **기여**:
   - S가 팬아웃 노드면: S의 현재 그룹이 살아 있을 때, 그 그룹 레인마다 정착한 현재 실행이 E로 보낸 아이템. 살아 있지 않으면 없다.
   - 아니면: S에서 가장 최근에 정착한 실행이 E로 보낸 아이템. 그 실행이 다른 포트로 나갔거나 옛 세대의 실행(3)이면 없다(죽은 경로).
   - 빈 전달도 "보낸 것"이다(아이템 0개).
   - 기여는 실행 단위다. 옛 세대가 된 실행이 보낸 것은 아이템을 지우는 것이 아니라 처음부터 기여가 아니므로, 새로움(8)도 생기지 않는다(재검수 반영: 기여 아이템만 지우고 새로움을 남기면 합류가 빈 입력으로 켜졌다).
8. 기여가 **새롭다** = 기여한 실행 중 하나가 E로 보냈고 T의 마지막 활성화 이후에 정착했다. 또는 S의 살아 있는 현재 그룹이 T의 마지막 활성화 이후 빈 전달을 E로 넘겼다. 옛 세대가 보낸 것은 기여가 아니므로 새롭지도 않다.
9. S가 T에 대해 **정착했다**:
   - **바쁘지 않다:** S에도, S의 현재 그룹에서 부모로 올라가며 만나는 그룹들의 레인에도 활성 실행이 없다(재실행 대기: 다시 도는 중이거나 돌 차례면 더 새 결과가 온다).
   - 기여가 새롭지 않은 S는 더해서, 활성 실행이 있는 어느 노드에서도 T를 거치지 않고 S에 닿을 수 없다(되돌아가는 간선 포함. 죽은 경로 제거).
   - 새 기여가 있는 S는 더 위에서 다시 올 수 있는 결과를 기다리지 않는다. 그것이 오면 합류가 다시 돈다. 이렇게 하지 않으면 언제 끝날지 모르는 사람 노드(예: "재계획" 입구)가 그 아래의 모든 합류를 막는다.

**켜짐**

10. **합류**(`completion: 'join'`, 출처 = 들어오는 간선의 노드들): 새 기여가 있는 출처가 하나 이상이고 모든 출처가 정착하면 켜지고 바로 done으로 끝난다. 입력 = 포트마다, 출처의 간선 순서대로 기여 아이템.
11. **팬인**(whole 입력이고 합류가 아닌 노드 T, 팬아웃 출처 S): 기여가 새롭고 바쁘지 않은 팬아웃 출처가 하나라도 있으면 켠다. 그런 출처가 여럿이면 한 번에 모두 받는다(따로 켜면 두 번째 출처는 더 이상 새롭지 않아 결과가 빠진다). 그 출처들이 이어진 포트의 입력은 그 기여를 출처 순서로 합친 것, 다른 포트는 그 포트 간선들의 최신 전달이다. 팬아웃이 아닌 출처에서 whole 입력으로 온 전달은 기다리지 않고 바로 켠다(빈 전달이면 아이템 0개). **다른 포트의 "최신 전달"(최종 검수 반영):** 간선마다 출처의 기여(7)와 같다. 팬아웃이 아닌 출처는 **가장 최근에 정착한 실행을 먼저 고르고**, 그 실행이 이 간선을 쓰지 않았으면 이 간선에서 받을 것은 없다(죽은 경로). 이전 실행이 이 간선을 썼어도 되살리지 않는다(예: 다시 돈 노드가 yes 대신 no로 나간 뒤 다른 포트의 전달로 켜져도 옛 yes 아이템은 들어가지 않는다). 그 실행이 옛 세대여도 없다.
12. 경로는 어디서든 죽을 수 있으므로 노드가 끝날 때마다 모든 합류와 팬인을 다시 판정한다. 같은 명령 안에서 끝까지 이어서 판정한다(합류가 끝나면 그 완료가 다시 판정을 부른다).

**끝과 티켓 종료**

13. **경로의 끝:** 끝 노드가 done, 간선 없는 포트로 나간 done(암묵적 끝, D-018), 더 갈 간선 없는 팬아웃 건너뛰기. **현재 세대의 것만 센다**(재검수 반영): done 실행은 현재 세대의 실행(3)이어야 하고, 건너뛰기는 그 그룹이 살아 있어야 한다. 옛 계획의 결과로 끝 노드가 끝났어도 재계획한 뒤에는 새 계획 쪽 경로가 끝나야 한다(D-021). 빈 전달로만 끝난 끝 노드도 그 기록(건너뛴 그룹)으로 세대를 가린다. 간선은 있지만 아이템이 모두 낡아 아무 데도 가지 않은 done은 경로의 끝이 **아니다**(D-021, 검수 반영): 낡은 출력만으로는 현재 작업이 끝났다고 보지 않는다.
14. **대기 사유:** 활성 실행, 그리고 레인의 현재 실행이 현재 세대이고 failed인데 어떤 간선도 받아 가지 않은 것(처리되지 않은 실패). 빈 전달을 받은 간선도 받아 간 것이다. 옛 세대의 실패(3)는 사유가 아니다. 또 현재 세대의 현재 실행이 done인데 아이템이 모두 낡아 아무 데도 가지 않았으면(13) 그것도 사유다(`stale`, D-021). 둘 다 재시도로 다시 실행한다. 로그에 이전 형식 이벤트가 있는 티켓(§6)은 "주의 필요"(`attention`)가 유일한 사유다.
15. **티켓 종료:** 경로가 하나라도 끝났고 대기 사유가 없으면 같은 커밋에서 `ticket.completed`. 열린 티켓에는 항상 대기 사유가 있다.

**오라클이 검사하는 것** (`test/workflow-property.test.ts`, 무작위 그래프 300개)

- **안전성:** 합류가 켜질 때 10이 성립하고 입력이 7의 기여와 같다. 팬인이 켜질 때 11이 성립하고 입력이 기여와 같다. 옛 세대 레인에는 활성화가 없고, 옛 세대의 실행은 끝나지(완료되지) 않으며, 밀려난 실행은 실제로 옛 세대다.
- **진행성:** 엔진이 더 할 일 없이 멈췄을 때(사람 결정이나 처리되지 않은 실패만 남음) 켜질 수 있는 합류·팬인이 없고, 보낸 아이템은 모두 대상의 활성화로 받아졌으며(each면 레인, 낡음은 제외), 옛 세대의 활성 실행이 없고(재계획 때 하류에서 Review를 기다리던 실행 포함), 열린 티켓에는 14의 사유가 있고, 사유가 없고 경로가 끝났으면 티켓은 완료다. 엔진의 `ticketWaitReasons`는 오라클의 사유와 같다.
- **커버리지:** 다중 출처 합류, 팬아웃 레인, 반려 루프, 재계획(살아 있는 그룹이 있던 노드에 새 세대), 옛 세대의 활성 실행 정리, 하류 Review 정리, 옛 계획의 끝 뒤 재계획, 재계획 때 혼합 lineage 입력을 가진 활성 실행 횟수의 최소치를 단언한다.

## 11. 엔진 데몬과 와이어 프로토콜 (M3)

> 코드: `packages/engine/src/daemon/`(기동, RPC 서버, 자격, 조회), `src/client/engine-client.ts`(CLI·앱 쪽), `packages/contracts/src/rpc.ts`(메서드·파라미터 스키마).

**기동 순서** (`startEngineDaemon`, 진입점 `daemon/main.ts`. Electron 없이 Node만으로 돈다)

1. Windows면 엔진 프로세스를 kill-on-close Job 객체에 넣는다(`bindDescendantsToProcess`). 핸들은 엔진만 가지므로 엔진이 어떻게 끝나든 에이전트 CLI와 그것이 띄운 도구가 함께 끝난다. 자식은 상속으로 Job에 들어가므로 띄운 직후 배정하는 틈이 없다.
2. 데이터 폴더 잠금(`engine/engine.lock`을 공유 없이 연다. 프로세스가 끝나면 OS가 푼다). **같은 데이터에 두 번째 엔진은 여기서 실패한다.** 아무것도 읽기 전이라, 살아 있는 엔진의 실행을 고아로 정착시킬 수 없다.
3. `startEnginePipe`: 새 토큰 → 리스닝(파이프 이름별 단일 인스턴스) → 토큰 커밋. 이때 들어온 연결은 준비가 끝날 때까지 기다린다.
4. 이벤트 저장소 → 정의 레지스트리 → 버스(`humanCredential` = CLI 자격 검증기) → `DefinitionWriter.start()`·`recover()` → `installBuiltins`.
5. `WorkflowEngine.start()`: 고아 실행을 정착시키고(§4) 남은 일을 잡는다.
6. 기다리던 연결을 받는다.

- **수신 크기:** 한 줄(완성된 줄과 아직 끝나지 않은 줄 모두)이 16 MiB를 넘으면 파싱하기 전에 `message too large`로 끊는다(검수 반영: 완성된 줄은 크기 검사 없이 파싱하던 것을 고침).

- **경로:** 데이터 폴더 기본 `%LOCALAPPDATA%\Vuyro`. 그 아래 `engine/engine.db`, `engine/engine.token`, `engine/engine.lock`, `definitions/`, `logs/engine.log`.
- **파이프 이름:** `\\.\pipe\vuyro-engine-<SHA-256(사용자 SID, 데이터 폴더) 앞 24자>`. 파이프 이름 공간은 PC 전체에 하나이므로 사용자와 데이터 폴더마다 다르게 한다. 클라이언트도 같은 규칙으로 찾고, `VUYRO_DATA_DIR`·`VUYRO_PIPE`가 있으면 그것을 쓴다. 엔진은 에이전트 환경에 이 둘을 넣어, 에이전트의 `vuyro` 호출이 자기를 띄운 엔진에 닿게 한다.
- **띄우기:** `launchEngineDaemon`은 `node main.js --data-dir … --pipe …`를 detached로 띄운다(띄운 쪽이 닫혀도 산다). 엔진이 응답할 때까지 기다리고, 응답한 엔진이 자기가 띄운 것인지(`started`) 알려준다. 이미 다른 엔진이 있으면 새 프로세스는 잠금에서 물러난다. 시작 실패는 `logs/engine.log`에 남는다.
- **멈추기:** 연결을 끊고 리스닝을 멈춘 뒤 실행 중인 에이전트를 취소한다. 취소된 실행은 정착과 `node.finish`까지 기록되고, 다음 시작에서 다시 줄을 선다. 그 뒤 DB를 닫고 잠금을 푼다.

## 12. 통계 (M3)

> 코드: `packages/engine/src/stats/ticket-stats.ts`(순수 함수), 조회 `query.ticketStats`, CLI `vuyro ticket stats`. 이벤트만으로 계산한다. 템플릿은 노드 종류를 알 때만 쓴다.

- **노드별 시간:** 실행마다 상태 구간을 더한다.
  - `queuedMs`: queued, 실행기 노드의 rejected
  - `runningMs`: running
  - `humanWaitMs`: review, 사람 노드의 rejected
  - `pausedMs`: paused
  - 실행이 끝나면(완료, 반려되어 버려짐, 밀려남, 새 입력에 밀림) 구간이 닫힌다. 열린 구간은 조회 시각(`asOf`)까지, 티켓이 끝났으면 완료 시각까지 센다.
- 실행기 노드인지는 고정된 템플릿의 `completion`으로 안다. 템플릿을 읽을 수 없으면 `node.started`가 한 번이라도 있었던 노드로 본다.
- **노드별 사용량:** 그 노드 에이전트 실행들의 토큰(`run` 범위는 덮어쓰고 `turn`은 더한다), 정가 기준 금액(있을 때만), 도구 호출·실패, 메시지 수. 그리고 `executions`, `attempts`, `failed`, `reworks`(rework·review·retry로 시작된 실행), `decisions {human, ai}`(엔진이 아닌 주체가 낸 완료·반려를 `actor.kind`로 나눔).
- **티켓:**
  - `totalMs`: 생성부터 완료까지, 열려 있으면 지금까지
  - `humanWaitMs`: **누군가 사람을 기다린 벽시계 시간.** 사람 대기 구간의 합집합이라 겹친 시간은 한 번 센다
  - `activeMs`: 에이전트·스크립트가 하나라도 돈 시간의 합집합
  - 노드 사용량의 합, `bottleneck`(running + 사람 대기가 가장 긴 노드)
  - 정의의 기획 판단은 [[결정 대기]] D-024.

**프로세스**

- 셸 없이 띄운다(`shell: false`). Windows는 `.cmd`/`.bat` 심을 셸 없이 띄울 수 없다. 그래서 PATH에서 실제 실행 파일(`.exe`/`.com`)만 찾고, 심만 있으면 실행 파일 경로를 설정하라는 오류를 낸다.
- **프롬프트는 stdin으로 보내고 닫는다.** Claude `-p`(프롬프트 인자 없이), Codex `exec … -`. 이어하기는 Claude `--resume <세션>`, Codex `exec … resume <세션> -`. 명령줄은 길이 제한이 있고 다른 프로세스가 볼 수 있기 때문이다. 둘 다 실제 CLI로 확인했다([[초기 검증 결과]] M3).
- **실행 토큰은 환경 변수로만 간다.** 환경 = 사용자 환경(로그인·프록시 설정에 필요, D-025)에서 `VUYRO_*`와 엔진을 띄운 세션의 변수(에이전트 CLI 세션 표시·메시징 소켓과 토큰, 터미널 통합 `HERDR_*`, D-070)를 뺀 것 + 실행 변수(`VUYRO_RUN_TOKEN`, `VUYRO_TICKET`, `VUYRO_NODE`, `VUYRO_LANE`, `VUYRO_RUN_ID`) + 엔진 위치(`VUYRO_PIPE`, `VUYRO_DATA_DIR`). 실행 변수가 언제나 이긴다.
- **에이전트 PATH의 `vuyro` (M7a, 검수 반영):** 데몬이 `vuyroCli`를 받으면 `<데이터>/bin/`에 `vuyro.cmd`(cmd·PowerShell)와 `vuyro`(Git Bash용 sh)를 두고, 어댑터가 그 폴더를 PATH 맨 앞에 넣는다(`pathDirs`). 심에는 CLI 경로만 있다.
  - **에이전트를 띄울 때마다** 엔진(`VuyroShims.ensure`)이 폴더와 두 파일을 다시 본다. 폴더는 링크가 아닌 진짜 폴더여야 하고, 두 심(일반 파일) 말고는 아무것도 없어야 한다(중단된 교체의 `<심>.<uuid>.tmp`만 지운다). 다른 항목(`claude.exe`, `git.exe`, 폴더, 링크)이 있으면 지우지 않고 에이전트 시작을 거부한다. 그 폴더가 PATH 맨 앞이라 그 항목도 실행 토큰과 함께 실행될 수 있기 때문이다(재확인 반영). 내용이 엔진이 쓴 것과 다르거나, 소유자가 현재 사용자가 아니거나, DACL이 본인 전용이 아니면, 본인 전용 DACL을 먼저 건 임시 파일에 내용을 쓰고 이름 바꾸기로 교체한 뒤 다시 확인한다. 폴더는 본인 전용 + 상속(`D:P(A;OICI;FA;;;<user>)`). 확인·교체가 실패하면 그 실행은 시작하지 않는다(`start_failed`).
  - **위협 모델:** 심을 바꿀 수 있는 쪽은 다음 에이전트 안에서 그 실행 토큰으로 명령을 낼 수 있다. 다른 사용자는 DACL로 막힌다. 같은 사용자의 프로세스는 확인과 에이전트의 조회 사이에 바꿀 수 있지만, 그 프로세스는 원래 경계 밖이다(D-001: 엔진 토큰과 에이전트 프로세스 메모리도 읽을 수 있다). 결정 대기 D-071.
- 기본 인자(D-028): Claude `--permission-mode acceptEdits --allowedTools "Bash(vuyro:*)"`, Codex `-s workspace-write`. 체크아웃 훅 주입은 §14.7(M4). 노드별 도구 목록은 아직 없다.
- **Codex는 `vuyro mcp`로 보고한다(검수 반영).** Codex의 셸은 제한 토큰 샌드박스라 엔진 파이프를 열 수 없다(`EPERM`, 실측). 그래서 어댑터가 `vuyro mcp`(노드 에이전트 전용 stdio MCP 서버, 도구 `vuyro_node_done`·`vuyro_artifact_add`)를 `-c mcp_servers.vuyro.{command,args,env_vars}`로 붙인다. Codex는 MCP 서버를 샌드박스 밖에서 띄우고, 이름을 적은 `VUYRO_*` 변수만 넘긴다. 명령줄에는 토큰이 없다. MCP 서버는 같은 명령 API로 같은 envelope(실행 토큰 포함)를 보낸다. 실행 토큰이 없으면 도구를 내놓지 않는다. CLI 위치는 데몬 옵션 `vuyroCli`(`main.ts --vuyro-cli`)로 받는다.
- 취소와 시간 제한(기본 60분, D-026)은 **프로세스 트리**를 끝낸다. Windows는 `%SystemRoot%\System32\taskkill.exe /T /F`(PATH를 보지 않는다)를 먼저 하고 자식을 끝낸다. 그 밖의 OS는 프로세스 그룹을 끝낸다.
- 자식이 끝났는데 출력 파이프를 손자가 쥐고 있으면 2초 뒤 읽기를 멈추고 정착한다.

## 14. 작업 공간과 내부 체크아웃 (M4)

> 코드: `packages/contracts/src/workspace.ts`(장부·worktree·머지 타입), `packages/engine/src/workspace/`(설정, 경로, 장부 접기, git, 조율기, 감시), 핸들러 `commands/workspace-handlers.ts`, 훅 `packages/cli/src/hook.ts`, 훅 인자 `packages/agent-adapters/src/hooks.ts`. 설계는 [[공유·권한·BlackBoard 설계]] §3.7~§3.9.
> **외부 툴에는 아무것도 걸지 않는다.** git이나 Perforce에 잠금·체크아웃을 걸지 않는다. Vuyro의 체크아웃은 자기 장부다. git은 읽기 전용 조회(`status`, `rev-parse`, `merge-base`, `diff --name-only`, optional lock 끔)와, worktree 모드에서 엔진 자신의 worktree·`vuyro/…` 브랜치를 만들고 머지하고 지우는 데만 쓴다. 셸 없이 실행한다.

### 14.1 설정 층

| 필드 | 기본값 | 뜻 |
|---|---|---|
| `workspaceMode` | `shared` | `shared`: 모든 노드가 프로젝트 폴더에서 일한다. `worktree`: git worktree |
| `worktreeScope` | `nodeRun` | `ticket`: 티켓마다 하나. `nodeRun`: 팬아웃 레인마다 하나(그 밖의 노드는 티켓 worktree) |
| `autoCheckoutHook` | shared면 켬, worktree면 끔 | 파일 수정 직전 훅 |
| `onConflict` | `firstWins` | claim·체크아웃 충돌(§14.3) |
| `pauseMode` | `boundary` | 선점할 때 점유한 쪽을 멈추는 방법 |
| `onMergeConflict` | `ask` | 합류 머지 충돌(§14.6) |
| `mergeAgent` | Claude | `agent` 정책이 띄울 에이전트 |
| `overlapWarning` | 켬 | 두 레인 worktree가 같은 파일을 바꾸면 머지 전에 경고 |

- 층은 앱(`app.configure`) → 프로젝트(`project.configure`) → 템플릿(`settings`) → 노드 인스턴스(`settings`)다. 아래 층이 필드 단위로 덮어쓴다. claim 하나가 자기 `onConflict`·`pauseMode`를 가질 수 있다.
- **티켓은 만들 때 앱 + 프로젝트 층과 프로젝트 폴더(`root`)·`baseRef`·감시 경로를 `ticket.created.workspace`에 고정한다.** 나중에 바꾼 설정은 새 티켓부터 쓴다. 템플릿·노드 층은 고정된 템플릿에서 온다. 그래서 설정 해석은 이벤트만으로 다시 할 수 있다.
- 프로젝트 폴더가 없으면 shared 모드의 장부는 동작하지 않는다(체크아웃은 `outside`로 허용). 작업 폴더는 엔진 옵션 `workspace`로 정해진다(M3와 같음). (M7b) 데몬의 기본값은 데이터 폴더의 `work/<티켓 키>`(티켓마다 빈 폴더)다. 전에는 기본값이 없어 엔진 프로세스의 현재 폴더에서 일했다(D-072).
- 감시 기본 제외: `.git/**`, `node_modules/**`, `Intermediate/**`, `Binaries/**`, `Saved/**`, `DerivedDataCache/**`. 프로젝트의 `watch.include`·`watch.exclude`로 바꾼다.

### 14.2 장부

- 집계 `workspace:<projectId>`(타입 `workspace`). 프로젝트마다 하나다. **공간(space)** 은 파일이 있는 폴더다: `root`(프로젝트 폴더), `wt:<티켓 키>`(티켓 worktree), `wt:<티켓 키>/<노드>-<레인>`(레인 worktree). 다른 공간끼리는 겹치지 않는다(다른 파일이다).
- 항목(`CheckoutEntry`): 공간, 정규화한 상대 경로 또는 패턴(`/` 구분, `..` 없음, Windows는 대소문자 무시), `claim`(노드 타입이 선언, 시작 때) 또는 `checkout`(수정 직전 한 파일), `exclusive`/`shared`, 점유자 `{ticketId, nodeId, lane, run}`, 해제 `nodeDone`/`ticketDone`/`manual`, 그때의 정책과 티켓 우선순위, 선택 `expiresAt`(ttl), 체크아웃이면 `baseHash`(SHA-256, 없던 파일은 null).
- 이벤트: `checkout.acquired`(겹침을 허용했으면 `overlaps`), `checkout.blocked`(거부와 그 결정), `checkout.released`(사유: `nodeDone`·`ticketDone`·`manual`·`ended`·`expired`·`preempted`·`recovered`), `checkout.retained`(ticketDone 항목을 티켓이 넘겨받음), `checkout.paused`(pauseHash), `checkout.resumed`(멈춘 동안 바뀐 것), `workspace.changesDetected`, `workspace.baselined`, `workspace.overlapWarned`, `worktree.created`, `worktree.removed`, `worktree.kept`(엔진이 지우지 않고 사람에게 남긴 worktree와 그 안에 남은 것, 검수 반영), `worktree.cleanupApproved`·`worktree.cleanupSkipped`(사람의 정리 확인과, 그 사이 바뀌었거나 쓰는 중이라 하지 않은 정리).
- **항목이 아직 쥐고 있는가**(충돌 판정과 사후 검출이 같은 규칙을 쓴다): 만료 전이고, `manual`이면 언제나, 넘겨받은 항목이면 티켓이 열려 있는 동안, 그 밖에는 점유한 실행이 그 레인의 현재 실행이고 활성(queued/running/review/rejected/paused)인 동안. 해제 이벤트가 늦어도(엔진의 후속 작업) 끝난 실행의 항목은 아무것도 막지 않는다.

### 14.3 충돌과 정책

| 정책 | 나중에 온 요청 |
|---|---|
| `firstWins` | 기다린다. 노드 시작이면 `node.paused`(`claim`), 수정 직전이면 실행을 멈추고(`node.pauseRequested` + `claim` → 취소 → `node.paused`) 세션을 보존한다. 막던 항목이 모두 사라지면 엔진이 `node.resume`(system)으로 다시 줄 세우고, 시작이 claim을 다시 판정한다 |
| `priorityWins` | 요청 티켓의 우선순위가 더 높고, 막는 항목의 `pauseMode`가 `immediate`이고, 점유자가 실행 중인 에이전트면 **선점**: 그 항목을 `preempted`로 해제하고 점유자를 멈춘다(`claim.preemptedBy`). 점유자는 요청자의 새 항목을 기다렸다가 세션을 이어서 재개한다. 그 밖에는 `firstWins`처럼 기다리고, 재개는 우선순위 순으로 시도한다 |
| `ask` | 기다리고 `claim.ask`를 단다. 사람이 결정한다 |
| `warn` | 둘 다 진행한다. `checkout.acquired.overlaps`에 남는다 |
| `fail` | 시작이면 그 노드가 `failed`로 끝난다. 수정 직전이면 실행을 멈추고 `failed`로 끝낸다(`pauseRequested.fail`) |

- 정책은 **요청하는 쪽**의 것이다(claim에 적은 값 → 노드 설정). `pauseMode`는 **점유한 쪽** 항목의 것이다. 충돌이 여럿이면 가장 엄격한 결정을 쓴다: fail > ask > wait > 선점 > warn.
- **교착:** 기다리게 될 요청이 점유자들의 대기 사슬을 따라 자기에게 돌아오면(넘겨받은 항목은 그 티켓의 대기 중인 모든 레인으로 본다) 정책과 상관없이 `ask` + `deadlock`이다.
- **사람의 결정:** claim을 기다리는 레인을 사람(system이 아닌 주체)이 `node.resume`하면 `override`가 붙는다. 그 실행은 끝날 때까지 claim과 체크아웃의 겹침을 경고로 허용한다(사람이 가라고 했으니 다시 기다리게 하지 않는다).
- 같은 실행의 기존 항목이 덮는 요청은 새로 기록하지 않는다. 같은 티켓이 넘겨받은 항목은 그 티켓의 다른 노드를 막지 않는다. 공유 claim끼리는 겹쳐도 된다.
- 패턴끼리의 겹침 판정은 보수적이다(글자 접두사가 겹치면 겹친다고 본다). 실제 파일과 패턴은 정확히 맞춘다.

### 14.4 명령

| 명령 | 범위 | 노드 에이전트 | 이벤트 |
|---|---|---|---|
| `project.configure` | project | 거부 | `project.configured`(있는 필드만 바꿈, `null`은 지움) |
| `app.configure` | app | 거부 | `app.configured`(앱 층 전체 교체, 집계 `settings:app`) |
| `ticket.create`/`update` + `priority?` | | 거부 | `ticket.created`(+`priority`, `workspace` 고정)/`ticket.updated` |
| `checkout.acquire` | node | **자기 실행만** | `checkout.acquired` 또는 `checkout.blocked`(+자기 레인의 `node.pauseRequested`) |
| `checkout.release` | node | 자기 실행만 | `checkout.released`(`manual`, 자기 `checkout` 항목만. claim은 노드와 함께 끝난다) |
| `checkout.forceRelease` | project | 거부 | `checkout.released`(`manual`, 사람이 id로) |
| `workspace.record` | project | 엔진 전용 | 엔진의 기록: 해제·넘겨받기·pauseHash·재개·변경·기준선·worktree |
| `node.start` | | 엔진 전용 | claim이 막으면 `node.started` 대신 `node.paused`(`claim`)이나 `node.completed`(failed)와 `checkout.blocked`. 결과 `blocked`. worktree 모드 합류의 머지 단계도 노드 타입의 claim을 같은 방식으로 잡는다(검수 반영) |
| `node.finish` + `result.kind: merge` | | 엔진 전용 | 합류의 머지 결과(§14.6) |
| `worktree.cleanup` | project | 거부(**사람만**, 고정) | `worktree.cleanupApproved`(`key`, 보여 준 내용의 `fingerprint`). 엔진이 그대로일 때만 지운다(§14.6) |

- `checkout.acquire`: 실행 토큰이 정한 실행이 running이고 그 레인의 현재 실행이어야 한다(밀려나거나 끝난 실행은 `invariant_violated`, 정착한 실행의 토큰은 `unauthenticated`). 레인을 지정하면 두 단계 판정(§2)이다. 경로는 절대 경로 또는 작업 폴더 기준 상대 경로다. 패턴은 거부(`validation_failed`), 폴더 밖 경로는 기록하지 않고 허용(`outside`)한다. 결과 `{granted, decision: granted|overlap|outside|wait|fail|ask, reason?, conflicts?, paths?}`. 거부도 명령은 성공이고 이벤트가 남는다(Codex는 거부된 호출을 출력에 남기지 않으므로 거부 기록의 정본은 장부다).
- 같은 명령에 선택 필드·유니언 대안을 더하는 것은 버전을 유지한다(이전 payload가 그대로 유효하다. M2의 `ticket.create.template`와 같다).
- **이벤트 버전:** `node.started`는 v2(`executor`에 `merge` 추가). v1은 업캐스터(그대로 통과)로 읽는다. 그 밖의 티켓 이벤트에는 선택 필드만 더했다: `node.activated.workspace.reset`, `node.reviewRequested.merge`, `node.pauseRequested.claim`·`fail`, `node.paused.claim`, `node.resumed.override`, `ticket.created.priority`·`workspace`, `ticket.updated.priority`.
- **엔진의 `node.start` 요청 id에 티켓 revision이 들어간다.** claim을 기다리다 재개된 레인은 같은 실행·같은 시도로 다시 시작하므로, 저장된 "막힘" 응답을 멱등으로 돌려받지 않게 하려는 것이다. 머지 단계의 시작도 같다(검수 반영: 처음에는 머지 시작 id에 revision이 없었고, 머지 단계가 claim 판정 전에 시작됐다).
- `workspace.record`의 `op`: `release`, `retain`, `pause`, `resume`, `changes`, `baseline`, `worktreeCreated`, `worktreeRemoved`, `worktreeKept`(검수 반영. 같은 내용이면 다시 기록하지 않는다), `cleanupSkipped`.
- **사람 전용 명령(검수 반영, 고정 규칙):** 카탈로그 `access.humanOnly`. 디스크의 것을 지우는 명령(`worktree.cleanup`)은 `human` 주체만 한다. AI 주체와 엔진 자신은 `forbidden`.

### 14.5 엔진의 일 (`WorkspaceCoordinator`)

- **실행 전:** 공간을 정한다. worktree면 티켓 worktree(없으면 `baseRef` 또는 HEAD에서 `vuyro/<티켓>/ticket` 브랜치)와 레인 worktree(티켓 브랜치 끝에서 `vuyro/<티켓>/<노드>-<레인>`)를 만든다. 레인을 새로 시작하는 실행(`node.activated.workspace.reset`, `rerun`)은 **새 세대의 worktree**(`<노드>-<레인>.r<실행>`, 새 폴더·새 브랜치)를 티켓 브랜치 끝에서 만들고, 그 뒤 실행들도 거기서 일한다. 세대는 이벤트에서 계산한다(레인의 그 실행까지 마지막으로 새로 시작한 실행). 이미 있는 worktree는 빨리 감기만 시도한다(겹치는 변경이 있으면 git이 거부한다). 그다음 `start` 검사(그 전에 생긴 변경은 이 실행의 것이 아니다), 멈췄다 재개하는 실행이면 pauseHash와 지금 해시를 비교해 프롬프트에 "멈춘 동안 바뀐 것"을 붙이고 `checkout.resumed`를 남긴다. 훅을 켤지 정한다.
- **실행 후(`node.finish` 전):** `finish` 검사를 하고, worktree면 엔진이 그 worktree의 자기 브랜치에 커밋한다(`--no-verify`, 저장소에 이름·이메일이 없으면 `Vuyro`). 머지 중인 worktree에는 커밋하지 않는다.
- **이벤트에 반응:** 프로젝트 장부를 티켓과 맞춘다. 끝난 실행의 항목은 해제(실행이 끝났으면 자기 해제 규칙, 밀려나거나 버려졌으면 `ended`), `ticketDone` 항목은 넘겨받기, 멈춘 점유자는 pauseHash, 만료는 `expired`(다음 만료 시각에 타이머), 막던 것이 모두 사라진 대기 레인은 재개, 머지된 레인 worktree와 끝난 티켓의 worktree는 제거한다.
- **엔진 시작:** 고아 실행 정착 뒤 모든 프로젝트를 맞추고(점유자가 이미 끝난 항목은 `recovered`), 기록이 있는 공간을 `startup` 검사한다.
- git·파일 작업은 프로젝트마다 하나씩 한다(worktree 명령이 저장소 파일을 함께 쓴다). 머지 에이전트를 기다리는 동안은 잡지 않는다.

**사후 검출**

- 후보: 읽기 전용 `git status --porcelain=v1 -z --untracked-files=all --no-renames`(GIT_OPTIONAL_LOCKS=0), 감시(@parcel/watcher) 후보, 전에 바뀐 것으로 기록된 경로(되돌린 파일), 장부의 체크아웃 경로. 감시 경로 설정으로 거른다.
- 판정은 SHA-256과 공간별 마지막 기록 해시의 비교다. 처음 본 경로는 git이 바뀌었다고 할 때(git이 없으면 감시가 알려 줬을 때), 또는 체크아웃의 `baseHash`와 다를 때 변경이다. 공간을 처음 볼 때는 기준선(`workspace.baselined`)만 남긴다.
- 귀속: 실행 중인 점유자의 배타 항목이 덮으면 `checkout`(그 점유자). 쥐고 있지만 실행 중이 아닌 점유자의 항목이 덮으면 `conflict`(다른 누가 바꿨다). 덮는 항목이 없으면, 레인 worktree이거나 엔진 worktree에 실행이 하나뿐이면 `worktree`(그 실행), 아니면 **`unattributed`**(그동안 그 공간에서 돈 실행을 `suspects`로). 엔진이 꺼져 있던 동안은 `startup` 검사로 잡는다.
- 레인 worktree의 변경은 레인별로 모은다. `overlapWarning`이면 다른 레인 worktree가 이미 바꾼 파일을 바꿀 때 `workspace.overlapWarned`를 쌍마다 한 번 남긴다.
- 감시가 없거나 끊겨도 `start`/`finish` 검사로 찾는다. git이 아닌 폴더는 감시 후보와 장부 경로만 본다(엔진이 꺼진 동안의 변경은 찾지 못한다).

### 14.6 worktree 모드의 합류 머지

- `nodeRun` 단위에서 레인 worktree를 쓰는 노드가 직접 들어오는 **합류 노드는 엔진의 머지 단계로 돈다**(바로 끝나지 않고 queued → `node.started` executor `merge` → `node.finish` kind `merge`). 합류의 켜짐·입력 규칙(§10.6)은 그대로다.
- 머지 단계: 입력 아이템의 lineage를 거슬러 레인 worktree를 쓰는 실행의 브랜치를 입력 순서대로 티켓 worktree에서 `git merge --no-ff`로 합친다. 이미 들어간 브랜치는 건너뛰어서 몇 번이고 다시 돌 수 있다(재시작, 사람이 푼 뒤).
- 결과(`MergeResult`): `merged` → 합류가 아이템을 넘긴다. 아이템마다 `artifacts.mergedBranch = {kind: git, uri: 티켓 브랜치, version: 커밋}`. `error` → 합류 failed.
- 충돌(`onMergeConflict`):
  - `fail`: 충돌하는 브랜치는 머지하지 않고 합류를 failed로 끝낸다(재시도 가능). (재검수 반영) 충돌은 `git merge-tree --write-tree`로 **worktree를 건드리지 않고** 미리 찾는다. 그래서 충돌하는 머지를 시작하지 않고, 되돌릴(`merge --abort`) 일도 없다.
  - `rerun`: 충돌하는 브랜치는 머지하지 않고(같은 미리 보기) 나머지는 합친다. 합류는 failed로 끝나고, 충돌한 레인을 `rework`(+`workspace.reset`, 의견)로 다시 켠다. 그 레인은 **새 worktree**(새 폴더·새 브랜치)에서 머지된 티켓 브랜치부터 다시 일한다. 옛 worktree와 브랜치는 그대로 남고(`worktree.kept`, `superseded`) 사람이 정리한다(D-042). 끝나면 합류가 다시 켜져 새 브랜치를 머지한다.
  - `ask`: 머지를 진행 중으로 두고 합류를 Review로 보낸다(`node.reviewRequested.merge`: worktree, 티켓 브랜치, 충돌 파일). **승인** = 사람이 풀었다 → 합류를 다시 돌려 머지를 마저 커밋하고 계속한다(충돌이 남았으면 다시 Review). **반려** = 의견을 지시로 에이전트에게 맡긴다.
  - `agent`: 진행 중인 머지를 에이전트(`mergeAgent`)가 그 worktree에서 푼다(`run.start` 엔진 전용, 실행 토큰은 그 합류 노드 범위). 충돌 표시와 미해결 파일이 없으면 `resolved` → Review(`resolvedBy: agent`, 사람이 승인해야 계속), 남았으면 `ask`와 같다.
  - `fail`·`rerun`인데 티켓 worktree에 충돌이 남은 머지가 진행 중이면(머지 도중 엔진이 멈췄거나, 미리 보기와 달리 충돌함) 엔진은 그것을 되돌리지 않는다. 합류를 오류(`error`, 그 폴더와 파일)로 끝내고, 사람이 그 자리에서 마무리하거나 직접 되돌린 뒤 재시도한다. 레인을 다시 돌리지 않는다(되풀이할 뿐이다).
  - 미리 보기에는 git 2.38 이상(`merge-tree --write-tree`)이 필요하다. 그보다 낮으면 머지 단계가 오류로 끝난다.
- **정리:** 티켓 브랜치에 들어간 레인 브랜치는 worktree와 함께 지운다(`merged`). 티켓이 끝나면 그 티켓의 worktree를 모두 지운다(`ticketDone`). **티켓 브랜치는 남긴다**(티켓의 결과다). 머지되지 않은 레인 브랜치도 남긴다. 실패한 레인의 worktree는 티켓이 끝날 때까지 남는다. 사람의 브랜치와 작업 폴더는 건드리지 않는다.
- **엔진은 스스로 파괴적인 git 조작을 하지 않는다(검수 반영, D-041·D-042).** `reset --hard`, `clean`, `worktree remove --force`를 엔진이 알아서 부르는 일은 없다.
  - 자동 정리는 그 worktree가 **아무것도 담고 있지 않을 때만** 한다: `git status --ignored`(`--untracked-files=all`)에 바뀐 파일, 추적하지 않는 파일, **무시되는 파일**이 하나도 없어야 한다. 그때도 `--force` 없이 지운다. 하나라도 있거나 읽을 수 없으면 지우지 않고 `worktree.kept`(바뀐 파일·무시 파일 목록 최대 1000개씩, 개수, 지우려던 이유, `reason`: `uncommitted`/`ignored`/`superseded`)를 남긴다. 레인 브랜치도 지우지 않는다.
  - 남긴 worktree는 그 티켓의 일이 진행될 때와 엔진 시작 때 다시 본다. 사람이 커밋해서 아무것도 남지 않으면 그때 지운다.
  - **사람의 정리:** `query.worktreeCleanup {projectId, ticketId?}`(CLI `vuyro workspace cleanup`)가 엔진이 쓰고 있지 않은 worktree마다 남은 것(무시 파일 포함, 각 200개까지)과 `fingerprint`(HEAD, 파일 목록, 각 파일의 SHA-256)를 보여 준다. 사람이 `worktree.cleanup {key, fingerprint}`(사람 전용)로 확인하면, 엔진은 다음 정리에서 지문을 다시 계산해 **같을 때만** `worktree remove --force`로 지운다(`worktree.removed`, `manual`). 그 사이 바뀌었으면 `worktree.cleanupSkipped`(`changed`), 쓰는 중이면 `inUse`로 남기고 지우지 않는다.
  - 처음 구현은 `--force`로 지웠다(QA 승인 대기 중 넣은 파일 손실). 1차 반영은 `git status`만 봐서 `.gitignore` 대상 파일을 지웠고, `rerun`은 레인 worktree를 `reset --hard`·`clean -fd`로 되감아 사람이 남긴 변경을 버렸다.
- 위치: 데이터 폴더 `wt/<티켓 키>/_ticket`, `wt/<티켓 키>/<노드>-<레인>`, 새 세대는 `wt/<티켓 키>/<노드>-<레인>.r<실행>`(티켓 키 = `t` + UUIDv7 끝 12자리, Windows 경로 길이 때문). `worktree` 모드는 프로젝트 폴더가 git 저장소일 때만 된다(아니면 노드가 이유와 함께 failed).

### 14.7 자동 체크아웃 훅

- 엔진이 실행마다 켤지 정하고(`AgentStartRequest.checkoutHook`), 어댑터가 공급자별 인자를 붙인다. 훅 명령은 `vuyro hook pretooluse --provider <p>`이고, 데몬 옵션 `vuyroCli`로 실행 방법을 받는다. 명령줄에는 경로와 고정 단어만 있다. 토큰은 환경 변수로 간다.
  - Claude: `--settings '{"hooks":{"PreToolUse":[{"matcher":"Write|Edit|MultiEdit|NotebookEdit", …}]}}'`.
  - Codex: `-c hooks.PreToolUse=[{matcher="apply_patch", hooks=[{type="command", command=…, commandWindows=…}]}]`. **셸이 다르다(M7a 실측):** Claude는 훅을 Git Bash로, Codex는 `commandWindows`를 Windows PowerShell로 돌린다. 그래서 `command`는 POSIX 모양(공백 등이 있는 부분만 작은따옴표), `commandWindows`는 `& '<node>' '<bin.js>' hook pretooluse --provider codex`(호출 연산자 + 작은따옴표)다. 따옴표 경로로 시작하는 줄은 PowerShell 문법 오류이고, Codex는 뜨지 못한 훅을 통과시킨다(L-20). + `--ignore-user-config` + `-c windows.sandbox="<사용자 값, 없으면 unelevated>"` + `--dangerously-bypass-hook-trust`. 작업 폴더에 Codex 프로젝트 훅(`.codex/hooks.json`, `.codex/config.toml`의 hooks)이 있거나 **사용자 `CODEX_HOME/hooks.json`에 훅이 있으면**(`--ignore-user-config`로도 읽힌다) 훅을 넣지 않고 실행에 경고를 남긴다(D-031, 검수 반영). 사용자 쪽 검사는 엔진과 어댑터가 둘 다 한다. 실측과 남는 위험은 [[초기 검증 결과]] "M4 검수 반영".
- `vuyro hook pretooluse`는 stdin의 도구 호출에서 파일을 읽고(Claude `file_path`/`notebook_path`, Codex 패치의 `Add/Update/Delete File`·`Move to`) `checkout.acquire`(`source: hook`)를 보낸다. 허용이면 아무것도 출력하지 않고, 거부면 JSON `deny`와 이유를 낸다. **언제나 exit 0이고, 어떤 실패(입력 해석 실패, 파일을 알 수 없음, 실행 토큰 없음, 엔진에 닿지 못함, 잘못된 인자)도 deny다.** 파일 도구가 아닌 호출(셸 등)은 그냥 통과시킨다. 셸로 고친 것은 사후 검출이 잡는다.
- 에이전트가 스스로 잡을 때는 `vuyro checkout <파일>…`(셸) 또는 MCP 도구 `vuyro_checkout`(Codex)를 쓴다.

### 14.8 조회

- `query.workspace {projectId, ticketId?, changes?: flagged|all, limit?}` → `{checkouts, blocks, changes, overlaps, worktrees}`. 기본은 표시할 변경(`unattributed`, `conflict`)만. CLI `vuyro workspace show`.
- `query.worktreeCleanup {projectId, ticketId?}` → `{worktrees: [{key, ticketId, scope, nodeId?, lane?, path, branch, merged, files, count, ignored, ignoredCount, fingerprint}]}`. 엔진이 디스크를 읽어 답한다. CLI `vuyro workspace cleanup --project <id>`(보기), `--remove <key> --fingerprint <fp>`(지우기, 결과를 기다림).
- 조회 테이블(projector `workspace` v3. `p_worktrees`에 남김(`kept_*`)과 사람의 정리(`cleanup_approved_at`, `cleanup_skipped_*`) 열을 더했다): `p_checkouts`, `p_checkout_blocks`, `p_workspace_changes`, `p_overlap_warnings`, `p_worktrees`. `p_projects`에 폴더·설정(projects v2), `p_app_settings`. `p_node_lanes.waiting_for`(nodes v4)는 claim을 기다리는 이유다(누가 어느 경로를 쥐었나).

### 14.9 엔진이 부르는 git 조작 전수 목록 (재검수 반영, D-042)

> 원칙: **엔진은 스스로 작업을 버리는 git 조작을 하지 않는다.** 모든 git 호출은 `workspace/git.ts`의 `GitClient` 한 곳에 있고, 셸 없이 인자 목록으로 실행한다. `test/workspace-git.test.ts`가 그 파일의 인자에 `reset`·`clean`·`stash`·`push`·`restore`·`checkout`·`switch`·`--abort`·`-D`·`-f`·`--hard`가 없고, `--force`는 사람 확인 경로 한 곳뿐이며, 조율기가 git을 직접 부르지 않는 것을 검사한다.

| 조작 | 부르는 곳 | 왜 작업을 잃지 않는가 |
|---|---|---|
| `status`, `rev-parse`, `merge-base --is-ancestor`, `diff --name-only`, `worktree list`, `var` | 사후 검출, 상태 판정 | 읽기 전용. `GIT_OPTIONAL_LOCKS=0`이라 인덱스도 쓰지 않는다 |
| `status --ignored` | 정리 전 내용 확인, 지문 | 읽기 전용 |
| `merge-tree --write-tree` | `fail`·`rerun` 머지 전 충돌 미리 보기 | worktree와 인덱스를 건드리지 않는다(객체만 쓴다) |
| `worktree add`(`-b` 새 브랜치 또는 기존 브랜치) | 티켓·레인 worktree 만들기 | 새 폴더를 만든다. 이미 있는 폴더면 git이 거부한다. 새 세대는 새 이름이다 |
| `worktree prune` | `worktree add`가 실패했을 때 한 번 | 폴더가 이미 없는 worktree의 등록 정보만 지운다(파일 없음) |
| `worktree remove`(`--force` 없음) | 자동 정리 | `status --ignored`에 아무것도 없을 때만 부른다. 그래도 바뀐·추적 안 하는 파일이 있으면 git이 거부한다 |
| `worktree remove --force` | 사람의 정리(`worktree.cleanup`) | 사람만 보낼 수 있고, 보여 준 내용의 지문(HEAD, 파일 목록, 각 파일 SHA-256)이 지금과 같을 때만 부른다 |
| `update-ref -d refs/heads/<브랜치> <커밋>` | 머지된 레인 브랜치 지우기 | 티켓 브랜치에 들어간 것을 확인한 그 커밋을 아직 가리킬 때만 지운다(원자적 비교 후 삭제). 그 뒤 커밋이 생겼으면 git이 거부하고 브랜치는 남는다. `branch -D`는 쓰지 않는다 |
| `add --all` + `commit --no-verify` | 실행 뒤 엔진의 커밋, 머지 전 티켓 worktree 커밋 | 있는 것을 엔진 자기 브랜치에 기록한다. 버리는 것이 없다 |
| `commit --no-edit`(머지 마무리) | 사람·에이전트가 푼 머지 | 미해결 파일이 없을 때만. 기록할 뿐이다 |
| `merge --no-ff` | 합류 머지 | `fail`·`rerun`은 미리 보기가 깨끗할 때만 시작한다. `ask`·`agent`는 충돌을 진행 중으로 두고 사람·에이전트를 기다린다. 어느 쪽도 되돌리지 않는다. 로컬 변경을 덮어써야 하면 git이 시작하지 않는다 |
| `merge --ff-only` | 레인 worktree가 머지된 일을 받아 올 때 | 앞으로만 간다. 로컬 변경을 덮어써야 하면 git이 거부한다(결과는 무시하고 진행) |

- 쓰지 않는 것: `reset`(모든 형태), `clean`, `checkout -f`/`checkout --`/`restore`/`switch`, `stash`, `merge --abort`, `branch -D`, `push`(모든 형태), `worktree remove --force`(사람 확인 밖).
- 처음 구현과 1차 반영에는 `worktree remove --force`, `reset --hard` + `clean -fd`(rerun), `branch -D`, `merge --abort`(`fail`·`rerun` 충돌)가 있었다. 모두 없앴다.

## 15. 공유 노드 (M5)

> 코드: `packages/contracts/src/shared.ts`(이벤트·명령 필드), `packages/engine/src/shared/`(상태 접기 `state.ts`, 원인 추정 `blame.ts`, 엔진 쪽 실행 `scheduler.ts`), 핸들러 `commands/shared-handlers.ts`, 스크립트 실행기 `workflow/script-runner.ts`(스크립트 노드와 공유). 설계는 [[공유·권한·BlackBoard 설계]] §4, 기획 기본값은 [[결정 대기]] D-043~D-055.

### 15.1 모양

- **공유 노드는 프로젝트의 집계다:** `shared:<projectId>:<name>`(타입 `shared`). 정의(`SharedNodeSpec`, 버전마다), 대기열, 실행 중인 묶음, Blocked 여부를 이벤트로 가진다. 정의는 `sharedNode.define`으로 이벤트에 담긴다(파일 정의·가져오기는 M6, D-043).
- **요청 노드는 티켓 쪽 노드다:** `completion: 'shared'`. 기본 타입 `vuyro.shared-request@1`(입력 `in`, 출력 `done`·`error`, 둘 다 선택 산출물 슬롯 `log`, param `sharedNode`). 요청 노드의 실행은 `queued`(대기열) → `running`(묶음 실행 중, `node.started.executor: 'shared'`) → `done`/`failed`다(설계 §4.6).
- **묶음 하나 = 노드 타입 한 번 실행.** 이 버전은 스크립트 노드 타입만 받는다(D-052). 스크립트는 스크립트 노드와 같은 실행기로 셸 없이, 최소 환경 변수로, **프로젝트 폴더에서** 돈다(보호 경로가 있는 그 폴더). 스크립트가 자기 `cwd`를 정하면 프로젝트 폴더 안(상대 경로, 또는 안을 가리키는 절대 경로)만 받고, 밖이면 프로그램을 띄우지 않고 실패한다. 띄우기 직전 `realpath`로 다시 본다: 정션·심볼릭 링크가 밖을 가리키거나 폴더가 없으면 실패한다(재검수 반영). 프로젝트 폴더가 없으면 `cwd`가 있어도 실패한다(엔진의 작업 폴더나 엉뚱한 폴더에서 빌드하지 않는다, 검수 반영).
- **한 프로젝트 폴더에서는 한 번에 한 묶음만 돈다(검수 반영, D-054).** shared 모드에서 묶음은 모두 같은 폴더를 빌드한다. **묶음을 시작할 때 강제한다(재검수 반영):** 프로젝트 장부에 폴더 잠금(`workspace.buildStarted`/`workspace.buildEnded`, `LedgerState.building`)을 두고, 묶음 시작과 같은 커밋에서 잡고 끝(성공·실패·중단)과 같은 커밋에서 푼다. 잠금을 쥔 묶음이 그 공유 노드에서 더는 실행 중이 아니면 낡은 잠금으로 보고 무시한다. 공유 노드 자신의 실행 중 묶음도 저장된 `maxConcurrent`와 무관하게 하나뿐이다. 정의 단계의 `maxConcurrent` 거부와 프로젝트의 공유 노드 목록(`project.sharedNodeAdded`, 같은 정의를 다시 저장해도 등록)은 보조일 뿐이고, 처음 구현은 그 둘에만 기대어 이미 저장된 정의(`maxConcurrent: 2`, 목록에 없음)에는 적용되지 않았다.

### 15.2 저장 검사

- 요청 노드 타입: 출력 `done`·`error` 필수, 필수 문자열 param `sharedNode`, `prompt`·`script`·`claims` 없음(보호는 공유 노드의 `protect`). 템플릿의 `sharedNode` 값은 표현식이 아닌 이름이어야 한다(타입의 스키마가 허용해도 거부).
- `sharedNode.define`: 프로젝트가 있고 노드 타입이 활성이어야 하며, 그 해시를 정의에 고정한다(`nodeType: {type, version, hash}`). 묶음을 시작할 때와 끝낼 때 고정된 해시로 다시 읽는다(파일이 바뀌면 fail closed). param 스키마, `requestSchema`, `protect` 경로(`..` 금지), 표현식 루트(`nodes.<id>` 없음)를 본다. 받지만 아직 하지 않는 것은 결과 `warnings`로 알린다: `schedule`, `expediteOnPriority`, 자동 조건이 하나도 없음, `protect`의 `ttl`(무시한다. 묶음이 끝날 때 놓는다). 말과 다르게 돌 것은 거부한다(`validation_failed`, 검수 반영): `onBatchFailure: ask|bisect|agent`(D-047), `maxConcurrent` 2 이상(D-054). 같은 내용이면 새 버전을 만들지 않는다.

### 15.3 흐름

1. **대기열에 넣기(`sharedNode.enqueue`, 엔진 전용):** 엔진이 `queued`인 요청 노드 실행마다 보낸다(요청 id에 티켓 revision). 핸들러는 티켓의 프로젝트, 요청 노드인지, 이름(`sharedNode` param), 레인의 현재 실행, 상태 `queued`를 확인한다. 이미 대기열이나 실행 중인 묶음에 있으면 아무것도 하지 않는다. **들어줄 수 없는 요청은 그 요청 노드를 error 포트로 끝낸다:** 공유 노드가 정의되지 않음, worktree 모드 티켓(통합 브랜치 머지는 MVP 이후, D-051), `requestSchema` 불일치(issues 포함). 같은 레인의 옛 실행 항목은 새 항목으로 바뀐다(`replaces`).
2. **묶음 시작(`sharedNode.start` 엔진 전용, `sharedNode.run` 사람):**
   - 막혀 있으면(Blocked) 시작하지 않는다. 실행 중인 묶음이 `maxConcurrent` 이상이거나, 같은 프로젝트의 다른 공유 노드 묶음이 돌고 있어도 마찬가지다. 사람의 `run`에는 이유를 담은 `invariant_violated`.
   - 대기열을 앞에서부터 본다. 실행이 끝났거나 바뀐 요청은 `sharedNode.requestDropped`로 뺀다. 일시정지된 요청과, 지금 열 수 없는 티켓(정의 파일 변경 등)의 요청은 자리를 지키되 이번 묶음에 넣지 않는다.
   - 조건(D-045): `retry`(실패·중단된 묶음에서 돌아온 요청이 있으면 곧바로) → `count`(대기 요청 수) → `afterPrevious`(실행 중인 묶음이 없으면) → `window`(가장 오래된 요청이 들어온 뒤 그 시간이 지나면. 아니면 결과 `nextCheckAt`) 순으로 먼저 맞는 것. 사람의 `run`은 `manual`. 조건이 맞으면 **대기 중인 요청 전부**(최대 4096)가 묶음이 된다.
   - 보호 경로(`protect`): 프로젝트 폴더(공간 `root`)에 공유 claim으로 잡는다. `ttl`은 쓰지 않는다(긴 빌드 도중 보호가 풀리지 않게, 검수 반영). **멤버 실행마다 같은 항목을 가진다**(한 멤버가 밀려나도 나머지가 쥐고 있다). 판정은 §14.3과 같다(정책은 프로젝트 층의 `onConflict`, claim에 적은 값이 우선). 다만 멤버 티켓이 쥔 항목(자기 실행, 넘겨받은 `ticketDone` 항목)은 막지 않고, 묶음은 실행 중인 에이전트를 선점하지 않는다(D-050). 기다릴 때는 `sharedNode.waiting`을 충돌이 바뀔 때만 남기고, 엔진이 경로가 풀릴 때(`checkout.released`) 다시 묻는다. `fail` 정책이면 멤버 요청이 모두 error로 끝난다. 사람의 `run`은 겹침을 허용하고 `batchStarted.overlaps`에 남긴다(D-033과 같은 생각).
   - 같은 커밋: 공유 노드에 `sharedNode.batchStarted`(번호, `batchId = <이름>-<번호>`, 멤버, 조건, 정의 버전, 보호 항목 id), 장부에 `checkout.acquired`, 멤버 티켓마다 `node.started`(v3, `executor: 'shared'`, `batch`).
3. **실행(엔진):** 묶음이 시작되면 엔진이 노드 타입을 한 번 돌린다. 표현식이 보는 것: `inputs.<입력 포트>` = 모든 요청의 입력 아이템(각각 `ticket {id, title}`, `request {nodeId, lane, run, item}` 포함), `input` = 첫 아이템, `params`, `node {id: 공유 노드 이름, batch, batchId, sharedNode, tickets}`. 출력 전체는 데이터 폴더 `logs/shared/<project>/<name>/<batchId>.log`에 쓰고 모든 티켓의 `log` 산출물로 건다.
4. **끝(`sharedNode.finish`, 엔진 전용):** 종료 코드 → 포트는 스크립트 노드와 같다(`exitPorts`, `output: json`). 같은 커밋에서 보호 항목을 놓고(`checkout.released`, `nodeDone`) 아직 그 묶음을 기다리는 멤버(실행 중, 같은 묶음)마다 결과를 나눠 준다. 밀려난 멤버는 아무것도 받지 않는다.
   - **성공:** 멤버마다 `done` 아이템 하나: `data = {스크립트 JSON의 data…, batchId, batch: [티켓 id], errorsForThisTicket: [], exitCode}`, `summary`, `artifacts.log`. 요청 노드의 포트 스키마에 맞지 않으면 그 멤버만 실패로 끝난다.
   - **실패, `blame`(D-046):** 오류 줄(단어 `error`/`fatal error`. `0 error(s)`·`4 errors` 같은 요약과 경고 제외)에서 줄 번호가 붙은 파일을 찾는다(MSVC `a.cpp(12):`, gcc/clang `a.c:7:1:`, TypeScript `a.ts(12,5):`). 절대 경로는 프로젝트 폴더 안만 센다. 공백이 든 절대 경로(`D:\Other Project\src\a.cpp(3)`)는 공백 뒤만 상대 경로로 읽지 않고 앞의 폴더를 붙여 절대 경로로 판정한다(검수 반영). 스크립트가 JSON 결과 `data.errorFiles`로 직접 알려 주면 그것을 쓴다. 그 파일들을 장부의 **편집 이력**(배타 체크아웃, 체크아웃으로 귀속된 변경. 항목이 풀린 뒤에도 남는다, `LedgerState.edits`. 공간마다 최근에 고친 경로 1만 개, 경로마다 최근 티켓 32개)과 대조해 그 파일을 고친 **멤버 티켓 전부**를 원인으로 본다. 없으면 그 파일을 덮는 배타 claim을 잡았던 멤버 티켓(`LedgerState.claimed`). 원인 멤버는 error 포트로(`errorsForThisTicket` = 그 티켓 파일을 가리킨 오류 줄, `errorFiles`, `blamedBy: edit|claim`), 나머지는 `node.requeued`로 `queued`가 되어 **대기열 맨 앞으로** 돌아간다(`retry`, 처음 들어온 시각 유지). 공유 노드는 `sharedNode.blocked {reason: 'blamed', by: 원인 레인}`. `raiseBlamedPriority`면 원인 티켓 우선순위를 묶음 최고값 + 1로 올린다(D-053).
   - **실패, `allFail`, 또는 원인을 못 찾은 `blame`:** 모든 멤버가 error 포트로(모든 오류 줄, 원인 미상이면 `blamedBy: 'none'`). 막지 않는다.
   - **중단(`result.kind: interrupted`):** 결과를 모른다. 멤버는 대기열 맨 앞으로, 공유 노드는 `blocked {reason: 'interrupted'}`. 사람이 풀면 같은 멤버로 다시 돈다(D-049).
5. **풀림(`sharedNode.unblocked`):** `blamed`는 막은 레인이 **더 새 실행으로** 대기열에 다시 들어와 모두 돌아왔을 때(`fixed`, 그 `enqueue` 커밋에서). 사람의 `sharedNode.unblock`(`person`)은 언제나. 다른 레인이나 다른 요청 노드로 돌아오면 풀리지 않는다(D-048). 막혀 있는 동안 새 요청은 대기열에 쌓이기만 한다.

### 15.4 명령과 이벤트

| 명령 | 범위 | 노드 에이전트 | 이벤트 |
|---|---|---|---|
| `sharedNode.define` | project | 거부 | `sharedNode.defined`(버전, spec, 고정한 노드 타입), 처음이면 프로젝트에 `project.sharedNodeAdded` |
| `sharedNode.run` | project | 거부 | (시작하면) `sharedNode.batchStarted` + 장부 + 멤버 `node.started`. 결과 `{started, batch?, reason?}` |
| `sharedNode.unblock` | project | 거부 | `sharedNode.unblocked`(`person`) |
| `sharedNode.enqueue` | node | 엔진 전용 | `sharedNode.requestQueued`(+`unblocked: fixed`), 또는 요청 노드의 `node.completed`(error) |
| `sharedNode.start` | project | 엔진 전용 | `run`과 같음. 조건이 안 맞으면 이벤트 없음(`nextCheckAt`), 보호 경로 대기면 `sharedNode.waiting` + `checkout.blocked` |
| `sharedNode.finish` | project | 엔진 전용 | `sharedNode.batchFinished`(성공·실패·중단, 멤버 분류, `errorFiles`, `log`) + 멤버 티켓의 완료·재대기 + `sharedNode.blocked` + `checkout.released` |

- **이벤트 버전:** `node.started` v3(`executor`에 `shared`, 선택 `batch`). v1·v2는 업캐스터(그대로 통과)로 읽는다. 그 밖에는 새 이벤트뿐이다.
- 조회 `query.sharedNodes {projectId, name?}` → 공유 노드마다 `{name, label, version, spec, status: idle|running|blocked|waiting, blocked?, queue[{…, position, queuedAt, retry}], running[], recent[](최근 20개)}`. 조회 테이블 `p_shared_nodes`(projector `shared` v1)는 목록과 개수만 두고, 나머지는 집계를 접어서 답한다. CLI `vuyro shared define|show|run|unblock`.

### 15.5 엔진의 일 (`SharedNodeScheduler`)

- **엔진 데몬 안에서 돈다.** 데몬은 앱과 따로 떠 있으므로(detached, §11) 창을 닫아도 대기열과 묶음은 계속된다. M6 트레이 상주는 이 데몬에 붙기만 한다.
- 공유 노드 이벤트, 같은 프로젝트의 `sharedNode.batchFinished`(대기열이 있는 공유 노드: 폴더가 비었다), 프로젝트의 `checkout.released`(보호 경로를 기다리는 공유 노드만), 대기열에 있는 요청의 `node.resumed`가 오면 그 공유 노드를 다시 본다: 시작된 묶음이 이 프로세스에서 돌지 않았으면 돌리고, 막히지 않았고 대기열이 있고 자리가 있으면 `sharedNode.start`를 보낸다. `window`는 `nextCheckAt`에 타이머를 건다.
- **`start`의 요청 id는 시도마다 새로 만든다.** 답이 티켓·장부·시계에 달려 있어서, 같은 id면 앞선 "아직 아님"이 멱등 재생된다(시험이 찾은 결함: 일시정지에서 돌아온 요청이 묶음을 시작시키지 못했다). 크래시 뒤 다시 보내도 상태(이미 시작된 묶음)로 다시 판정하므로 안전하다. `finish`의 id는 (공유 노드, 묶음)이다.
- **한 묶음은 한 엔진에서 한 번만 돈다.** 결과 기록(`finish`)이 실패하면 스크립트를 다시 돌리지 않고 `interrupted`로 마감한다(부작용이 있을 수 있다, D-011). 처음 구현은 기록이 거부되면 같은 묶음을 다시 띄웠다(시험이 찾았다).
- **엔진 시작:** 고아 실행 정착 → 장부 복구 → 앞선 엔진이 남긴 실행 중 묶음을 `interrupted`로 마감 → 모든 공유 노드를 다시 본다(대기열과 `window` 타이머가 이어진다).
- **엔진 멈춤(`cancelRunning`):** 도는 묶음을 죽이고 `interrupted`로 기록한다(실패가 아니다).

## 16. 데스크톱 앱 (M6a)

> 코드: `apps/desktop/src/main/`(Electron main), `src/preload/preload.cts`, `src/shared/bridge.ts`(main·렌더러 공용 타입), `src/renderer/`(React). 시험 `apps/desktop/test/{main,renderer}`.

**연결 (`EngineConnection`, Electron 없이 시험한다)**

1. 앱이 UI 자격(`vuc_` + 32바이트)을 만들어 **main 프로세스 메모리에만** 둔다. 파일·인자·환경 변수·렌더러에는 가지 않는다.
2. 그 자격으로 붙는다. 엔진이 없으면 `launchEngineDaemon`으로 띄우고 stdin으로 자격을 넘긴 뒤 다시 붙는다. 엔진은 앱의 Electron이 아니라 **별도 Node**로 돈다(`nodePath`: `VUYRO_NODE` 또는 PATH의 `node`. 설치본은 M7에서 Node를 함께 넣는다). `--vuyro-cli`로 앱 옆 `@vuyro/cli`의 `bin.js`를 넘긴다.
3. 엔진이 떠 있는데 자격을 모르면(터미널에서 띄움, 앱 없이 재시작) **읽기 전용**으로 붙는다. 사람이 배너의 [권한 연결]을 누를 때만 `auth.pair {kind: 'ui'}`를 보낸다. 엔진의 대화 상자와 앱 배너에 같은 코드가 보인다. 자동으로 짝을 청하지 않는다(트레이에 있는 동안 대화 상자가 불쑥 뜨지 않게).
4. 연결이 끊기면 0.5·1·2·5초 간격으로 다시 붙는다. 연결은 살아 있는데 구독 시작만 실패하면 그 구독을 같은 간격으로 다시 시도한다(검수 반영). 엔진이 사라졌으면 같은 자격으로 다시 띄운다(앱이 떠 있는 동안 엔진은 떠 있어야 한다). **구독은 main이 이어 간다:** 구독마다 마지막으로 넘긴 sequence를 기억하고 새 연결에서 그 뒤부터 다시 구독한다. 화면은 다시 구독하지 않는다.
5. 3초마다 `engine.status`로 실행 중 수를 읽어 트레이에 보인다.

**렌더러 경계**

- `contextIsolation`, `sandbox`, `nodeIntegration: false`, `webviewTag: false`. 화면은 전용 스킴 `vuyro-app://ui/`로 읽는다(파일 경로 밖으로 못 나감, 응답 헤더에 CSP). CSP: `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'none'; …`(인라인 스크립트·네트워크 없음). 새 창·탐색·웹뷰·권한 요청은 모두 막는다.
- preload가 내놓는 것은 `window.vuyro`의 함수뿐이다: `request(method, params)`, `subscribe(afterSequence, onEvents)`, `connection()`, `onConnection()`, `pair()`, `retry()`. M6b에 파일·클립보드 셋(§17.4), M7b 검수 반영으로 프로젝트 폴더 둘(아래 "프로젝트 폴더")을 더해 열한 개다.
- main은 보낸 프레임이 앱 화면인지 확인하고, 메서드는 `RENDERER_METHODS`(조회, `command.execute`, `events.read`, `engine.status`)만 받는다. `session.hello`·`auth.pair`·`engine.shutdown`·구독 메서드는 main만 쓴다. 렌더러가 보낸 명령 봉투에 `auth`(실행 토큰)가 있으면 거부한다.
- 화면의 모든 변경은 `command.execute`로 간다(같은 명령 버스, 같은 이벤트 로그). 렌더러는 DB·파일을 만지지 않는다. 에이전트·사람이 쓴 글은 React 텍스트로만 그린다(`dangerouslySetInnerHTML`·`innerHTML`은 린트로 금지).
- 이벤트는 화면 상태를 직접 고치지 않고, 닿는 조회(TanStack Query 키)를 200 ms씩 모아 낡음으로 표시한다.

**오래된 화면의 결정 (M6a 검수 반영)**

- 사람 노드 명령(`node.done`의 사람 경로, `node.approve`, `node.reject`, `node.retry`, `node.pause`, `node.resume`)의 대상에 선택 필드 `run`(화면이 본 실행 번호)을 더했다. 명령이 고른 레인이 지금 다른 실행이면 `revision_conflict`(`details: {aggregateId, nodeId, lane, expectedRun, actualRun}`)로 거부하고 아무것도 기록하지 않는다. 예: 반려로 Spec이 다시 돌아 승인 노드가 2번째 실행을 기다리는데, 1번째를 보여 주던 다른 창이 승인을 누른 경우.
- 티켓의 `expectedRevision`을 쓰지 않은 이유: 티켓 revision은 다른 레인이 움직일 때마다 바뀐다. 병렬 Dev가 도는 동안의 승인이 정상인데도 거의 매번 거부된다. 결정의 대상은 "그 레인의 그 실행"이라 실행 번호로 비교한다.
- 앱은 모든 노드 명령에 `run`을 싣는다. 거부되면 티켓을 다시 읽고 "그 사이 다른 실행으로 바뀌어 반영하지 않았습니다"를 보인다. 노드 에이전트는 `run`을 보낼 필요가 없다(실행 토큰이 정한다). 선택 필드라 명령 버전은 그대로다(§6).

**공유 노드 (M6a 검수 반영):** 보드 위와 티켓 상세(그 티켓이 기다리거나 원인으로 지목된 것만)에 `query.sharedNodes`의 상태·Blocked 사유·원인 티켓(누르면 그 티켓을 연다)·대기 요청 수·최근 묶음과 [풀기](`sharedNode.unblock`, UI 세션만)를 보인다.

**IPC 보낸 쪽 (M6a 검수 반영):** main은 보낸 프레임이 창의 **주 프레임**(processId·routingId가 같음)이고 앱 화면을 보여 줄 때만 받는다. 하위 프레임·사라진 프레임은 거부한다.

**프로젝트 폴더 (M7b 검수 반영, D-072)**

- 화면은 경로를 보내지 않는다. `pickProjectFolder()`(`vuyro:pick-folder`)는 main이 폴더 대화 상자를 열고 고른 경로를 확인한다(절대 경로, 있음, 폴더임, git 저장소인지). **git 저장소 판단은 git에게 묻는다:** 엔진의 `isRepositoryTop`이 `git rev-parse --show-toplevel`(셸 없이, 읽기 전용)을 그 폴더에서 돌려 최상위 폴더가 그 폴더 자신일 때만 저장소로 본다(빈 `.git`, 다른 저장소 안의 하위 폴더, git 없음은 아님). 앱 main과 엔진이 같은 함수를 쓴다. 화면은 `{token, path, name, isGitRepo}`를 받는다. `path`는 보여 주기만 한다.
- `setProjectFolder(projectId, token, settings?)`(`vuyro:set-project-folder`)는 main이 토큰을 경로로 바꾸고 폴더를 다시 확인한 뒤(사라졌으면, 또는 `settings.workspaceMode: worktree`인데 git 저장소가 아니면 거부) `command.execute {type: 'project.configure', payload: {projectId, root, settings?}}`를 앱의 UI 세션으로 보낸다. 같은 명령 버스·같은 이벤트(`project.configured`, 주체 `human`·`via: ui`)다.
- 토큰(`vpf_` + 16바이트 16진수)은 main 메모리에만 있고, 고른 창(webContents)만, 한 번, 30분 안에 쓸 수 있다. 다른 창의 토큰은 거부하되 소모하지 않는다. 창이 닫히면 버리고, 16개를 넘으면 오래된 것부터 버린다.
- `checkRendererRequest`는 화면이 보낸 `project.configure`에 `root`가 있으면(경로든 `null`이든) 거부한다. 모드만 바꾸는 `project.configure {projectId, settings}`는 받는다(프로젝트 설정 층은 통째로 바뀌므로 화면은 기존 값을 합쳐 보낸다).
- `query.projects`의 행: `projectId`, `name`, `createdAt`, `root`, `baseRef`, `settings`(프로젝트 층), `rootIsGitRepo`(`isRepositoryTop`).
- **worktree 모드 검사 (마지막 다듬기, 최종 확인 반영):** ① 폴더와 함께 저장(`setProjectFolder`), ② 화면이 모드만 바꾸는 `project.configure {settings}`(main이 `query.projects`로 프로젝트 폴더를 읽어 확인, 엔진에 물을 수 없으면 엔진에 맡김), ③ **엔진의 `project.configure`**: 폴더나 설정을 건드리는 변경이면, 바뀐 뒤의 폴더와 **실효 모드**(앱 층 → 프로젝트 층)가 worktree일 때 폴더가 있고 git 저장소여야 한다(`validation_failed`), ④ **엔진의 `ticket.create`**: 고정할 설정(앱 → 프로젝트 → 템플릿 → 노드)으로 worktree에서 돌 노드가 하나라도 있으면 같은 조건. 앱 층에서 물려받은 worktree도 잡는다. CLI도 같은 규칙을 받는다. 티켓을 만든 뒤 폴더가 저장소가 아니게 되면 그 노드가 이유와 함께 실패한다(전과 같음).
- **git 환경:** 엔진의 모든 git 호출(`gitEnvironment`)은 저장소 위치를 바꾸는 상속 변수(`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_CEILING_DIRECTORIES`, `GIT_DISCOVERY_ACROSS_FILESYSTEM`, `GIT_NAMESPACE`, `GIT_PREFIX`, `GIT_IMPLICIT_WORK_TREE`; 이름 대소문자 무시)를 뺀다. 엔진은 늘 폴더(`cwd`)를 직접 지정한다.

**트레이와 종료**

- 사용자별 단일 인스턴스(`requestSingleInstanceLock`). 창을 닫으면 창만 없어지고 앱은 트레이에 남는다(처음 한 번 알림). 트레이 메뉴: 창 열기 / 실행 중 작업 N개 / 완전 종료.
- **완전 종료 = 앱과 엔진을 함께 멈춘다.** 실행 중 작업이 있거나, 엔진에 물어볼 수 없어 **개수를 모르면** 확인을 받는다(검수 반영). 엔진을 멈출 권한이 없으면(읽기 전용) 그렇게 알리고 앱만 끝낸다. 멈춘 에이전트는 엔진 규칙대로 취소로 기록되고 다음 시작 때 다시 줄을 선다(§11 "멈추기").
- **종료 중 재연결 금지 (M7b 검수 반영):** 사람이 확인하면(또는 확인이 필요 없으면) 엔진에 `engine.shutdown`을 보내기 **전에** `EngineConnection.beginQuit()`으로 종료 상태에 든다. 그 뒤로는 연결이 끊겨도 다시 붙지 않고(`retry()` 포함), 엔진을 띄우지 않는다. 엔진이 멈추며 응답보다 먼저 파이프를 닫으면 요청은 실패로 끝나고 "엔진을 멈추지 못했습니다" 안내가 떠 있는 동안에도 새 엔진이 뜨지 않는다. 종료 상태에 들기 전에 시작한 엔진 기동이 그 뒤에 끝나면, 그 엔진에 붙어 `engine.shutdown`을 보내고 닫는다. **붙지 못한 채 남은 자기 엔진**(기동은 성공했지만 연결이 실패)은 종료 상태에 들 때(시도가 진행 중이면 그 시도가 끝날 때) 한 번 더 붙어 `engine.shutdown`을 청한다. 그래도 아무 답이 없을 때만 **그 기동이 띄운 자식 프로세스의 핸들**(`launch`의 `stop()`, 숫자 pid가 아님. 이미 끝난 프로세스에는 아무것도 하지 않음)로 끝낸다(L-22). 앱은 이 정리와 진행 중인 시도가 끝날 때까지(최대 10초, `whenQuitSettled`) 기다린 뒤 종료한다(`quitForGood`의 `settleConnection`). [취소]하면 종료 상태에 들지 않는다. 시험: `engine-connection.test.ts` "quitting for good…", "a link lost after…", "an engine launch still on its way…", `tray.test.ts`.

### 17.2 내보내기 형식

- 노드 타입·템플릿 하나는 **정의 파일과 같은 봉투**(§10.1)다. 그래서 내보낸 파일 하나가 그대로 정의 파일이 될 수 있다. `checksum`을 다시 계산해 넣는다.
- 템플릿은 기본으로 **묶음**(`kind: bundle`)이다: `{vuyro, formatVersion: 1, kind: 'bundle', id, version, name, description?, author?, requires: {nodeTypes, credentials?}, content: <템플릿 봉투>, embedded: <노드 타입 봉투들>, checksum}`. 안의 봉투는 정의 파일 그대로라서(비밀값을 뺐을 때만 바뀐다) 같은 엔진에 다시 가져오면 "이미 있음"이 된다. 의존성은 묶음의 `requires.nodeTypes`(타입 → 버전, 한 타입의 여러 버전이면 가장 높은 것)다.
- **비밀값(D-062, 검수 반영, `src/workflow/secrets.ts`):** 세 겹으로 찾는다. ① 노드 타입이 `secret: true`로 선언한 파라미터(기본값과 모든 템플릿의 값, 정본), ② 스크립트 `env` 값(표현식뿐인 값 제외)과 이름이 비밀처럼 보이는 파라미터, ③ 정의 안 모든 글의 값 패턴(토큰 접두사 `sk-`·`ghp_`·`github_pat_`·`xox*`·`AKIA`·`Bearer`, 개인 키 블록, 32자 이상 무작위 문자열). 검사 대상은 **내보내는 문서 전체**다(M6b 재검수): 내용과 봉투 메타(이름·설명·작성자, `requires`의 자격증명 이름·노드 타입 버전 밖), 내장 노드 타입 모두. 묶음의 이름·설명·작성자는 검사를 마친 템플릿 것을 쓴다. 마지막으로 완성된 문서 전체를 다시 검사해 바꿀 수 없는 자리(id 등)에 토큰처럼 보이는 값이 남았으면 내보내기를 거부한다(fail closed). 찾은 글은 `${secret:<이름>}` 자리표시자로 바꾸고(글이 아닌 값은 뺌) 이름을 `requires.credentials`에 남긴다. 결과의 `redacted[]`는 위치(JSON 포인터), 사람 말, `reason`(`declared`·`env`·`name`·`pattern`), `looksLike`, `placeholder`를 준다. 앱은 목록을 보여 주고 사람이 확인해야 파일·클립보드로 내보낸다. 탐지는 완전하지 않다(L-16).
- 정본 형식에 없는 종류(`schema`, `permissionPreset`, `blackboardSpec`, `nodes`, `sharedNode`)는 아직 내보내지도 가져오지도 않는다.

### 17.3 가져오기 미리보기 (`previewImport`)

1. 글을 JSON으로 읽고, `vuyro: 'export'`·`formatVersion: 1`·종류(`nodeType`·`template`·`bundle`)를 본다. **권한 규칙(`permission…` 종류)은 언제나 거부한다**(AI가 자기 권한을 못 올린다는 고정 규칙, [[공유·권한·BlackBoard 설계]] §2.6). 다른 종류도 거부한다.
2. 봉투를 엄격 스키마로 검사한다(모르는 필드 거부 → 정의에 권한 같은 필드를 끼워 넣을 수 없다). 체크섬이 있으면 봉투마다·묶음 전체를 확인하고, 같은 항목이 두 번 있거나 묶음이 다른 템플릿을 담으면 막는다.
3. 항목마다 이 엔진의 버전과 비교한다: `new`(id 없음), `newVersion`(id 있음, 버전 없음), `same`(같은 버전 같은 해시 → 기본 건너뛰기), `conflict`(같은 버전 다른 내용 → **사람이 고를 때까지 막힘**).
4. 처리(`choices[key].action`): `add`, `skip`, `newVersion`(= "덮어쓰기". 버전은 바꿀 수 없으므로 그 id의 다음 빈 버전으로 저장, D-063), `newId`(새 id·이름. id 형식, 이미 있는 id, 파일 안 중복을 검사). 노드 타입을 새 id·버전으로 저장하면 같은 파일의 템플릿이 그것을 가리키게 고친다(`dependencies[].savedAs`).
5. 의존 노드 타입: `file`(파일에 있고 저장함), `installed`(이미 있음), `installedDifferent`(파일 것을 건너뛰어 이 엔진의 다른 내용이 돈다 → 화면 경고), `missing`(→ 템플릿을 저장하면 막힘).
6. **실행 내용:** 노드마다 완료 방식, 스크립트(프로그램·인자·폴더·환경 변수 이름·제한 시간), 에이전트 프롬프트(앞 1200자 + 길이), 템플릿 노드의 파라미터 값, claim 경로(쓰기/읽기), BlackBoard 읽기·쓰기, 사람 확인, 설정. 건너뛴 노드 타입은 이 엔진의 것을 보여 준다(실제로 돌 것). 템플릿은 그래프(`workflow`)도 준다.
7. 저장 명령 목록(`saves`: 노드 타입 먼저, 템플릿 나중)을 만들어 노드 타입은 컴파일, 템플릿은 그 노드 타입들로 컴파일해 본다. 바꾼 정의는 `checksum`을 뺀다.
8. **최종 저장 위치 전체 검사(검수 반영):** 새 id가 파일의 다른 항목이 저장될 id와 겹치거나, 두 항목이 같은 id@버전에 저장되면 막는다. 덮어쓰기(새 버전)는 이 엔진과 파일 안의 모든 버전보다 새 번호를 받는다.
9. `canSave`: 문서 문제도, **어느 항목의 문제도 없고**(건너뛸 항목의 문제 포함), 저장할 것이 있을 때만 true. `saves[].expect`는 미리보기가 약속한 것(`newId`: 그 id가 아직 없음, `newVersion`: 그 id의 가장 새 버전)이다.
10. 가져오는 글 속의 `${secret:…}` 자리표시자는 `credentials`에 더해 보인다.

### 17.4 앱

- **저장은 명령 하나다(검수 반영).** 앱은 사람이 실행 내용 확인 칸을 체크한 뒤에만 미리보기의 `saves`를 `definition.import {items: [{definition, expect?}]}`(UI 세션) **한 번**으로 보낸다. 엔진은 노드 타입 먼저, 템플릿은 같은 가져오기의 노드 타입으로 컴파일해 모두 한 커밋에 `definition.staged`로 올리거나, 하나라도 안 되면 아무것도 올리지 않는다(중복 항목, 체크섬, 같은 버전 다른 내용, `expect` 위반 = 미리보기 뒤 변경, 검사 실패). 그 뒤 앱은 각 버전이 활성이 될 때까지 `query.definitions`로 기다린다. `definition.activate`는 템플릿이 쓰는 노드 타입이 모두 활성일 때만 템플릿을 활성으로 만든다(노드 타입 파일을 못 쓰면 같은 가져오기의 템플릿도 버려짐). 거부되면 앱은 "그 사이 정의가 바뀌어 아무것도 저장하지 않았습니다"를 보이고 미리보기를 다시 받는다. 선택을 바꾸면 확인을 다시 받고, 새 미리보기가 오기 전에는 저장할 수 없다. 노드 에이전트는 저장 명령이 모두 거부된다(카탈로그 `nodeAgent: 'deny'`), 읽기 전용 연결도 거부된다.
- **파일과 클립보드(IPC):** 크기 제한은 모두 UTF-8 바이트다(재검수 반영). `vuyro:open-file`(main이 열기 대화 상자 → 일반 파일·4 MiB 이하만 읽어 `{name, text}`만 넘김. 경로는 화면에 가지 않는다), `vuyro:save-file {name, text}`(이름은 폴더·특수 문자를 뺀 파일 이름으로만 쓰고, 경로는 저장 대화 상자에서 사람이 고름), `vuyro:copy-text {text}`(Electron clipboard). 붙여넣기는 대화 상자의 글 상자(Ctrl+V)라 클립보드 읽기 IPC는 없다. 보낸 프레임 검사는 §16과 같다. `RENDERER_METHODS`에 위 조회 4개를 더했다.
- **그래프 캔버스(@xyflow/react):** 티켓의 고정된 워크플로를 단계 순서대로(템플릿 좌표, 없으면 정방향 간선의 최장 경로로 열을 나눔) 그리고, 레인 상태로 노드를 칠한다(이벤트 → 조회 무효화 → 다시 칠함). 반려 루프(`back`)는 아래로 도는 점선이다. 보기 전용이고 끌어 옮긴 위치는 저장하지 않는다. 처음 화면은 전체가 읽을 만한 크기(0.8배 이상)로 들어가면 전체, 아니면 0.8배로 지금 걸린 노드(선택 → 대기·완료가 아닌 첫 노드)를 가운데에 둔다. 템플릿 미리보기(템플릿 화면, 새 티켓 대화 상자, 가져오기 미리보기)도 같은 컴포넌트다.
- **노드 상세와 로그:** 노드를 누르면 그 노드의 사람 차례(승인·반려를 여기서도 보냄, 실행 번호 포함 §16), 시간·토큰·도구 호출, 실행 기록, 에이전트 실행별 로그. 로그는 처음에 그 실행의 마지막 1000개(`tail`)를 읽고, 그 실행의 이벤트가 오면 마지막 항목 뒤만 더 읽는다. 화면 메모리에는 최근 1000개만 두고(재검수 반영), 그 앞은 [처음부터 페이지로 보기]로 200개씩 다시 읽는다. 도구 시작과 끝을 한 줄(걸린 시간, 결과 첫 줄)로 묶고, 같은 메시지 id의 줄을 합친다. 화면에는 최근 200행만 그리고(요청하면 200행씩 더), 6줄·600자를 넘는 글은 접으며, 엔진이 자른 글은 요청할 때만 전체를 불러온다. 글은 모두 `PlainText`다.
- **보기와 선택:** 보드·그래프·템플릿 보기가 같은 선택 티켓을 쓴다(티켓 상세 서랍은 따로 열고 닫는다). 보기와 선택 티켓은 창을 닫았다 열어도 남는다(`localStorage`).
- **창을 다시 열 때 구독:** 새 창은 `engine.status`의 `lastSequence`를 읽고, 보이는 조회를 모두 다시 가져온 뒤, 그 sequence 다음부터 구독한다. 닫힌 동안의 일은 다시 가져온 상태에 있고, 그 뒤의 이벤트는 빠짐없이 온다(main의 연결 구독은 엔진 재연결에도 이어진다, §16). 시험: `engine-integration.test.ts` "work goes on while no window listens…", `m6b.test.tsx` "a window opened again…".

### 17.5 M6b 변이 시험 (가드 40개)

- 가져오기 검증(엔진 24개): 내보내기 파일 표시, 형식 버전, 가져올 수 있는 종류(권한 규칙 거부), 엄격 스키마, 체크섬, 파일 안 중복, 묶음과 템플릿의 id, 봉투와 내용의 id, 제공한 처리만, 충돌은 사람이 고름, 새 id 형식·이미 있음·파일 안 중복, 노드 타입·템플릿 컴파일, 누락 노드 타입, 문서 문제·항목 문제로 막기, 내보낼 때 `env`·비밀 기본값·비밀 파라미터 빼기, 다른 내용 설치본 표시, 새 id·버전을 따라가는 템플릿, 건너뛴 노드 타입은 설치본의 실행 내용. 로그 조회의 없는 실행.
