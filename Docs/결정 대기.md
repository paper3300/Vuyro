# 결정 대기

> 구현 중 생긴 기획 질문을 멈추지 않고 기본값으로 진행한 기록이다. 데모가 나오면 한꺼번에 확인한다.
> 형식: 질문 / 고른 기본값 / 이유 / 영향 범위. 확인이 끝난 항목은 결과를 적고 지우지 않는다.

## D-001. 다른 Windows 계정이나 원격에서 엔진에 접근해도 되는가 (M0, 2026-10-24 갱신)

- **질문:** 같은 PC의 다른 Windows 계정, 다른 PC, SSH로 들어온 세션에서 엔진(`vuyro` CLI 포함)을 쓸 수 있어야 하는가?
- **고른 기본값:** 엔진을 띄운 사용자만 명령을 보낼 수 있다. 엔진 토큰 파일(현재 사용자 전용 ACL)을 읽을 수 있는 프로세스만 인증에 성공한다.
- **이유:** MVP는 "내 로컬에서만 도는 앱"이다(PRD 비목표). 엔진 명령으로 에이전트를 실행할 수 있으므로 열어 둘 이유가 없다.
- **영향 범위:**
  - 같은 사용자라면 SSH 세션에서도 토큰 파일을 읽을 수 있으므로 CLI를 쓸 수 있다. 이전 방식의 "네트워크 로그온 거부"는 없어졌다.
  - 다른 계정은 파이프를 읽기 전용으로 열 수는 있지만 인증할 수 없다.
  - 같은 PC의 관리자는 기술적으로 막을 수 없다.
  - 근거와 시험 결과: [[초기 검증 결과]] #1

## D-002. Claude가 주는 금액을 화면에 보여줄 것인가 (M0b)

- **질문:** Claude CLI가 주는 금액(`total_cost_usd`)은 정가로 계산한 값(`costBasis: "list"`)이다. 구독 요금제에서는 실제로 청구된 금액이 아니다. 이 값을 보여줄 것인가?
- **고른 기본값:** 보조 정보로 보여주되 "정가 기준 추정"이라고 표시한다. 정렬·병목 판단에는 쓰지 않는다. Codex는 금액을 표시하지 않는다.
- **이유:** PRD는 "금액은 공급자가 실제 값을 줄 때만 보조로" 보여주라고 한다. API 키 사용자에게는 이 값이 실제 금액에 가깝고, 구독 사용자에게도 작업 크기를 비교하는 참고는 된다.
- **영향 범위:**
  - M1 이벤트 계약에 금액의 출처 필드(`basis`)가 들어간다.
  - M6 노드 상세 화면에 표시 문구가 들어간다.
  - 근거: [[초기 검증 결과]] M0b

## D-003. 터미널에서 `vuyro` CLI를 쓰는 사람은 누구로 보는가 (M1)

- **질문:** 실행 토큰 없이 `vuyro` CLI로 보낸 명령을 사람이 한 것으로 볼 것인가?
- **고른 기본값 (검수 반영, 2026-10-24 갱신):** 아니다. 실행 토큰도 사람 자격도 없는 CLI는 "확인되지 않은 로컬 클라이언트"(`unverified`)이고 **읽기 전용**이다. 티켓 만들기 같은 쓰기도 거부된다.
  - 사람이 터미널에서 쓰기를 하려면 사람 자격을 증명해야 한다.
  - (M3 갱신) 방법: `vuyro auth login`을 실행하면 엔진이 이 PC 화면에 확인 창을 띄운다. 사람이 "예"를 누르면 CLI 사람 자격이 나오고, 사람이 자기 터미널에 `VUYRO_HUMAN_CREDENTIAL`로 둔다. 8시간 뒤 만료된다(D-023).
- **이유:** 엔진 토큰 파일은 같은 사용자의 모든 프로세스가 읽을 수 있다. 에이전트도 실행 토큰을 버리고 CLI를 부르면 터미널의 사람과 구분할 수 없다. "AI는 자기 권한 규칙을 고칠 수 없다"를 지키려면 이 경로를 사람으로 볼 수 없다. 또 쓰기를 허용하면 "토큰을 넣으면 범위 밖, 빼면 허용"이 되어 노드 범위 제한이 무의미해진다(검수 지적).
- **영향 범위:**
  - 권한 규칙과 모든 쓰기는 앱 화면(또는 M3의 사람 자격을 받은 CLI)에서만 할 수 있다.
  - 사람 자격으로 CLI를 쓰면 작업 기록에 "사람(CLI)"으로 표시된다.
  - 근거: [[명령·이벤트 계약]] §3

## D-004. 권한 규칙은 엔진 자신도 바꿀 수 없게 할 것인가 (M1)

- **질문:** 권한 규칙 변경을 사람만 하게 할 것인가, 엔진 내부 동작(가져오기, 프리셋 적용 등)도 할 수 있게 할 것인가?
- **고른 기본값:** 사람만 한다. 엔진 내부 호출(`system`)도 거부한다. 프리셋 적용·가져오기는 사람이 화면에서 누른 명령으로 처리한다.
- **이유:** AI가 엔진 내부 동작을 유도해 우회하는 길을 처음부터 없앤다.
- **영향 범위:** M6 가져오기 화면에서 권한 프리셋이 들어 있으면 사람 확인이 따로 필요하다. 근거: [[명령·이벤트 계약]] §4

## D-005. 거부된 AI 동작도 작업 기록에 남길 것인가 (M1)

- **질문:** 권한 경계에서 거부된 명령을 기록할 것인가?
- **고른 기본값:** 남긴다. 거부(`forbidden`, `out_of_scope`)마다 `command.denied` 이벤트를 쓴다. 누가, 어떤 명령을, 어느 티켓·노드에, 왜 거부됐는지가 들어간다. 형식 오류나 토큰 오류는 남기지 않는다.
- **이유:** 설계 문서 §2.4 "모든 AI 동작은 작업 기록에 남는다". 에이전트가 범위 밖을 자주 건드리면 프롬프트나 노드 설정을 고쳐야 한다는 신호다.
- **영향 범위:** M6 노드 상세에 "거부된 시도" 표시를 넣을 수 있다. 이벤트 수가 늘어난다.

## D-006. 외부 MCP 클라이언트의 기본 권한 (M1)

- **질문:** 외부에서 Vuyro MCP로 붙은 클라이언트(`mcp.external`)가 무엇을 할 수 있는가?
- **고른 기본값:** 권한 정책이 들어오기 전까지 쓰기 명령은 모두 거부(읽기 전용)한다.
- **이유:** 설계 문서 §2.2의 기본 성향이 "읽기 전용"이다. MCP는 MVP 이후다.
- **영향 범위:** MCP를 붙일 때 권한 정책과 함께 연다.

## D-007. 병렬 작업 중 하나가 실패하면 나머지는 계속 가는가 (M2)

- **질문:** Plan이 나눈 Dev 작업 중 하나가 실패했을 때 합류(Join)와 QA를 계속 진행할 것인가, 전부 멈출 것인가?
- **고른 기본값:** 계속 간다. 합류는 성공한 레인의 결과만 모아 다음으로 넘긴다. 다만 **실패한 레인을 누가 다시 시도하거나 처리하기 전까지 티켓은 Done이 되지 않는다.** 재시도해서 성공하면 합류가 그 결과까지 넣어 다시 돈다.
- **이유:** Archon 분석 B9(팬아웃은 all_done)를 따른다. 한 작업 때문에 나머지 결과를 버리지 않는다. 대신 실패를 조용히 넘기지 않도록 티켓 완료를 막는다.
- **영향 범위:** QA가 일부 작업만 보고 판정할 수 있다. 템플릿이 error 포트를 다른 노드로 이어 두면 그 실패는 "처리된 것"으로 보고 티켓 완료를 막지 않는다.

## D-008. "Rejected" 상태는 무엇을 뜻하는가 (M2)

- **질문:** 노드 상태 Rejected를 반려한 노드(승인 노드)에 붙일 것인가, 반려당한 노드에 붙일 것인가?
- **고른 기본값:** **반려당해서 다시 해야 하는 노드**에 붙인다. 다시 시작되기 전까지 Rejected이고, 시작하면 Running이 된다. 에이전트 노드는 곧바로 다시 시작하므로 잠깐만 보이고, 사람 노드는 사람이 다시 끝낼 때까지 Rejected로 남는다. 반려한 승인 노드는 Done(나간 포트: reject)이다.
- **이유:** 칸반에서 "다시 해야 하는 일"을 바로 찾을 수 있다. 결과(승인/반려)와 상태를 나누는 Archon A5와도 맞다.
- **영향 범위:** M6 칸반·그래프의 상태 표시, 통계(반려 횟수 = rework/review로 시작된 실행 수).

## D-009. 기본 템플릿의 QA는 누가 판정하는가 (M2)

- **질문:** QA를 에이전트만, 사람만, 또는 둘 다로 할 것인가?
- **고른 기본값:** QA 에이전트가 판정(승인 또는 일부 작업 반려)하고, **사람이 그 판정을 확인**해야 다음으로 간다(노드의 리뷰 게이트 `review: human`). 사람이 QA 판정을 반려하면 QA가 의견을 받아 다시 돈다.
- **이유:** PRD의 기본 템플릿 그림이 "QA(agent+human)"이고, 설계 원칙이 "되돌릴 수 없는 판단은 기본적으로 사람이 확인"이다.
- **영향 범위:** 기본 템플릿 `vuyro/ai-sdlc@1`. 템플릿에서 `review`를 빼면 에이전트만으로 판정한다.

## D-010. 결과를 보고한 뒤 비정상 종료한 에이전트의 결과를 인정하는가 (M2)

- **질문:** 에이전트가 `vuyro node done`으로 결과를 낸 뒤 프로세스가 비정상 종료하면 그 노드를 성공으로 볼 것인가?
- **고른 기본값:** 인정한다. 보고한 결과로 노드를 끝내고, 실행 기록에는 비정상 종료가 그대로 남는다. 보고 없이 끝나면 실패다.
- **이유:** 노드 완료의 정본은 `vuyro` 명령이다([[기술 스택 결정]] §5). 결과를 낸 뒤의 종료 문제 때문에 다 한 일을 다시 하게 하지 않는다.
- **영향 범위:** 통계에서 "성공한 노드"와 "정상 종료한 실행"이 다를 수 있다.

## D-011. 엔진이 재시작되면 하던 일은 어떻게 되는가 (M2)

- **질문:** 앱(엔진)이 꺼졌다 켜지면 실행 중이던 에이전트와 스크립트를 어떻게 할 것인가?
- **고른 기본값:**
  - 에이전트: 자동으로 다시 시작한다(실행 하나에 최대 3번). 세션이 기록돼 있으면 그 세션을 이어서 한다.
  - 스크립트: 다시 돌리지 않고 실패로 끝낸다. 사람이 재시도할 수 있다.
- **이유:** 에이전트는 이어하기가 있고 같은 작업을 다시 해도 대체로 안전하다. 스크립트는 p4 submit 같은 부작용이 있을 수 있다(Archon 분석 B5).
- **영향 범위:** 비용(이어서 하는 실행의 토큰). M3에서 실제 CLI로 이어하기를 붙인다.

## D-012. 정의 파일을 직접 고치거나 넣으면 어떻게 되는가 (M2)

- **질문:** 사용자가 템플릿·노드 타입 JSON 파일을 편집기로 직접 고치거나, 새 파일을 폴더에 넣으면 바로 쓸 것인가?
- **고른 기본값:**
  - 고친 파일: **쓰지 않는다.** 등록된 내용과 해시가 다르면 그 버전은 쓸 수 없다고 알린다. 그 버전을 쓰는 진행 중 티켓도 멈춘다. 되돌리거나 새 버전으로 저장해야 한다.
  - 넣은 파일: 자동으로 등록하지 않는다. "미등록 파일"로 보여주고, 가져오기(M6)로 등록한다.
- **이유:** 티켓은 시작할 때 고정한 내용 그대로 돌아야 한다. 아무도 승인하지 않은 파일이 자동으로 실행되면(스크립트 명령, 에이전트 프롬프트) 권한 경계가 무너진다.
- **영향 범위:** git으로 `.vuyro/` 정의를 공유하는 경우, 받은 변경은 가져오기 화면을 거친다. M6 가져오기 화면에 미등록·변경 파일 목록이 들어간다.

## D-013. 동시에 몇 개의 에이전트·스크립트를 돌리는가 (M2)

- **질문:** 병렬 Dev처럼 여러 작업이 동시에 준비되면 몇 개까지 한꺼번에 돌릴 것인가?
- **고른 기본값:** 앱 전체에서 4개(에이전트와 스크립트 합계). 나머지는 Queued로 기다린다.
- **이유:** 토큰 사용과 PC 부하를 사용자가 예측할 수 있게 한다. 작은 데모 저장소에는 충분하다.
- **영향 범위:** 설정 화면(M6)에 이 값을 넣는다. 프로젝트·템플릿별 한도는 나중에.

## D-014. 실행 중인 노드에 새 입력이 오면 어떻게 하는가 (M2)

- **질문:** 노드가 실행 중인데 앞 노드가 다시 끝나 새 입력이 오면, 지금 실행을 끝까지 둘 것인가 새 입력으로 바꿀 것인가?
- **고른 기본값:** 새 입력으로 바꾼다. 지금 실행은 취소되고 "밀려남(superseded)"으로 남는다. 그 실행이 늦게 보고한 결과는 쓰지 않는다.
- **이유:** 낡은 입력으로 만든 결과가 다음 노드로 가는 것을 막는다.
- **영향 범위:** 취소된 실행이 쓴 토큰은 버려진다. Stale·변경 요청(MVP 이후)이 들어오면 "사람에게 먼저 묻기" 옵션을 검토한다.

## D-015. 일시정지는 누가, 언제 할 수 있는가 (M2)

- **질문:** 노드 일시정지를 AI도 할 수 있게 할 것인가, 실행 중인 스크립트도 멈출 수 있게 할 것인가?
- **고른 기본값:** 사람(과 패널 에이전트)만 한다. 노드 에이전트는 못 한다. 실행 중인 에이전트는 멈추면 취소하고 재개할 때 세션을 이어서 한다. 실행 중인 스크립트는 멈출 수 없다(끝나거나 제한 시간이 지날 때까지 기다린다).
- **이유:** 스크립트를 중간에 끊으면 외부 상태가 어중간하게 남을 수 있다.
- **영향 범위:** M4의 claim 대기(Paused)와 같은 상태값을 쓴다.

## D-016. 계획이 작업을 하나도 내지 않으면 어떻게 하는가 (M2 검수 반영)

- **질문:** Plan 같은 노드가 아이템 0개를 내면(나눌 작업이 없음) 그 뒤의 병렬 작업은 열리지 않는다. 티켓이 아무 복구 명령 없이 멈추지 않게 하려면 어떻게 할 것인가?
- **고른 기본값:**
  - 에이전트·스크립트가 다음 노드로 이어진 포트에 아이템 0개를 내면 그 노드를 **사람 확인(Review)** 으로 보내고 "아이템 0개" 사유를 남긴다.
  - 사람은 **반려(다시 실행, 의견 전달)** 나 **승인(팬아웃 건너뛰기)** 을 고른다. 건너뛰면 병렬 작업 노드는 레인 없이 지나가고, 합류와 그 뒤 노드(QA 등)는 아이템 0개로 돈다.
  - 사람이 사람 노드를 아이템 없이 끝내면 그 자체를 "건너뛰기"로 본다.
  - (재검수 반영) error 포트도 같다. 아이템이 있어도 간선 조건을 하나도 통과하지 못해 갈 곳이 없으면 같은 규칙을 쓴다. 승인한 빈 error 출력은 실패로 남지만 "처리된 실패"라서 티켓 완료를 막지 않는다.
- **이유:** 에이전트가 실수로 빈 계획을 냈는지, 정말 할 일이 없는지는 사람이 판단해야 한다. 어느 쪽이든 티켓이 막힌 채로 남지 않는다.
- **영향 범위:** M6 결정 인박스에 "아이템 0개" 카드가 생긴다. 건너뛰면 QA 에이전트가 빈 입력으로 한 번 돈다(토큰 사용).

## D-017. 새 계획이 나온 뒤 도착한 옛 반려는 어떻게 하는가 (M2 검수 반영)

- **질문:** QA가 옛 계획의 작업 하나를 반려했고 그것을 사람이 확인하기 전에 계획이 다시 나왔다(새 작업 묶음). 그 뒤에 옛 반려가 승인되면 무엇을 다시 할 것인가?
- **고른 기본값:** 아무것도 하지 않는다. 옛 작업을 가리키는 반려는 "낡음(stale)"으로 기록만 하고, 새 계획의 작업과 그 합류 결과는 그대로 둔다.
- **이유:** 옛 작업은 새 계획으로 바뀌었다. 옛 반려로 새 레인을 열면 새 계획의 결과가 합류에서 빠질 수 있다.
- **영향 범위:** 화면에 "반영되지 않은 반려"로 보여줄 수 있다(M6).

## D-018. 끝 노드에 닿지 않고 끝난 경로는 어떻게 보는가 (M2 재검수 반영)

- **질문:** 노드가 다음 간선이 하나도 없는 포트로 성공하면(예: 요약만 남기고 끝나는 작업) 그 경로는 끝 노드에 닿지 않는다. 다른 할 일이 없을 때 티켓을 끝낼 것인가?
- **고른 기본값:** 끝낸다. 간선 없는 포트로 성공한 것을 그 경로의 끝(암묵적 끝)으로 본다. 빈 전달이 더 갈 곳 없는 병렬 노드를 지나가는 경우도 같다. 활성 작업도, 처리되지 않은 실패도 없으면 티켓은 Done이다.
- **이유:** BPMN의 암묵적 끝과 같은 규칙이다. 이렇게 하지 않으면 할 일이 없는데도 티켓이 아무 이유 없이 열린 채로 남는다(속성 테스트가 찾은 반례).
- **영향 범위:** 템플릿 작성자가 간선을 빠뜨리면 그 경로에서 티켓이 일찍 끝날 수 있다. M6 그래프 편집기에서 "끝 노드가 아닌데 성공 포트에 간선이 없음"을 경고로 보여준다.

## D-019. 계획이 다시 나오면 옛 계획의 진행 중인 작업은 어떻게 하는가 (M2 재검수 반영)

- **질문:** Plan이 다시 돌아 새 작업 묶음(새 세대)을 냈을 때, 옛 묶음의 작업 중 아직 실행 중이거나 사람 확인(Review)을 기다리는 것을 계속 둘 것인가?
- **고른 기본값:** 둘 다 끝낸다. 새 묶음이 열리는 순간 옛 묶음의 진행 중·대기 중 작업은 "밀려남(superseded)"이 되고, 에이전트는 취소되며, 사람 확인 카드는 사라진다. 옛 묶음의 실패는 다시 시도할 수 없고 티켓 완료도 막지 않는다.
- **이유:**
  - 합류는 새 묶음의 결과만 모은다. 옛 작업을 계속 두면 결과는 버려지는데 토큰과 사람 시간만 쓴다.
  - 옛 작업이 살아 있으면 합류가 그것을 기다려 새 묶음이 다 끝나도 다음으로 가지 못했다(검수가 찾은 결함).
  - D-014(새 입력이 오면 실행 중인 것을 바꾼다), D-017(옛 작업에 대한 반려는 버린다)과 같은 방향이다.
- **(검수 반영) 옛 계획의 결과만 받은 후속 작업도 같다.** 예: 옛 합류 결과로 돌던 QA가 Review에서 기다리는 중에 계획이 다시 나오면 그 QA도 밀려난다. 새 계획의 결과가 다시 합류하면 QA가 새로 돈다. 입력 일부라도 현재 결과에 기대는 작업은 남긴다.
- **영향 범위:** 사람이 옛 작업을 검토하던 중이면 그 검토가 사라진다. M6 화면에 "새 계획으로 밀려남"을 보여줘야 한다. 나중에 "옛 작업을 살릴지 사람에게 묻기" 옵션을 정책으로 둘 수 있다.
- 근거: [[명령·이벤트 계약]] §10.6

## D-020. 반려가 고칠 작업과 새 작업을 함께 내면 어떻게 묶는가 (M2 재검수 반영)

- **질문:** QA가 기존 작업 일부를 반려하면서 새 작업도 하나 추가하면, 새 작업을 기존 묶음에 더할 것인가, 새 묶음(새 계획)으로 볼 것인가?
- **고른 기본값:** 기존 묶음에 더한다. 같은 전달에 기존 작업으로 이어지는 아이템이 하나라도 있으면 새 아이템은 현재 묶음의 새 레인이 된다. 기존 작업으로 이어지는 것이 하나도 없을 때만 새 묶음(새 계획)이다.
- **이유:** 새 묶음으로 보면 D-019에 따라 같은 반려로 다시 돌리던 작업이 곧바로 밀려난다. "고칠 것 + 추가할 것"은 계획을 바꾼 것이 아니라 고친 것이다.
- **영향 범위:** 합류는 기존 작업과 추가 작업의 결과를 함께 모은다. 계획을 통째로 바꾸려면 Plan을 다시 돌린다.
- 근거: [[명령·이벤트 계약]] §10.6 항목 5

## D-021. 낡은 결과만 낸 작업을 "끝"으로 볼 것인가 (M2 재검수 반영)

- **질문:** 노드의 출력 아이템이 모두 옛 계획의 작업을 가리켜(낡음, D-017) 아무 데도 가지 않았다. 이것을 그 경로가 끝난 것(암묵적 끝, D-018)으로 보고 티켓 완료를 허락할 것인가?
- **고른 기본값:** 아니다. 낡은 출력만으로는 현재 작업이 끝났다고 보지 않는다. 암묵적 끝은 간선이 없는 포트로 성공한 경우뿐이다. 티켓은 새 계획 쪽 경로가 끝나야 완료된다.
  - (재검수 반영) 옛 계획의 결과로 끝 노드가 이미 끝났더라도 재계획한 뒤에는 그 끝을 세지 않는다. 경로의 끝은 현재 계획의 결과로 끝난 것만 센다.
  - 그런 노드는 "반영되지 않은 결과"로 **대기 사유**가 되고, 사람이 다시 실행(재시도)하면 풀린다. 그렇지 않으면 할 일도 끝도 없이 티켓이 열린 채 남는다.
- **이유:** 낡은 출력은 현재 계획에 대해 아무것도 말하지 않는다. 그것을 끝으로 세면 새 계획의 일이 남아 있는데도(예: 새 레인이 실패한 채 error 간선으로 처리됨) 티켓이 닫힐 수 있다.
- **영향 범위:** 화면에는 "반영되지 않은 결과"로 보여준다(M6). 근거: [[명령·이벤트 계약]] §10.6 항목 13

## D-022. 엔진이 떠 있지 않을 때 `vuyro` CLI가 엔진을 띄울 것인가 (M3)

- **질문:** 엔진이 꺼져 있는데 `vuyro ticket list` 같은 명령을 치면 CLI가 엔진을 자동으로 띄울 것인가?
- **고른 기본값:** 띄우지 않는다. "엔진이 떠 있지 않다, `vuyro engine start`나 앱으로 띄우라"고 알리고 종료 코드 3으로 끝난다. 엔진은 앱이 띄우거나, 사람이 `vuyro engine start`로 명시적으로 띄운다.
- **이유:**
  - 앱이 엔진을 띄워야 앱이 엔진을 띄우면서 UI 자격을 바로 넘길 수 있다. CLI가 띄운 엔진에 앱이 붙으면 확인 창을 한 번 더 눌러야 한다(D-023).
  - 아무 명령이나 엔진을 띄우면, 의도하지 않은 때에 고아 실행 정리와 에이전트 재시작이 일어난다.
- **영향 범위:** 터미널만 쓰는 사람은 처음에 `vuyro engine start`를 한 번 쳐야 한다. 노드 에이전트는 엔진이 떠 있을 때만 돌므로 영향이 없다.

## D-023. 사람 자격을 어떻게 받는가 (M3)

- **질문:** 이미 떠 있는 엔진에 앱이나 터미널이 "나는 사람"이라고 증명하려면 어떻게 해야 하는가? 에이전트도 같은 사용자로 돌기 때문에 파일이나 환경 변수로는 구분할 수 없다.
- **고른 기본값:**
  - 앱이 엔진을 띄울 때는 자격을 바로 넘긴다(확인 없음).
  - 그 밖에는 엔진이 화면에 **확인 창**을 띄운다. 요청한 화면과 확인 창에 같은 4자리 코드가 보이고, 사람이 "예"를 눌러야 자격이 나온다. 기본 버튼은 "아니요"이고, 2분 안에 답이 없으면 거부다.
  - 앱 자격은 엔진이 멈출 때까지, 터미널(CLI) 자격은 **8시간** 유효하다.
  - 엔진이 재시작하면 모든 자격이 사라진다.
- **이유:** 실행 중인 엔진을 재시작하지 않고(작업이 끊기지 않게), 에이전트가 스스로 사람이 될 수 없게 하는 방법이다. 에이전트가 요청하면 사람 눈앞에 창이 뜨므로 드러난다.
- **영향 범위:**
  - 앱이 죽었다 다시 뜨거나 CLI가 띄운 엔진에 앱이 붙을 때 확인 창이 한 번 뜬다.
  - 터미널은 하루에 한두 번 `vuyro auth login`을 다시 해야 한다.
  - 앱이 떠 있을 때 확인을 앱 화면으로 받는 방식은 M6에서 정한다.
  - 근거: [[명령·이벤트 계약]] §3

## D-024. 통계의 "사람 대기 시간"은 무엇인가 (M3)

- **질문:** 사람 확인을 기다리는 일이 동시에 여러 개면, 티켓의 사람 대기 시간을 더할 것인가, 겹친 시간은 한 번만 셀 것인가?
- **고른 기본값:**
  - 티켓의 사람 대기 시간은 **누군가 사람을 기다린 벽시계 시간**이다. 겹친 시간은 한 번 센다.
  - 노드별 사람 대기 시간은 그 노드의 실행마다 더한다.
  - 사람 대기에 넣는 것: 리뷰(Review), 사람 노드, 반려되어 사람이 다시 해야 하는 사람 노드.
  - 넣지 않는 것: 일시정지(따로 센다), 실행 슬롯 대기(Queued).
- **이유:** 병목 분석에서 "사람 때문에 티켓이 얼마나 늦어졌나"는 벽시계 기준이 맞다. 노드별 합은 "어느 확인이 오래 걸리나"를 보여준다.
- **영향 범위:** M6 티켓 화면의 사람 대기 시간, 병목 노드(실행 + 사람 대기가 가장 긴 노드). 근거: [[명령·이벤트 계약]] §12

## D-025. 에이전트가 사용자의 환경 변수를 물려받는가 (M3)

- **질문:** 스크립트 노드는 최소한의 환경 변수만 받는다. 에이전트 CLI도 그렇게 할 것인가?
- **고른 기본값:** 에이전트는 사용자 환경을 물려받는다. 다만 `VUYRO_`로 시작하는 변수는 모두 지우고, 엔진이 그 실행의 변수(실행 토큰 등)를 넣는다.
- **이유:** 에이전트 CLI는 로그인 정보, 설정 폴더, 프록시 같은 사용자 환경이 있어야 돈다. 사람 자격이나 다른 실행의 토큰이 섞여 들어가는 것만 막으면 된다.
- **영향 범위:** 사용자 환경에 있는 API 키 같은 값은 에이전트가 볼 수 있다(지금도 사용자가 직접 CLI를 쓸 때와 같다). 노드별로 환경을 줄이는 옵션은 나중에 권한 정책과 함께 본다.

## D-026. 에이전트 한 번의 실행 시간 제한 (M3)

- **질문:** 에이전트가 멈추지 않고 계속 돌면 언제 멈출 것인가?
- **고른 기본값:** 실행 한 번에 60분. 넘으면 프로세스 트리를 멈추고, 그 실행은 실패(`timeout`)로 끝난다. 노드는 실패로 남고 사람이 재시도할 수 있다.
- **이유:** 데모 규모의 작업에는 충분하다. 막힌 에이전트가 토큰과 동시 실행 슬롯을 계속 쥐고 있지 않게 한다.
- **영향 범위:** 앱 설정(M6)과 노드별 덮어쓰기(정책 층)에 넣는다. 지금은 엔진 옵션 `agentTimeoutMs` 하나다.

## D-027. 합류·끝 노드가 넘겨준 산출물도 산출물 목록에 따로 보이는가 (M3)

- **질문:** Dev가 등록한 산출물이 합류와 끝 노드의 결과에도 그대로 실려 간다. 산출물 목록에 노드마다 따로 보여줄 것인가?
- **고른 기본값:** 아니다. 직접 등록한 것(`vuyro artifact add`)은 모두 보이고, 결과에만 실려 온 것은 같은 위치·버전이 처음 나올 때 한 번만 보인다.
- **이유:** 같은 파일·같은 버전은 하나의 산출물이다. 넘겨준 노드마다 보이면 목록이 늘어나기만 한다.
- **영향 범위:** M6 산출물 화면. 어느 노드를 거쳐 갔는지는 노드 상세(입력·출력)에서 본다.

## D-028. 에이전트는 확인 없이 파일을 고칠 수 있는가 (M3)

- **질문:** 무인으로 도는 에이전트에게 파일 수정 권한을 어디까지 줄 것인가?
- **고른 기본값:**
  - Claude: 작업 폴더의 파일 수정은 확인 없이 허용(`acceptEdits`), 명령은 `vuyro` CLI만 허용(결과 보고용).
  - Codex: 작업 폴더 안에서만 쓰기(`workspace-write` 샌드박스).
  - 그 밖의 명령과 작업 폴더 밖 쓰기는 CLI의 기본 동작대로 막힌다.
- **이유:** 노드는 사람 없이 끝까지 가야 하고, 결과는 리뷰·QA·사람 확인 노드가 본다. 쓰기 범위는 작업 공간으로 묶는다.
- **영향 범위:**
  - 빌드·테스트 명령이 필요한 노드는 허용 목록을 넓혀야 한다(노드 설정, M4 이후).
  - 내부 체크아웃 훅(M4)이 붙으면 쓰기 직전 판정이 더해진다.
  - 실제 CLI로 끝까지 도는지는 M7 스모크에서 확인한다.

## D-029. worktree 모드에서 무엇마다 worktree를 만드는가 (M4)

- **질문:** `worktreeScope`를 고르지 않았을 때 기본은 무엇이고, `nodeRun` 단위에서 팬아웃이 아닌 노드(Spec, Plan, QA)는 어디서 일하는가?
- **고른 기본값:** `nodeRun`. 팬아웃 노드의 레인(병렬 Dev 아이템)마다 worktree를 하나씩 만든다. 팬아웃이 아닌 노드는 티켓 worktree에서 일하고, 합류가 레인 브랜치들을 티켓 브랜치로 머지한다.
- **이유:** worktree 모드를 켜는 이유가 병렬 Dev다. Plan·QA까지 따로 worktree를 주면 그 결과를 합칠 곳이 없다(합류는 레인만 머지한다).
- **영향 범위:** 같은 티켓에서 팬아웃이 아닌 노드가 동시에 돌면 티켓 worktree를 함께 쓴다. 그때는 내부 체크아웃(훅을 켜면)과 사후 검출이 겹침을 막고 알린다. 근거: [[명령·이벤트 계약]] §14.1, §14.6.

## D-030. 엔진이 worktree에서 커밋하고 브랜치를 지워도 되는가 (M4)

- **질문:** worktree 모드에서 엔진이 git에 무엇까지 해도 되는가?
- **고른 기본값:**
  - 엔진은 자기 worktree의 자기 브랜치(`vuyro/<티켓>/…`)에만 커밋한다. 노드가 끝날 때마다 남은 변경을 커밋한다. 저장소의 커밋 훅은 돌리지 않고(`--no-verify`), 이름·이메일이 없으면 `Vuyro`로 커밋한다.
  - 티켓 브랜치는 처음 worktree를 만들 때 `baseRef`(없으면 그때의 HEAD)에서 시작한다.
  - 티켓 브랜치에 머지된 레인 브랜치는 지운다. 머지되지 않은 레인 브랜치와 **티켓 브랜치는 남긴다**. 티켓 브랜치를 사람의 브랜치(main 등)로 합치는 일은 하지 않는다.
  - worktree 폴더는 머지된 레인은 바로, 나머지는 티켓이 끝날 때 지운다. 실패한 레인의 worktree는 티켓이 끝날 때까지 남는다. 위치는 데이터 폴더 `wt/`다. (재검수 반영) 단, 아무것도 담고 있지 않을 때만 지운다. 남은 것이 있으면 사람이 정리한다(D-041, D-042).
- **이유:** 머지에는 커밋이 필요하다. 사람의 브랜치와 작업 폴더는 건드리지 않아야 한다. 결과(티켓 브랜치)는 사람이 보고 합친다.
- **영향 범위:** 사용자가 쓰는 커밋 훅(린트 등)은 엔진 커밋에서 돌지 않는다. 결과 브랜치를 언제 지울지는 M6 화면에서 다룬다. 준비 스크립트(worktree를 만든 직후 돌릴 명령)와 "실패 worktree 보존" 옵션은 아직 없다.

## D-031. Codex 훅을 어떻게 믿게 하는가 (M4)

- **질문:** Codex는 세션 플래그로 넣은 훅도 신뢰 확인이 없으면 돌리지 않는다([[초기 검증 결과]] M0b). 사용자 Codex 설정에 Vuyro 훅의 신뢰를 등록하려면 사용자 설정 파일을 고쳐야 한다(동의 필요). 무엇을 기본으로 할 것인가?
- **고른 기본값:** 사용자 설정은 고치지 않는다. 자동 체크아웃 훅을 켠 Codex 실행에만 `--dangerously-bypass-hook-trust`를 붙인다. **단, 작업 폴더에 Codex 프로젝트 훅(`.codex/hooks.json`이나 `.codex/config.toml`의 hooks)이 있으면 그 실행에는 훅을 넣지 않는다.** 이 플래그가 그 저장소의 훅까지 확인 없이 돌리기 때문이다. 대신 실행에 경고를 남기고, 사후 검출이 변경을 찾는다.
  - (M4 검수 반영) 이 플래그는 **사용자 전역 훅**도 확인 없이 돌린다. 그래서 훅을 넣는 실행은 `--ignore-user-config`로 사용자 `config.toml`(그 안의 훅과 플러그인)을 읽지 않는다. 로그인은 유지되고, Windows 샌드박스 설정만 옮겨 넣는다. **사용자 `hooks.json`(`CODEX_HOME/hooks.json`)은 이 옵션으로도 읽히므로, 거기에 훅이 있으면 체크아웃 훅을 넣지 않는다.** 근거: [[초기 검증 결과]] "M4 검수 반영: Codex 체크아웃 훅과 사용자 훅 격리".
- **이유:** 동의 절차 없이 사용자 설정을 고치지 않는다. 저장소나 사용자가 심어 둔 훅을 Vuyro가 확인 없이 실행하게 만들지도 않는다.
- **영향 범위:** 프로젝트 훅이 있는 저장소, 또는 사용자 `hooks.json`이 있는 PC(예: herdr 연동)에서는 Codex 노드가 수정 직전에 막히지 않는다(사후 검출만). 훅을 넣은 Codex 실행은 사용자 설정의 모델·공급자·MCP 서버를 쓰지 않는다. 모델은 노드 파라미터로 고른다. **아직 실제로 확인하지 않은 것(M7 스모크):** Codex가 훅 프로세스에 `VUYRO_*` 환경 변수를 넘기는지, `commandWindows`를 어떤 셸로 돌리는지. 넘기지 않으면 훅이 실행 토큰을 몰라 모든 수정을 거부한다(닫힌 쪽으로 실패). 그러면 이 기본값을 끄는 쪽으로 바꾼다.

## D-032. claim이 겹치면 누구의 정책을 따르는가 (M4)

- **질문:** 나중에 온 요청과 이미 점유한 항목의 충돌 정책이 다르면 어느 쪽을 쓰는가?
- **고른 기본값:** 나중에 온 쪽의 정책(claim에 적은 값, 없으면 노드의 설정 층)으로 그 요청의 운명을 정한다. 이미 점유한 쪽을 멈추는 방법(`pauseMode`)은 점유한 쪽 항목의 것이다. 충돌이 여럿이면 가장 엄격한 것(실패 > 사람 > 대기 > 선점 > 경고)을 쓴다.
- **이유:** 정책 표가 "나중에 온 티켓의 노드"를 어떻게 할지 정의한다. 멈춤 방법은 멈추는 쪽이 견딜 수 있는지의 문제다.
- **영향 범위:** [[명령·이벤트 계약]] §14.3.

## D-033. 기다리던 노드를 사람이 재개하면 (M4)

- **질문:** claim을 기다리는(Paused) 노드를 사람이 재개하면 어떻게 하는가?
- **고른 기본값:** 겹침을 무릅쓰고 진행한다. 그 실행이 끝날 때까지 claim과 체크아웃의 겹침은 경고로 기록하고 막지 않는다. 엔진이 스스로 재개할 때(막던 것이 풀렸을 때)는 claim을 다시 판정한다.
- **이유:** 설계 문서의 "사람이 직접 풀 수 있다". `ask`와 교착의 결정 수단이 따로 없으므로(결정 인박스는 M6) 재개가 곧 "이 노드를 먼저 하라"다.
- **영향 범위:** M6 결정 인박스가 생기면 "어느 쪽을 먼저" 같은 선택지를 따로 둘 수 있다.

## D-034. 우선순위가 높은 티켓은 어디까지 앞지르는가 (M4)

- **질문:** `priorityWins`에서 높은 티켓이 낮은 티켓의 점유를 언제 가져가는가?
- **고른 기본값:** 막는 항목이 `pauseMode: immediate`이고 점유자가 실행 중인 에이전트일 때만 바로 가져간다(점유자는 세션을 보존하고 멈췄다가 나중에 이어서 한다). `boundary`(기본)이면 `firstWins`처럼 기다리고, 점유가 풀리면 기다리던 노드를 우선순위 순으로 다시 시작한다. 티켓 우선순위는 `ticket.create`/`update`의 `priority`(정수, 기본 0)다.
- **이유:** 노드 경계에서 "다음 노드로 넘어가지 않게" 하는 동작은 노드 실행 순서 전체를 바꿔야 해서 MVP에서는 기다리기로 갈음한다.
- **영향 범위:** `ticketDone`으로 넘겨받은 claim은 높은 티켓이 와도 그 티켓이 끝날 때까지 남는다.

## D-035. 수정 직전에 막히면 실행 중인 에이전트를 멈추는가 (M4)

- **질문:** 훅이 체크아웃을 거부했을 때(다른 노드가 잡은 파일) 에이전트를 계속 돌게 둘 것인가?
- **고른 기본값:** 정책이 기다리기(`firstWins` 등)면 그 실행을 멈춘다(Paused, 세션 보존). 파일이 풀리면 엔진이 이어서 시작하고, 프롬프트에 "멈춘 동안 다른 노드가 바꾼 내 체크아웃 파일" 목록을 넣는다. `fail`이면 그 노드를 실패로 끝낸다.
- **이유:** 설계 문서 §3.8 "막힌 쪽 노드는 Paused". 에이전트가 거부를 무시하고 다른 길(셸)로 고치는 것을 줄인다.
- **영향 범위:** 멈춘 동안 바뀐 파일이 있으면 자동으로 재개하지 않고 사람 확인을 받는 옵션은 아직 없다.

## D-036. "귀속 불명 변경"은 무엇으로 정하는가 (M4)

- **질문:** 누가 바꿨는지 모르는 변경을 어떻게 가리는가?
- **고른 기본값:** 실행 시작·끝, 감시 이벤트, 엔진 시작 때 바뀐 파일을 찾는다(git status 읽기 전용 + 감시 후보 + 장부 경로, 판정은 SHA-256). 실행 중인 점유자의 체크아웃이 덮으면 그 점유자, 엔진 worktree에서 실행이 하나뿐이면 그 실행의 것이다. 그 밖에는 "귀속 불명"이고 그동안 돈 실행을 용의자로 적는다. 점유자가 멈춰 있는 동안 바뀌면 "충돌"이다. 공간을 처음 볼 때 이미 바뀌어 있던 파일은 기준선으로만 기록한다.
- **이유:** 훅을 우회한 수정(셸)과 사람의 수정을 같은 방법으로 찾는다. 공간에 실행이 하나뿐인 엔진 worktree는 사람이 손대지 않는 곳이다.
- **영향 범위:** 노드 사이에 사람이 공유 폴더를 고치면 다음 노드 시작 때 "귀속 불명"으로 뜬다. git이 아닌 폴더는 엔진이 꺼져 있던 동안의 변경을 찾지 못한다(`p4 opened` 같은 조회는 플러그인으로 붙일 자리만 있다).

## D-037. 실패한 노드의 체크아웃도 풀리는가 (M4)

- **질문:** 노드가 실패로 끝나면 그 노드의 claim과 체크아웃을 풀 것인가?
- **고른 기본값:** 푼다(`nodeDone` 해제는 완료와 실패 모두). 밀려나거나 버려진 실행의 것도 푼다. `ticketDone`은 티켓이 끝날 때, `manual`은 사람(또는 ttl)이 푼다.
- **이유:** 실패한 노드가 사람의 재시도를 기다리는 동안 다른 노드를 막지 않게 한다. 재시도는 새 실행이라 claim을 다시 잡는다.
- **영향 범위:** 실패한 노드가 반쯤 고친 파일을 다른 노드가 잡을 수 있다. 그 사이 바뀐 것은 재시도 실행의 시작 검사로 보인다.

## D-038. 머지 충돌을 사람에게 보낼 때 무엇을 누르면 되는가 (M4)

- **질문:** `onMergeConflict: ask`로 합류가 Review에 있을 때 사람의 승인·반려는 무엇을 뜻하는가?
- **고른 기본값:** 머지는 티켓 worktree에 진행 중인 채로 둔다. **승인** = 사람이 그 폴더에서 풀고 스테이징했으니 계속한다(아직 남았으면 다시 Review). **반려** = 의견을 지시로 붙여 에이전트에게 맡긴다(에이전트가 풀면 다시 Review). `rerun`은 충돌한 레인을 머지된 브랜치에서 처음부터 다시 하게 한다(새 worktree에서. 옛 worktree와 브랜치는 정리 대기로 남는다, D-042). `agent`가 못 풀면 `ask`로 넘어간다.
- **이유:** 결정 인박스(M6) 전이라 기존 승인·반려 버튼에 뜻을 붙였다.
- **영향 범위:** M6 화면은 Review의 `merge` 정보(폴더, 충돌 파일)를 보여 줘야 한다.

## D-039. 수정 직전 체크아웃의 범위 (M4)

- **질문:** 작업 폴더 밖 파일, 이미 잡은 파일, 패턴은 어떻게 다루는가?
- **고른 기본값:** 작업 폴더 밖 파일은 장부에 적지 않고 허용한다(다른 노드와 겹칠 공간이 아니다). 같은 실행이 이미 잡은 파일은 다시 적지 않는다. 체크아웃은 파일만 받고, 패턴은 노드 타입의 claim으로만 잡는다. 에이전트는 자기 체크아웃을 먼저 풀 수 있다(`vuyro checkout release`). claim은 노드와 함께 끝난다.
- **이유:** 장부는 "같은 공간의 같은 파일"을 막기 위한 것이다.
- **영향 범위:** 작업 폴더 밖 수정은 에이전트 CLI의 권한 설정(D-028)이 막는다.

## D-040. 감시에서 빼는 경로 기본값 (M4)

- **질문:** 프로젝트가 정하지 않았을 때 변경 감지에서 무엇을 뺄 것인가?
- **고른 기본값:** `.git/**`, `node_modules/**`, `Intermediate/**`, `Binaries/**`, `Saved/**`, `DerivedDataCache/**`. git status는 `.gitignore`도 따른다. 프로젝트 설정 `watch.include`·`watch.exclude`로 바꾼다.
- **이유:** 빌드 결과물은 바뀌어도 귀속을 따질 대상이 아니고 양이 많다([[기술 스택 결정]] §10).
- **영향 범위:** Unreal 크기 폴더에서 감시 이벤트가 유실되는지는 아직 재지 않았다(§13 #6). 유실돼도 시작·끝 검사의 git status가 남는다.

## D-041. 지울 worktree에 커밋하지 않은 변경이 있으면 (M4 검수 반영)

- **질문:** 티켓이 끝나거나 레인이 머지되어 엔진이 worktree를 지우려는데, 그 폴더에 아무도 커밋하지 않은 변경이 있다. 예: QA 승인을 기다리는 동안 사람이 티켓 worktree에 파일을 추가했다. 지울 것인가?
- **고른 기본값:** 지우지 않는다. 폴더를 그대로 두고 "정리 대기"(`worktree.kept`, 바뀐 파일·무시 파일 목록)로 남긴다. 엔진은 그 티켓의 일이 진행될 때와 엔진이 시작할 때 다시 보고, 아무것도 남지 않았으면 그때 지운다. (재검수 반영) **무시되는 파일도 남은 것으로 센다.** 처음에는 빌드 결과물이라 보고 함께 지웠는데, `.gitignore` 대상인 사람의 파일(로컬 설정 등)도 지워졌다. 사람이 지우려면 D-042의 정리 명령을 쓴다.
- **이유:** worktree를 지우면 커밋하지 않은 일은 되찾을 수 없다. 보존 브랜치에 자동으로 커밋하는 방법도 있지만, 사람이 손댄 것을 엔진이 사람 대신 커밋하게 된다. 남겨 두고 알리는 쪽이 되돌리기 쉽다.
- **영향 범위:** 보류된 worktree는 디스크에 남는다. M6 관제실에 목록(`query.workspace`의 `keptAt`·`keptFiles`)과 "지우기" 동작이 필요하다. 지금은 사람이 그 폴더에서 커밋하거나 되돌려야 한다. 근거: [[명령·이벤트 계약]] §14.6.

## D-042. 엔진은 스스로 파괴적인 git 조작을 하지 않는다 (M4 재검수 반영)

- **질문:** worktree 모드에서 엔진이 사람의 확인 없이 작업을 버리는 git 조작(`worktree remove --force`, `reset --hard`, `clean`)을 해도 되는가? `rerun`으로 레인을 다시 시작할 때 옛 worktree는 어떻게 하는가?
- **고른 기본값:**
  - 하지 않는다. 엔진이 알아서 지우는 worktree는 **아무것도 담고 있지 않은 것**(바뀐 파일, 추적하지 않는 파일, 무시되는 파일이 모두 없음)뿐이고, 그때도 `--force` 없이 지운다. 브랜치는 티켓 브랜치에 머지된 레인 브랜치만 지운다.
  - `rerun`은 옛 worktree를 되감지 않는다. **새 폴더·새 브랜치**(`<노드>-<레인>.r<실행>`)를 머지된 티켓 브랜치에서 만들어 거기서 다시 한다. 옛 worktree와 브랜치는 그대로 두고 "정리 대기"(`superseded`)로 표시한다. 티켓이 끝났을 때 아무것도 담고 있지 않으면 폴더만 지우고, 브랜치는 남긴다.
  - (재재검수 반영) 머지된 레인 브랜치는 확인한 그 커밋을 아직 가리킬 때만 지운다(`update-ref -d` 비교 후 삭제, `branch -D` 안 씀). 합류 머지의 `fail`·`rerun`은 충돌을 미리 보기(`merge-tree`)로 찾아 그 머지를 시작하지 않는다. 그래서 `merge --abort`를 쓰지 않는다. 진행 중인 충돌 머지는 엔진이 되돌리지 않고 사람에게 남긴다. 엔진이 부르는 git 조작 전체와 그 근거는 [[명령·이벤트 계약]] §14.9.
  - 그 밖의 정리는 **사람이 확인하는 명령**으로만 한다: `vuyro workspace cleanup --project <id>`가 남은 내용(무시 파일 포함)과 지문을 보여 주고, `--remove <key> --fingerprint <fp>`로 확인하면 엔진이 그 사이 바뀌지 않았을 때만 지운다. 이 명령은 사람만 할 수 있다(AI·엔진은 거부, 고정 규칙).
- **이유:** worktree 안의 미커밋 변경과 무시 파일은 git으로도 되찾을 수 없다. 사람이 무엇이 지워지는지 보고 정하게 한다. 지문은 "본 것만 지운다"를 지킨다.
- **영향 범위:** 빌드 결과물(무시 파일)이 있는 worktree는 자동으로 지워지지 않아 디스크에 남는다. 사람이 정리 명령으로 지워야 한다. M6 관제실에 같은 목록과 확인 단계를 둔다. `rerun`마다 레인 worktree·브랜치가 하나씩 늘어난다. `fail`·`rerun`에서 머지 도중 엔진이 멈추면 그 머지는 사람이 마무리하거나 되돌려야 합류를 재시도할 수 있다. git 2.38 이상이 필요하다. 근거: [[명령·이벤트 계약]] §14.5·§14.6.

## D-043. 공유 노드는 어디에 정의하는가 (M5)

- **질문:** 공유 노드(빌드 스테이션 등)의 정의를 템플릿·노드 타입처럼 정의 파일로 둘 것인가, 프로젝트에 둘 것인가?
- **고른 기본값:** 프로젝트에 둔다. `vuyro shared define --project <id> <spec>`(명령 `sharedNode.define`)이 정의를 이벤트에 담는다. 정의를 바꾸면 버전이 하나 올라가고, 이미 돌고 있는 묶음은 시작할 때의 정의로 끝난다. 정의는 쓰는 노드 타입의 해시를 고정한다.
- **이유:** 설계 §4.1 "공유 노드는 티켓 밖, 프로젝트 범위에 산다. 프로젝트에 하나 만들어 두고 여러 템플릿이 가리킨다". 이름으로 가리키므로 템플릿을 바꾸지 않고 프로젝트마다 다른 빌드를 붙일 수 있다.
- **영향 범위:** 내보내기 봉투 `kind: sharedNode`는 CLI가 받기만 한다(`content`를 spec으로 씀). 파일로 내보내기·가져오기 미리보기는 M6.

## D-044. 요청 노드의 출력 포트 이름 (M5)

- **질문:** 설계 §4.4 예시는 `success | error | skipped`다. 요청 노드의 포트를 무엇으로 할 것인가?
- **고른 기본값:** `done`과 `error`. `skipped`는 두지 않는다. 사용자 정의 요청 노드 타입도 이 두 포트가 있어야 한다.
- **이유:** 다른 기본 노드(스크립트, 에이전트, 합류)가 모두 `done`/`error`라서 템플릿을 같은 방식으로 잇는다. "건너뜀"이 필요한 경우가 아직 없다.
- **영향 범위:** 원인 티켓의 `error` 포트를 Dev로 되돌리는 간선을 템플릿에 둔다(반려 루프). 연결하지 않으면 그 티켓은 "처리되지 않은 실패"로 사람의 재시도를 기다린다.

## D-045. 묶음을 언제 시작하고 무엇을 넣는가 (M5)

- **질문:** 실행 조건이 여럿일 때와, 대기열에 조건보다 많은 요청이 있을 때 어떻게 하는가?
- **고른 기본값:**
  - 조건 중 먼저 맞는 것으로 시작한다. `count`: 대기 요청이 N개 이상. `window`: 가장 오래된 요청이 들어온 뒤 T가 지남(엔진 재시작과 무관하게 들어온 시각부터). `afterPrevious`: 실행 중인 묶음이 없으면 곧바로(첫 요청도). `manual`: 사람이 실행할 때만. 사람의 실행은 조건과 무관하게 언제나 된다(막혔거나 자리가 없을 때 빼고).
  - 시작하면 **대기 중인 요청을 모두** 넣는다(N개에서 자르지 않음).
  - 실패하거나 중단된 묶음에서 대기열로 돌아온 요청이 있으면 조건을 다시 기다리지 않고 곧바로 시작한다(이미 한 번 조건을 채웠다).
  - 일시정지된 요청은 자리를 지키지만 묶음에 넣지 않는다.
- **이유:** 빌드는 한 번에 많이 넣을수록 싸다. 돌아온 요청을 다시 기다리게 하면 원인 수정 뒤 "함께 재실행"이 조건에 따라 늦어진다.
- **영향 범위:** `schedule`(정해진 시각)과 `expediteOnPriority`는 받기만 하고 쓰지 않는다(정의할 때 경고, D-047).

## D-046. 빌드가 깨졌을 때 원인 티켓을 어떻게 고르는가 (`blame`, M5)

- **질문:** 묶음이 실패했을 때 어느 티켓 탓으로 볼 것인가?
- **고른 기본값:**
  - 빌드 출력의 오류 줄에서 줄 번호가 붙은 파일(`a.cpp(12): error`, `a.c:7:1: error`, `a.ts(12,5): error`)을 찾는다. 스크립트가 JSON 결과에 `errorFiles`를 주면 그것을 쓴다.
  - 그 파일을 내부 체크아웃 장부의 편집 기록(배타 체크아웃, 체크아웃으로 확인된 변경)과 대조해 **고친 적 있는 묶음 안의 티켓 모두**를 원인으로 본다. 편집 기록이 없으면 그 파일을 덮는 배타 claim을 잡았던 티켓을 본다. 묶음 밖 티켓은 원인으로 보지 않는다.
  - 원인을 하나도 못 찾으면 `allFail`처럼 모든 티켓을 error로 보낸다(`ask`가 아직 없으므로).
- **이유:** 설계 §4.5. 같은 파일을 둘이 고쳤으면 어느 쪽 변경이 깨뜨렸는지 장부만으로는 모른다. 둘 다 보내는 쪽이 놓치지 않는다.
- **영향 범위:** 헤더를 고쳐 다른 파일에서 오류가 나면 원인을 못 찾아 모두 실패한다. 훅 없이(셸로) 고친 파일은 사후 검출이 체크아웃으로 귀속하지 못하면 기록에 없다. 링커 오류처럼 파일이 없는 오류도 모두 실패다.

## D-047. 아직 하지 않는 실패 정책과 조건 (M5)

- **질문:** `onBatchFailure: ask | bisect | agent`, `batchTrigger.schedule`, `expediteOnPriority`를 정의에 쓰면 어떻게 하는가?
- **고른 기본값 (검수 반영으로 바뀜):** `ask`·`bisect`·`agent`는 **정의할 때 거부한다**(처음에는 받고 경고한 뒤 `allFail`로 돌렸는데, 적은 것과 다르게 도는 정의를 남기지 않기로 했다). `schedule`·`expediteOnPriority`는 받되 경고하고 아무것도 시작하지 않는다. 자동 조건이 하나도 없으면(예: `schedule`만) 사람이 실행할 때만 돈다고 경고한다.
- **이유:** 설계 §4.7 MVP 범위. 정의를 거부하면 나중에 지원할 때 정의를 다시 써야 한다. `ask`는 결정 인박스(M6), `bisect`는 worktree 통합 브랜치(MVP 이후)가 필요하다.
- **영향 범위:** `ask` 등을 쓰려면 지원될 때까지 `blame`이나 `allFail`을 고른다. 경고(`schedule` 등)를 정의 화면(M6)에 보여야 한다.

## D-048. 원인 티켓 때문에 멈춘 공유 노드는 언제 풀리는가 (M5)

- **질문:** Blocked가 된 공유 노드를 무엇으로 다시 돌게 할 것인가?
- **고른 기본값:** 원인으로 지목된 요청 레인(티켓·요청 노드·레인)이 **더 새 실행으로 대기열에 다시 들어오면** 그 레인은 풀린다. 지목된 레인이 모두 돌아오면 공유 노드가 풀리고, 기다리던 티켓과 함께 곧바로 다시 돈다. 사람은 언제든 `vuyro shared unblock`으로 푼다. 막힌 동안 새 요청은 대기열에 쌓이기만 한다.
- **이유:** 설계 §4.5 "원인 티켓이 고친 뒤 요청 노드가 다시 대기열에 들어오면 풀린다", "사람이 직접 풀 수 있다".
- **영향 범위:** 원인 티켓이 다른 요청 노드나 다른 레인으로 돌아오거나, 고치지 않고 버려지면 사람이 풀어야 한다(티켓 취소가 아직 없다). 사람이 풀면 원인 티켓 없이 나머지가 먼저 빌드된다.

## D-049. 묶음이 도는 중에 엔진이 멈추면 (M5)

- **질문:** 빌드 중에 엔진이 꺼졌다 켜지면(또는 결과를 기록하지 못하면) 그 묶음을 다시 돌릴 것인가?
- **고른 기본값:** 다시 돌리지 않는다. 그 묶음은 "중단"으로 기록하고, 묶음의 티켓들은 대기열 맨 앞으로 돌아가며, 공유 노드는 Blocked(중단)가 된다. 사람이 풀면 같은 티켓들로 다시 돈다. 엔진을 정상 종료할 때 도는 묶음도 같다(실패로 보지 않는다).
- **이유:** D-011(스크립트는 부작용이 있을 수 있어 다시 돌리지 않음)과 같은 생각이다. 일괄 submit·배포 같은 공유 노드는 두 번 돌면 안 된다. 실패로 보면 죄 없는 티켓이 Dev로 돌아간다.
- **영향 범위:** PC가 재부팅되면 빌드 대기열이 사람의 확인까지 멈춘다. 빌드처럼 다시 돌려도 되는 공유 노드에 "자동 재실행" 옵션을 두는 것은 나중에 본다.

## D-050. 빌드 중 보호 경로와 다른 노드의 편집 (M5)

- **질문:** `protect`(예: `src/**`)를 잡을 때 다른 노드가 그 안의 파일을 편집 중이면? 묶음이 도는 중에 다른 노드가 편집하려 하면?
- **고른 기본값:**
  - 묶음은 보호 경로를 **공유 claim**으로, 묶음의 모든 티켓 이름으로 잡는다. 누가 그 안의 파일을 체크아웃하고 있으면 프로젝트의 충돌 정책(기본 `firstWins`)대로 기다리고, 풀리면 엔진이 다시 시도한다. `fail` 정책이면 묶음의 요청이 모두 실패한다. 묶음은 다른 노드를 선점하지 않는다(`priorityWins`여도 기다린다).
  - 묶음의 티켓들이 스스로 쥔 것(티켓이 끝날 때까지 잡는 claim 등)은 묶음을 막지 않는다.
  - 묶음이 도는 중에 다른 노드가 그 안의 파일을 고치려 하면 그 노드가 기다린다(D-035와 같다).
  - 사람이 `vuyro shared run`으로 실행하면 겹침을 무릅쓰고 시작하고 겹침을 기록한다(D-033과 같다).
- **이유:** 설계 §4.3. 반쯤 고친 파일로 빌드하면 결과를 믿을 수 없다. 빌드는 에이전트처럼 멈췄다 이어갈 수 없으므로 선점하지 않는다.
- **영향 범위:** 오래 편집하는 노드가 있으면 빌드가 늦어진다. 보호를 끄려면 `protect`를 비운다.

## D-051. worktree 모드 티켓과 프로젝트 폴더가 없는 프로젝트 (M5)

- **질문:** worktree 모드 티켓이 공유 노드에 요청하면? 프로젝트 폴더가 없으면?
- **고른 기본값:** worktree 모드 티켓의 요청은 이유와 함께 error 포트로 끝난다(통합 브랜치에 머지해 빌드하는 것은 MVP 이후). 프로젝트 폴더가 없으면 묶음은 프로그램을 띄우지 않고 모든 티켓이 실패한다. (검수 반영) 노드 타입이 자기 작업 폴더(`cwd`)를 정해도 프로젝트 폴더 안만 받는다. 밖이면 실패한다. 보호 경로와 실제로 빌드하는 폴더가 어긋나지 않게 하려는 것이다.
- **이유:** 설계 §4.7 MVP는 `shared` 모드만. 엔진의 작업 폴더에서 빌드하면 엉뚱한 것을 빌드한다.
- **영향 범위:** worktree 모드를 쓰는 프로젝트는 아직 공유 노드를 쓸 수 없다.

## D-052. 공유 노드 안에서 도는 노드 (M5)

- **질문:** 공유 노드가 묶음마다 돌리는 노드로 무엇을 허용하는가?
- **고른 기본값:** 스크립트 노드 타입만(셸 없이, 최소 환경 변수, 제한 시간, 종료 코드 → 포트). 에이전트 노드는 정의할 때 거부한다.
- **이유:** MVP 사례(빌드, 테스트, 배포)는 스크립트다. 에이전트는 실행 토큰이 한 티켓·노드 범위라서 여러 티켓 묶음의 권한 모양을 새로 정해야 한다.
- **영향 범위:** "에러 분석 에이전트"(`onBatchFailure: agent`)와 함께 나중에 본다.

## D-053. 원인 티켓의 우선순위를 올리는 정도 (`raiseBlamedPriority`, M5)

- **질문:** 옵션이 켜져 있으면 원인 티켓의 우선순위를 얼마나 올리는가? 되돌리는가?
- **고른 기본값:** 그 묶음 티켓들의 가장 높은 우선순위 + 1로 올린다(최대 1000). 되돌리지 않는다.
- **이유:** 다른 티켓들이 이 티켓을 기다리므로 claim 경쟁(`priorityWins`)에서 먼저 가게 한다.
- **영향 범위:** 우선순위는 지금 claim 경쟁에만 쓰인다. 실행 슬롯 순서에는 아직 쓰지 않는다.

## D-054. 한 프로젝트 폴더에서 묶음을 동시에 몇 개 돌리는가 (M5 검수 반영)

- **질문:** 공유 노드의 `maxConcurrent`를 2 이상으로 두거나, 한 프로젝트에 공유 노드가 여럿(빌드, 테스트)이면 묶음이 같은 폴더에서 동시에 돌아도 되는가?
- **고른 기본값:** 안 된다. shared 모드에서 묶음은 모두 프로젝트 폴더를 빌드하므로 **한 프로젝트에서 한 번에 한 묶음만** 돈다. 묶음을 시작할 때마다 프로젝트의 폴더 잠금으로 확인하므로, 이 규칙 전에 저장된 정의에도 적용된다(재검수 반영). `maxConcurrent`는 1만 받는다(2 이상은 정의할 때 거부, 이미 저장된 값은 1로 본다). 다른 공유 노드의 묶음이 돌고 있으면 시작하지 않고, 그 묶음이 끝나면 엔진이 다시 본다. 사람의 실행도 기다리라는 답을 받는다.
- **이유:** 두 빌드가 같은 폴더의 중간 산출물을 함께 쓰면 결과를 믿을 수 없다. 보호 경로는 공유 claim끼리라 서로 막지 않으므로 따로 막아야 한다(검수 지적).
- **영향 범위:** 빌드와 테스트를 나란히 돌릴 수 없다. 여러 묶음을 동시에 돌리는 것은 worktree 통합 브랜치(MVP 이후)와 함께 본다.

## D-055. 보호 경로에 `ttl`을 주면 (M5 검수 반영)

- **질문:** 공유 노드의 `protect`에 `ttl`(정리 기한)을 적으면 빌드 도중 보호가 풀려도 되는가?
- **고른 기본값:** `ttl`을 쓰지 않는다(정의할 때 경고). 묶음은 끝날 때까지 보호 경로를 쥐고, 끝나거나 중단될 때 놓는다. 엔진이 죽어도 다음 시작에서 그 묶음을 중단으로 마감하며 놓으므로 기한이 필요 없다.
- **이유:** 기한이 빌드보다 짧으면 빌드 도중 다른 노드가 소스를 고칠 수 있다(검수 지적).
- **영향 범위:** 없음(설정이 무시된다는 경고만).


## D-056. 칸반 보드의 컬럼은 무엇인가 (M6a)

- **질문:** 보드의 컬럼을 노드 상태(대기·실행 중·사람 차례·완료)로 할 것인가, 시안 02처럼 템플릿의 단계로 할 것인가?
- **고른 기본값:** 템플릿 하나를 고르면 그 템플릿의 **단계**가 컬럼이다(그래프의 왼쪽→오른쪽 순서, 컬럼 머리에 "사람 승인", "자동 · 병렬" 같은 완료 방식). 티켓은 **가장 앞에 있는 끝나지 않은 일**의 컬럼에 놓인다(그 일이 티켓을 붙잡고 있으므로). 반려되어 Spec으로 돌아가면 Spec 컬럼으로 돌아온다. 처음에는 프로젝트에서 가장 많이 쓴 템플릿을 보여 주고, 「전체 (상태별)」을 고르면 사람 차례·실행 중·막힘·대기·완료 컬럼이 된다. 다른 템플릿의 티켓은 숨긴 수를 알려 준다.
- **이유:** 사용자가 고른 시안 방향(02)이 단계 컬럼이다. 템플릿마다 단계가 달라 섞으면 컬럼을 정할 수 없으므로 전체 보기는 상태로 한다.
- **영향 범위:** 병렬 레인이 여러 단계에 걸치면 가장 앞 단계에만 보인다(카드의 진행 막대와 칩으로 나머지를 보여 준다).

## D-057. 보드에서 카드를 끌면 무엇이 바뀌는가 (M6a)

- **질문:** dnd-kit으로 카드를 끌었을 때 어떤 의미를 줄 것인가? 컬럼 사이로 옮기면 노드를 승인·진행시키는가?
- **고른 기본값:** **같은 컬럼 안에서 위아래로 끌면 티켓의 우선순위가 바뀐다**(`ticket.update priority`, 위가 높다). 컬럼 사이로는 옮길 수 없다. 우선순위가 같은 카드끼리는 오래된 것이 위라서, 같은 값 사이로 끌면 바로 그 자리에 서지 않을 수 있다.
- **이유:** 컬럼은 엔진의 진행 상태를 보여 주는 것이라 손으로 옮기면 사실과 달라진다. 승인·반려는 비용이나 되돌릴 수 없는 결과가 따르므로 끌기 같은 가벼운 동작에 걸지 않는다. 우선순위는 claim 경쟁(D-034)에 쓰이는 실제 값이라 보드 순서와 맞추면 뜻이 생긴다.
- **영향 범위:** 우선순위 범위는 -1000~1000. 새 티켓 대화 상자에 높음(10)·보통(0)·낮음(-10)이 있다.

## D-058. "완전 종료"는 엔진도 멈추는가 (M6a)

- **질문:** 트레이의 완전 종료가 앱만 닫는가, 엔진(에이전트 실행·공유 노드 대기열)까지 멈추는가?
- **고른 기본값:** **앱과 엔진을 함께 멈춘다.** 실행 중인 작업이 있으면 "실행 중인 작업 N개가 있습니다. 완전히 종료할까요?"로 확인한다(기본 버튼은 취소). 엔진에 물어볼 수 없어 개수를 모를 때도 확인한다(M6a 검수 반영). 멈춘 에이전트는 취소로 기록되고 다음에 Vuyro를 시작하면 다시 줄을 선다. 터미널에서 띄운 엔진이라 앱에 권한이 없으면 "엔진은 계속 실행됩니다"라고 알리고 앱만 닫는다.
- **이유:** 기획 결정(2026-10-23)이 "완전 종료할 때 실행 중인 작업이 있으면 확인을 받는다"이다. 앱만 닫는 것이면 확인할 이유가 없다. 창 닫기가 이미 "작업은 계속"이다.
- **영향 범위:** 앱이 떠 있는 동안 엔진이 사라지면 앱이 같은 자격으로 다시 띄운다(앱이 엔진의 주인). 터미널에서 `vuyro engine stop`을 해도 앱이 떠 있으면 다시 뜬다.

## D-059. 이미 떠 있는 엔진에 앱이 붙을 때 사람 권한을 언제 청하는가 (M6a)

- **질문:** 엔진이 앱의 자격을 모를 때(터미널에서 띄움, 앱 없이 재시작) 앱이 시작하자마자 짝 맺기(엔진 대화 상자)를 띄울 것인가?
- **고른 기본값:** 아니다. 읽기 전용으로 붙어서 보드는 보여 주고, 배너의 [권한 연결]을 사람이 누를 때만 청한다. 대화 상자와 배너에 같은 4자리 코드가 보인다. 거부되면 다시 누를 수 있다.
- **이유:** 앱은 트레이에 오래 머문다. 엔진이 바뀔 때마다 시스템 모달 대화 상자가 불쑥 뜨면 사람이 요청하지 않은 대화 상자에 익숙해져 [예]를 누르게 된다. 그러면 에이전트가 청한 대화 상자도 구분하지 못한다(계약 §3의 경계가 약해진다).
- **영향 범위:** 앱을 완전 종료 없이 껐다 켜면(앱만 죽은 경우) 한 번 [권한 연결]이 필요하다. 보통의 완전 종료 → 시작에서는 앱이 엔진을 새로 띄우므로 필요 없다.

## D-060. 티켓 상세에서 사람이 하는 일과 보여 주는 수치 (M6a)

- **질문:** 사람 노드를 어떻게 끝내고, 상세 화면에 무엇을 보여 줄 것인가?
- **고른 기본값:**
  - 사람 작업(BrainStorming 같은 `human-task`): 요약을 적고 출력 포트마다 버튼(`done` = 완료, `error` = 못 함). 데이터(JSON)는 적지 않는다(YAML·JSON 없이, PRD 성공 기준).
  - 승인 노드: 입력(요약·데이터·산출물 위치)을 보고 의견과 함께 승인/반려. 반려할 아이템 고르기(`items`)는 아직 없다(모두 돌려보낸다).
  - 리뷰 게이트(QA 같은 에이전트 결과 확인): 결과를 보고 승인(다음으로 보냄)/반려(다시 실행). 빈 결과면 그렇다고 알린다.
  - 수치: 티켓 총 시간·사람 대기 시간·실행 시간·토큰(입력/캐시/출력)·병목 노드, 노드마다 실행 시간·사람 대기·토큰·도구 호출(실패 수)·실행 횟수(재작업 수). 금액은 정가 추정이라 아래에 작게(D-002).
  - 티켓 짧은 표시는 `T-` + id 끝 6자(UUIDv7 앞부분은 시각이라 서로 비슷하다).
- **이유:** PRD 성공 기준("티켓 하나의 총 소요 시간, 사람 대기 시간, 토큰 사용량을 화면에서 바로 확인하고, 어느 노드가 병목인지")을 한 화면에서 보이게.
- **영향 범위:** 노드 상세 로그(메시지·도구 호출 목록)는 M6b다.

## D-061. 보드와 그래프를 오갈 때 무엇이 유지되는가 (M6b)

- **질문:** 칸반에서 고른 티켓을 그래프에서도 그대로 볼 것인가? 티켓 상세 서랍은 어떻게 되는가? 창을 닫았다 열면?
- **고른 기본값:** 보드·그래프·템플릿 세 보기가 **선택한 티켓 하나**를 같이 쓴다. 보드에서 카드를 누르면 그 티켓이 선택되고 상세 서랍이 열린다. 서랍의 [그래프로 보기]나 머리글의 [그래프]로 가면 같은 티켓의 그래프가 보이고, 보드로 돌아오면 그 카드에 테두리가 있다. 서랍을 닫아도(Esc) 선택은 남는다. 보기와 선택 티켓은 창을 닫았다 열어도 남는다. 그래프 왼쪽 목록은 「진행 중」이 기본이고 「내 차례·완료·전체」로 바꾼다.
- **이유:** 과제 지시("같은 티켓 선택 유지")와 시안 01(왼쪽 티켓 목록, 가운데 그래프, 오른쪽 노드 상세). 트레이에서 창을 다시 열 때 보던 곳으로 돌아오는 것이 자연스럽다.
- **영향 범위:** 화면 상태만. 선택한 티켓이 지워졌거나 다른 데이터 폴더면 목록의 첫 티켓을 고른다.

## D-062. 내보낼 때 무엇을 비밀값으로 보고 빼는가 (M6b)

- **질문:** "비밀값 제외"에서 무엇을 뺄 것인가? 뺀 사실은 어떻게 알리는가?
- **고른 기본값:** 스크립트 노드 타입의 `env` **값 전부**, 그리고 이름에 `token`·`secret`·`password`·`passphrase`·`api key`·`access key`·`private key`·`credential`이 든 파라미터의 기본값과 템플릿 노드의 값. 뺀 것은 이름만 `requires.credentials`에 남는다. 내보내기 화면이 "비밀값일 수 있어 빼고 내보냅니다"와 목록을 보여 주고, 가져오는 화면이 "이 값 없이 실행됩니다"를 보여 준다.
- **이유:** 환경 변수는 토큰을 넘기는 흔한 자리라 값이 비밀인지 엔진이 가릴 수 없다. 파라미터는 이름으로만 추정한다. 자격증명 저장소(이름 → 값 연결, 설계 §1.3의 "연결" 단계)는 MVP에 없다.
- **영향 범위:** 비밀이 아닌 환경 변수도 빠져서 받는 쪽이 다시 적어야 한다(MVP에는 정의 편집기가 없어 JSON을 고쳐 다시 가져와야 함). 필수 파라미터가 빠진 템플릿은 가져올 때 검사에 걸려 저장되지 않는다. 이름이 평범한 파라미터에 든 비밀이나 `extensions`(플러그인 데이터) 속 비밀은 못 거른다.

## D-063. 가져올 때 같은 id가 있으면 (덮어쓰기의 뜻) (M6b)

- **질문:** 같은 id·같은 버전이 다른 내용으로 이미 있을 때 "덮어쓰기"는 무엇을 하는가?
- **고른 기본값:** 버전은 바꿀 수 없으므로(그 버전으로 도는 티켓이 있다) **덮어쓰기 = 같은 id의 다음 빈 버전으로 저장**이다. 새 티켓은 최신 버전을 쓰고 옛 티켓은 그대로다. 그 밖의 선택은 새 id(와 이름)로, 건너뛰기. 같은 버전·다른 내용은 **사람이 셋 중 하나를 고를 때까지 저장할 수 없다.** 같은 버전·같은 내용은 기본 건너뛰기다. 어느 항목에든 문제(잘못된 새 id, 누락된 노드 타입, 검사 실패)가 있으면 아무것도 저장하지 않는다.
- **이유:** 설계 §1.3("같은 id의 새 version → 새 버전으로 추가", "같은 version인데 내용이 다르면 거부하고 묻는다")과 정의 불변 규칙(§10.1). 일부만 저장하면 사람이 고른 것과 다른 결과가 된다.
- **영향 범위:** 덮어쓰기를 할수록 버전이 늘어난다. 같은 파일의 템플릿은 새로 저장한 노드 타입 버전을 가리키도록 고쳐 저장한다.

## D-064. 템플릿을 내보낼 때 노드 타입을 함께 넣는가 (M6b)

- **질문:** 템플릿만 내보낼 것인가, 쓰는 노드 타입을 함께 묶을 것인가? 가져올 때 파일의 노드 타입을 건너뛰면?
- **고른 기본값:** 기본은 **함께 묶는다**(묶음, 기본 노드 타입 포함). 끄면 템플릿 봉투 하나만 내보낸다. 가져올 때 파일의 노드 타입이 이 엔진과 같으면 건너뛰고, 다른데 건너뛰기를 고르면 템플릿은 **이 엔진의 내용으로 돈다**. 미리보기가 그것을 경고("이 엔진의 다른 내용으로 실행됨")하고 실행 내용도 이 엔진의 것을 보여 준다.
- **이유:** 받는 쪽에 노드 타입이 없어도 가져올 수 있어야 공유가 된다(설계 §1.1 `bundle`). 실행 내용은 실제로 돌 것을 보여야 확인의 의미가 있다.
- **영향 범위:** 기본 템플릿 하나를 내보내면 노드 타입 6개가 같이 들어간다(약 18 KB).

## D-065. 가져오기를 사람이 어떻게 확인하는가 (M6b)

- **질문:** 미리보기를 보여 주는 것만으로 충분한가?
- **고른 기본값:** 미리보기 아래 "실행 내용(스크립트 명령·인자·폴더, 에이전트 프롬프트, 쓰는 경로)을 확인했습니다" 칸을 **체크해야** [가져오기]가 열린다. 처리(덮어쓰기·새 id·건너뛰기)를 바꾸면 미리보기를 다시 받고 체크도 풀린다. 저장할 노드 타입과 모든 템플릿은 실행 내용이 펼쳐져 있고, 건너뛰는 노드 타입은 접혀 있다.
- **이유:** 가져온 정의는 이 PC에서 프로그램을 실행한다(설계 §1.3 "실행되는 것을 따로 표시"). 클릭 한 번으로 넘어가지 않게.
- **영향 범위:** 가져오기 한 번에 클릭이 하나 는다.

## D-066. 노드 로그를 얼마나 보여 주는가 (M6b)

- **질문:** 에이전트가 오래 돌아 로그가 길면 화면이 멈추지 않게 어떻게 줄일 것인가?
- **고른 기본값:** 엔진이 글을 4000자에서 자르고 전체 길이를 함께 준다([전체 불러오기]로 그 항목만 다시 받음). 화면은 최근 200행만 그리고 [이전 항목 더 보기]로 200행씩 늘린다. 6줄·600자가 넘는 글은 접는다. 원본 줄(어댑터가 해석 못 한 줄)은 숨기고 체크하면 보인다. 한 번에 최대 5000항목을 받고, 더 있으면 [나머지 기록 더 불러오기].
- **이유:** 노드 로그의 목적은 병목·실패 원인 찾기다(도구 호출의 시간과 결과 첫 줄이 먼저 보이면 된다).
- **영향 범위:** 아주 긴 실행은 받은 항목을 메모리에 모두 둔다(화면에 그리지는 않음).

## D-067. 그래프의 첫 화면 크기 (M6b)

- **질문:** 단계가 많은 템플릿을 좁은 캔버스에 모두 맞추면 글자를 읽을 수 없다. 처음에 어디를 보여 줄 것인가?
- **고른 기본값:** 전체가 0.8배 이상으로 들어가면 전체를 맞춘다. 아니면 0.8배로, 선택한 노드(없으면 대기·완료가 아닌 첫 노드 = 지금 티켓을 붙잡은 곳)를 가운데에 두고 그래프 양 끝을 넘어 비지 않게 한다. 확대·축소·이동은 사람이 한다.
- **이유:** 사람이 그래프를 여는 이유는 대개 "지금 어디서 멈췄나"다.
- **영향 범위:** 화면만.
